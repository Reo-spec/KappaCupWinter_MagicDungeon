教材の目次 デバッグGUI

エンジン改造の内容とマージの手引き

k2Engine にデバッグGUI（Dear ImGui）、GOHandle、 簡易プロファイラを組み込みました。 学習教材（LV1〜LV5 全92章）が、この機能を前提に書かれています。

この文書は、変更をレビューしてマージする人向けです 学生向けの使い方は デバッグGUI と GOHandle にあります。

1. 先に読んでほしいこと ― 差分が巨大に見えます

git diff --stat を素で叩くと、約4,300行の変更に見えます。 これはほぼ全部が改行コードの差です。

見方結果
git diff --stat4,345行追加 / 3,982行削除
git diff --ignore-cr-at-eol --stat 377行追加 / 14行削除

作業ツリーが CRLF、git 内のブロブが LF という状態がこの改造より前からあります （.gitattributes が無く、core.autocrlf の設定に依存している状態）。 触ったファイルを保存すると、その行が全部 CRLF になって差分に出てきます。 

# レビューはこれで
git diff --ignore-cr-at-eol -- GameTemplate/k2Engine GameTemplate/k2EngineLow
改行コードの問題自体には、手を付けていません .gitattributes を足すとリポジトリ全体が一度に書き換わるので、 この改造とは別に判断していただくのが良いと考えました。

2. 削除された14行について

実質差分の「14行削除」は、すべて字下げの変更です。 K2_PROFILE_SCOPE を入れるために { } で囲んだ結果、 元の行が消えて字下げ後の行が足された形で出ています。 

// 変更前
g_engine->ExecuteUpdate();
m_renderingEngine.Update();

// 変更後
{
    K2_PROFILE_SCOPE("Update");
    g_engine->ExecuteUpdate();
    m_renderingEngine.Update();
}

呼び出しの順番も内容も変えていません。 消した処理はひとつもありません。

5. 丸ごと無効にできます

k2EngineLow/dbg/DebugConfig.h の1行です。 

#define K2_ENABLE_DEBUG_GUI

これをコメントアウトすると、デバッグGUIもプロファイラも一切動かなくなります。 K2_PROFILE_SCOPE と K2_COUNT_DRAW_CALL は空のマクロになります。

前提にしていること理由
ImGui:: の呼び出しは、 DebugGui::RegisterPanel() で登録した関数の中だけに書く 無効時は、その関数が一度も呼ばれないので、 define を消すだけで丸ごと外れる

この約束は DebugConfig.h のコメントにも書いてあり、 教材の 2-23 でも同じことを教えています。

6. 判断をお願いしたいところ

実装中に気づいた点です。いずれも今回は手を付けていません。

#内容今回の扱い
1 RenderingEngine::EnableRaytracing() が true && IsEnableRaytracing() という式になっており、 引数が使われていません 既存のバグに見えますが、直していません。 レイトレのトグルもパネルに出していません
2 Dof と Ssr が、基底の m_isEnable を それぞれ自前のメンバで隠しています 基底を触らず、各クラスに IsEnable() を足して回避
3 設定の保存が key=value のテキストです（JSONではない） kxEngine が Game.sln に入っておらず、 JSONライブラリが使えなかったため。 必要なら差し替えられるよう DebugSettings に閉じてあります
4 作業ツリー CRLF / git 内 LF（第1節） この改造より前からの状態。別途ご判断ください
5 GameObjectManager.h だけ UTF-8 BOM、 他は CP932 これも既存の状態。各ファイルの元の文字コードに合わせて書いています

8. マージの順番（おすすめ）

一度に入れるのが不安な場合、この順で分けられます。 どこで止めても動きます。

段入れるものこれだけで使えるもの

9. 改造はしていないが、見つかったこと

教材 LV5-16 の完成形サンプル （Sample/Goal_LV5）を作るときに計測して分かったことです。 エンジンには手を入れていません。 判断が要ることなので、報告だけします。

Sprite::Init が毎回 HLSL をコンパイルし直しています Sprite::Init → InitShader → Shader::LoadVS / LoadPS → D3DCompileFromFile という流れで、 Shader::Load にキャッシュがありません （k2EngineLow/graphics/Shader.cpp:25）。
つまり 同じ .fx・同じエントリポイントでも、 SpriteRender を1つ作るたびにコンパイルが走ります。

実測（Debug ビルド、Assets/shader/sprite.fx、VS と PS で2回）:

SpriteRender の数シーン開始で止まる時間
256約 2.5 秒
768約 7 秒
1024約 10 秒
2048約 20 秒（ハングに見える）

1枚あたり およそ 10ms。 弾幕シューティングのようにスプライトを大量にプールする作りだと、 ここがそのままロード時間になります。 学生が「起動が固まる」と言ってきたとき、たいていこれです。

直すなら Shader::Load に (filePath, entryFuncName, shaderModel) をキーにした std::unordered_map のキャッシュを1枚かぶせるだけです。 ID3DBlob* を使い回せば、上の表はほぼゼロになります。

今回は入れていません シェーダの寿命とスレッドの扱いをどうするかは エンジンを持っている人が決めることだと思ったためです。
サンプル側は弾プールを 256 に抑えることで回避し、 「なぜ 256 なのか」を Goal_LV5/readme.txt に 計測結果ごと書いて、学生への教材にしてあります。
