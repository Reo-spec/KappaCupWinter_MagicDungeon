# コーディング規約

このドキュメントは、MagicDungeon の `Game05/Game/` 以下の C++ コードを書く・読むときのルールをまとめたもの。
ルールだけを覚えるのではなく、「なぜそのルールがあるのか」を理解して使うこと。理由が分からなくなったら、このファイルの該当行を読み返す。

**適用範囲**: 自分で書くゲーム側のコード（`Game05/Game/` 以下）だけ。学校の内製エンジン（`k2Engine/`、`k2EngineLow/`）は配布されたものなので、このルールに合わせて書き換えない。エンジンの書き方（古い `enum`、`/// <summary>` 形式のコメント、CP932 の文字コードなど）がこの規約と違っていても、それは正しい状態。

**今あるコード**: この規約より前に書いたコードには、ルールに合っていない所がある。一度に全部直すのではなく、そのファイルを触るときに合わせていく。

## 基本ルール

| # | 項目 | ルール | なぜ |
|---|------|--------|------|
| R-01 | 文字コード | UTF-8（BOM付き）に統一。`Game05/Game/.editorconfig` で強制する | Visual Studio のコンパイラは、BOM のない UTF-8 のファイルを CP932（Shift-JIS）として読む。すると日本語コメントの最後のバイトと `*/` がくっついてコメントが閉じなくなり、エラー C1071「コメント内で予期しない EOF」になることがある。原因がコードの中身ではなく文字コードなので、エラーを見ても気づきにくい。人の注意力ではなく `.editorconfig` という仕組みで最初から固定する。エンジン側は CP932 のままなので、`.editorconfig` は `Game05/Game/` にだけ置いている |
| R-02 | 改行コード | CRLF に統一 | 開発環境が Windows / Visual Studio だけで、LF と混ぜるメリットがない。混ざると差分（diff）にノイズが出て、変更点が読みにくくなる |
| R-03 | クラス名 | UpperCamelCase。例: `Player`、`MagicSelectUI` | C++ では名前の形以外に「型か値か」を一目で見分ける手段がない。型名を大文字始まりに固定しておけば、宣言を読み返さずに済む |
| R-04 | メンバ変数 | `m_` を前置。例: `m_position`、`m_selectedSlot` | `SetPosition(const Vector3& position)` のように、引数名とメンバ名が同じ単語になりやすい。`m_` がないと「引数への代入か、メンバへの代入か」を毎回確認することになる |
| R-05 | 構造体のメンバ | `m_` を付けない。例: `moveSpeed`。構造体名自体はクラスと同じく UpperCamelCase（例: `AttackMagicStatus`） | クラスと構造体を書き分けるのは、「ふるまいを持つ実体」と「ただのデータの入れ物」を区別したいから。魔法のステータス（速度・威力・寿命）は「ただの数値のまとまり」なので構造体にする。`m_` の有無をその境界線にすると、名前を見ただけでどちら側か分かる |
| R-06 | enum | 新規は `enum class`。基底型を明示する。例: `enum class EnMagicType : uint8_t` | エンジンの `EnButton` は `enButtonA` のように接頭辞を付けて名前の衝突を避けているが、これは古い `enum` にスコープがないための苦肉の策。`enum class` ならスコープが衝突を防ぐので接頭辞がいらず、暗黙の int 変換によるバグも防げる。その代わり、魔法プールの配列の添え字に使うときのように、`static_cast<uint8_t>(EnMagicType::Fire)` が必要になる |
| R-07 | ドキュメント | `/** */` の Doxygen 形式に統一 | ゲーム側のコメントの書き方を1つに決めておかないと、同じファイル内でコメントの見た目が揺れて読みにくくなる。エンジンは `/// <summary>` 形式だが、エンジンはこの規約の対象外なので合わせない |
| R-08 | 綴り | 英単語は辞書で確認してから使う | 綴りミスはコンパイルエラーにならない。特に `NewGO<MagicSelectUI>(0, "magicSelectUI")` と `FindGO<MagicSelectUI>("magicSelectUI")` のように、ゲームオブジェクトの名前を文字列で書く場面では、片方だけ綴りを間違えると「見つからない」バグになり、コンパイラは何も教えてくれない。書く瞬間に確認する以外に防ぐ方法がない |
| R-09 | 未使用コード | 使わなくなったコードはコメントアウトせず削除する | 「後で使うかも」で残したコメントアウトは、検索の邪魔になり、今動いているコードがどれか分かりにくくなる。たとえば古い魔法の enum がコメントアウトで残っていると、どちらが本物か迷う。本当に必要になったら GitHub の履歴（`git log`）から戻せる |
| R-10 | 例外の明記 | ルールを破るときは、理由をコメントで書く | このルールは今の時点で分かっている範囲の判断でしかなく、将来のすべてのケースを予見できない。破っていいかを毎回悩むより、「なぜ破ったか」を1行残すほうが安く、後から読む自分がルールと実装のどちらを信じればいいか迷わずに済む |

## 追加ルール

### 関数名の命名規則

**ルール: メンバ関数（`public` / `private` / `static` を問わない）は UpperCamelCase とし、動詞、または `Get` / `Set` / `Is` / `Can` などの接頭辞＋名詞で始める。**
例: `Update()`、`RotateRight()`、`GetSelectedSlot()`、`SetPositionAndDirection()`、`IsTrigger()`

理由: エンジン（`g_pad[0]->IsTrigger()`、`GetLStickXF()` など）が既にこの形式で書かれている。ゲーム側も同じ形にしておけば、エンジンの関数と自分の関数が並んだときに見た目がそろい、呼ぶ側のコードを読むときに迷わない。ローカル変数・引数は逆に lowerCamelCase（`magicPos`、`status` など）にする。大文字始まりは「関数と型」、小文字始まりは「値」という使い分けになる。

### 定数の命名規則

**ルール: `constexpr` などの定数は、全部大文字＋アンダースコア区切り（UPPER_SNAKE_CASE）にする。**
例: `ONE_THIRD_CIRCLE`（`MagicSelectUI.cpp` の、円の3分の1 = 120度）

理由: 定数は「途中で値が変わらない」ことを名前で示しておくと、読む側が代入されていないか探さなくて済む。メンバ変数（`m_`）やローカル変数（小文字始まり）と見た目で区別できる。

### キャストの書き方

**ルール: キャストは C 言語形式の `(int)a` ではなく、`static_cast<int>(a)` を使う。**

理由: `(int)` はどんな変換でも通してしまい、危ない変換をしても気づけない。`static_cast` は意図しない変換をコンパイラが止めてくれるうえ、「ここで型を変えている」ことが文字で目立つので、読む側にも分かりやすい。

### const の付け方

**ルール: 引数・ローカル変数・メンバ関数でも、途中で値を変えないものには `const` を付ける。** const 参照（`const Vector3&`）だけでなく、値で受け取る引数（`const float rate`）や、計算結果を入れておくだけのローカル変数（`const float dt = g_gameTime->GetFrameDeltaTime();`）も対象。メンバを書き換えない関数は `const` メンバ関数（`GetSelectedSlot() const`）にする。

理由: 学校の先生のコードレビューで指摘された。`const` は「この値は変わらない」という制限を自分でかけておくもので、うっかり書き換えるとコンパイラが止めてくれる。たとえば魔法の発射位置や向きを計算したあとに、別の処理で書き換えてしまうと「弾が変な方向に飛ぶ」バグになるが、`const` にしておけばその時点でコンパイルエラーになる。読む側も、その変数が後で書き換えられていないかを探さずに済む。

### マジックナンバーを書かない

**ルール: コードの中に意味の分からない数値を直接書かない。名前を付けた `constexpr` の定数にする。** `0`、`1`、`0.5f`（半分）、`1000.0f`（秒→ミリ秒）のように、見れば意味が分かるものは直接書いてよい。

- 魔法のダメージ・クールダウン・速度・寿命など、遊んで調整したい値の置き場所は、設計を見直し中。決まったらここに書く
- それ以外の、配列の大きさや計算のための値（`ONE_THIRD_CIRCLE` など）は、使う所の近くで `constexpr` にする
- JSON などの外部ファイルから読む仕組みは、まだない。導入したら、調整したい値は外部ファイルに移し、この節を書き直す

理由: 学校の先生のコードレビューで指摘された。たとえば `1.5708f` と書いてあるだけでは、それが「90度（π/2 ラジアン）」のことで、魔法選択リングの最初の向きだとは分からない。`-700.0f` もそれだけでは、UI を画面のどこに置くための値なのか分からない。同じ値を何か所にも書くと、直すときに1か所だけ直し忘れる。名前を付けておけば意味が分かり、直す場所も1か所になる。

### 1つしかあってはいけないクラス（シングルトン）

**ルール: ゲーム全体で1つしかあってはいけないもの（入力やサウンドの管理役など）は、シングルトンにして複製できないようにする。** コンストラクタを `private` にし、コピーを禁止し（エンジンの `Noncopyable` を継承するか、コピーコンストラクタと代入演算子を `= delete` で消す）、`Get()` などの `static` 関数から唯一の実体を受け取る形にする。

理由: 学校の先生のコードレビューで指摘された。たとえば入力の管理役が2つ作られると、片方だけが毎フレーム更新され、もう片方は古い入力を返し続ける、という分かりにくいバグになる。作れないようにしておけば、間違えたときにコンパイラが止めてくれる。ただし、どこからでも呼べる分、どのクラスが何に頼っているかが見えにくくなるので、何でもシングルトンにはしない。本当に1つしかあってはいけないものだけにする。

### `#include` の並べ方

**ルール:**
1. `"stdafx.h"`（必ず最初）
2. 対応する自分自身のヘッダ（`.cpp` なら同名の `.h`）
3. 空行
4. 依存するゲーム内ヘッダ（フォルダ分けしたら、フォルダ名込みのパスで。例: `"magic/Magic.h"`）

理由: このプロジェクトはプリコンパイル済みヘッダ（`stdafx.h`）が `k2EnginePreCompile.h`（エンジン）を一括で取り込んでいるので、各 `.cpp` / `.h` がエンジンや標準ライブラリのヘッダを直接 `#include` する場面はほぼない。一般的な「標準ライブラリ → エンジン → ゲーム内コード」の3段のうち、最初の2段は `stdafx.h` が肩代わりしている形になる。今は `Game05/Game/` 直下にファイルを置いているが、魔法・敵・UI などでファイルが増えてフォルダ分けしたときに、どこのファイルか分かるようにフォルダ名込みで書く。

### 1ファイルの行数の上限

**結論: 未定。**

理由: 問題になるのは「行数が多いこと」そのものより、「1つのクラスが本来持つべきでない責任を持っていること」のほうが多い。例えば、分岐が多いだけで1つ1つの処理は単純なファイルもあれば、短くても色々な仕事を抱え込んでいるクラスもある。行数に数字を決めると、前者を機械的に分けることになる一方、後者を見逃してしまう。今の1人・学習段階の規模では、「このクラスは何をするクラスか一言で言えるか」をレビューのたびに確かめるほうが効果がある（例: `MagicSelectUI` は「魔法選択リングを回して、選んでいる魔法を表示するクラス」と言える）。コードが大きくなって目が届かなくなったら、そのときの実際の行数を見て数字を決める。

このゲームでは、7種類の魔法・敵・宝箱などの処理が `Player` に集まりやすい。「プレイヤーの移動」以外の仕事が増えてきたら、行数ではなく役割の問題として、別のクラスに分けることを検討する。

### パラメータを外部ファイルから読む場合

**ルール: 速度や敵の強さなどのパラメータを JSON などの外部ファイルから読むようにした場合、キーが見つからないときに既定値で黙って動かさず、エラーで止めて気づけるようにする。**

理由: このゲームは魔法ごとのダメージ・クールダウン・速度の差（雷は少し短い、闇は少し長い、など）が手触りに直結するので、パラメータを外部ファイルに出して何度も調整することになる可能性が高い。キー名を打ち間違えたときに既定値で動き続けると、「調整したつもりが全く反映されていない」という原因の分かりにくいバグになる。開発中は止まって気づけるほうが安全。

ただし、配布したあとにユーザーの手元でファイルが壊れていた場合、同じ動きだと「起動すらしない」という最悪の体験になる。GFF に提出する段階になったら、提出版では警告を出しつつ既定値で動かすように切り替えるかを検討する。
