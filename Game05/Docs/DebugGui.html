デバッグGUI と GOHandle

k2Engine に Dear ImGui によるデバッグGUIと、ゲームオブジェクトを安全に参照するための GOHandle を組み込みました。

用意されているパネルは次の3つです。

メニューパネル内容
GameObjectGameObject List生きているゲームオブジェクトの一覧
GraphicsLightディレクショナルライトと環境光
GraphicsPost Effectブルーム、トーンマップ、FXAA、被写界深度、SSR
ProfilerProfiler処理時間、ドローコール、メモリ使用量

1. まず起動してみる

ゲームを起動すると、画面の一番上に黒いメニューバーが出ています。

[Debug] [GameObject]                                    62.5 FPS (16.01 ms)
  • F1キー で、デバッグGUI全体の表示/非表示が切り替わります。
  • [GameObject] メニュー → GameObject List を選ぶと、

いま生きているゲームオブジェクトの一覧が出ます。

ウィンドウの位置や大きさは imgui.ini に自動で保存されるので、次に起動したときも同じ配置で開きます。

まずこれを見る癖をつける

  • 敵を倒したのに数が減らない → 同上
  • Dead(waiting) がずっと残っている → 削除処理が止まっている

「動いているけど、なんか重い」の原因はだいたいここで見つかります。

3. 「削除済みオブジェクトにアクセスする」バグ

k2Engine で一番多い事故がこれです。パネルを使うと目で見て確認できます。

何が起きているのか

DeleteGO() は 「死亡予約」をするだけ で、その場ではメモリを解放しません。

このバグの本当に怖いところ

クラッシュしないことがある。

解放されたメモリがまだ上書きされていなければ、何事もなく動いてしまいます。そして、まったく関係ない場所で、何日か経ってからクラッシュします。「昨日は動いてたのに」の正体はこれです。

GameObject List パネルで、DeleteGO ボタンを押した直後にState が赤い DEAD になり、次のフレームで行が消えることを実際に目で見て確認してみてください。

4. GOHandle — 安全に他のオブジェクトを覚えておく

ダメな書き方

class Missile : public IGameObject {
    Enemy* m_target = nullptr;      // 生ポインタで敵を覚えておく
};

void Missile::Update()
{
    // 敵がすでに DeleteGO されていたら、ここで事故る
    HomingTo(m_target->GetPosition());
}

良い書き方

class Missile : public IGameObject {
    GOHandle<Enemy> m_target;       // ハンドルで敵を覚えておく
};

bool Missile::Start()
{
    Enemy* enemy = FindGO<Enemy>("enemy");
    m_target.Reset(enemy);          // ハンドルに覚えさせる
    return true;
}

void Missile::Update()
{
    Enemy* target = m_target.Get();     // 毎回取り直す
    if (target == nullptr) {
        // 敵はもういない。自分も消える。
        DeleteGO(this);
        return;
    }
    HomingTo(target->GetPosition());
}

仕組み

GOHandle はポインタではなく インスタンスID を覚えています。Get() を呼ぶたびに GameObjectManager へ

「このIDのオブジェクト、まだ生きてる？」

と問い合わせます。死んでいれば nullptr が返ってきます。IDは使い回されないので、別のオブジェクトと取り違えることもありません。

API

関数説明
Reset(T* go)参照するオブジェクトを設定する
Get()生きていればアドレス、死んでいれば nullptr
IsAlive()生きているか
Clear()参照を空にする
GetInstanceID()参照しているインスタンスID

なぜ -> が使えないのか

GOHandle には わざと operator-> を用意していません。

m_target->Update();     // ← こう書けてしまうと、nullチェックを忘れる

必ず Get() でポインタを受け取り、nullptr かどうかを確認してください。「ちょっと面倒くさい」と感じる書き方が、バグを防いでくれます。

4.5 Light / Post Effect パネル — 見た目を調整する

Graphics メニューから開きます。シェーダを書く前に、まずこのスライダーを動かして絵がどう変わるかを体で覚えてください。

Light パネル

項目意味
ambient環境光。どこからともなく当たっている光。影の中の明るさがこれで決まる
direction光が進んでいく向き。{0, -1, 0} なら真上から真下。長さは自動で1に直される
colorライトの色と強さ。1.0より大きい値を入れるとより強く光る
cast shadowこのライトで影を落とすかどうか

ディレクショナルライトは4つまで使えます（0番が既定で影を落とします）。

やってみよう

  • ambient を真っ黒にすると、影の中が何も見えなくなります
  • direction を横向きにすると、夕方のような長い影になります
  • color を 3.0 くらいまで上げると、ブルームがはっきり出ます

Post Effect パネル

項目意味
Bloom明るい部分をにじませる。threshold を超えた明るさだけがにじむ
Tone map明るさを画面に表示できる範囲に収める。middle gray はカメラの露出のようなもの
FXAA輪郭のギザギザをなめらかにする（アンチエイリアス）
Depth of fieldピントの合っていない距離をぼかす
SSR床などへの映り込み。レイトレーシングが有効なときは実行されません

やってみよう

  • Tone map を切ると、明るいところが真っ白につぶれます
  • FXAA を切って、輪郭を拡大して見比べてみてください
  • Bloom の threshold を 0 に近づけると、画面全体がぼんやり光ります

調整した値を保存する

両方のパネルの一番下にある Save / Load ボタンで、Assets/settings/renderSettings.txt に保存・復元できます。

# k2Engine debug settings
# Saved from the debug GUI. You can edit this file by hand.

light.directional.0.direction  = 0.5774 -0.5774 -0.5774
light.directional.0.color      = 1.2000 1.2000 1.2000
light.directional.0.castShadow = 1
light.ambient                  = 0.1000 0.1000 0.1000
postEffect.bloom.enable        = 1
postEffect.bloom.threshold     = 1.0000
postEffect.tonemap.enable      = 1
postEffect.tonemap.middleGray  = 0.1800
postEffect.fxaa.enable         = 1
postEffect.dof.enable          = 0
postEffect.ssr.enable          = 1

ただのテキストファイルなので、メモ帳で開いて直接書き換えることもできます。書かれていない項目は、今の設定のまま残ります。

保存した設定をゲーム開始時に自動で反映したい場合は、ライトを設定しているコードのあと で読み込んでください。

bool Game::Start()
{
    // ...自分のライト設定...

    // デバッグGUIで調整した設定を反映する。
    nsDbg::LoadRenderSettings();
    return true;
}

エンジンの初期化直後には読み込んでいません。そこで読み込んでも、そのあとのゲーム側のライト設定で上書きされてしまうためです。

EndFrame(Present/Wait) が長いのは正常です

EndFrame(Present/Wait) には、60fpsに合わせるための「何もしないで待っている時間」 が含まれています。ここが長いのは、処理に余裕があるということです。

ここが短くなってきたら、処理が重くなってきたサインです。

自分のコードを計測する

計測したい { } の先頭に1行書くだけです。

void Player::Update()
{
    K2_PROFILE_SCOPE("Player");

    Move();
    Turn();
}

入れ子にもできます。

void Player::Move()
{
    K2_PROFILE_SCOPE("Player Move");
    ...
}

K2_PROFILE_SCOPE は、その { } を抜けた瞬間に自動で計測を終了します（DebugGuiPanel と同じ RAII の仕組みです）。return で途中で抜けても、ちゃんと計測されます。

注意 計測自体にも少しだけ時間がかかります。 1フレームに何千回も呼ばれる関数（弾1つ1つの Update など）に入れると、 計測が重くなって正しい値が測れません。 まずは大きい単位（Player 全体、敵全体 など）から入れて、 重い場所を絞り込んでいってください。

最適化の手順

「速くなった気がする」は最適化ではありません。 かならずこの順番で。

  1. 計測する — どこが重いのかをProfilerで確認する
  2. 仮説を立てる — なぜ重いのかを考える
  3. 直す — 一箇所だけ直す
  4. もう一度計測する — 本当に速くなったか数字で確認する

5. 自分のデバッグパネルを作る

一番かんたんな書き方

DebugGui::RegisterPanel("Game", "Score", []() {
    ImGui::Text("score = %d", g_score);
});
  • 第1引数：メニューバーでの分類名（好きな名前でよい）
  • 第2引数：パネルの名前（ウィンドウのタイトルになる）
  • 第3引数：中身を描画する関数

ImGui::Begin() / ImGui::End() は書かなくて大丈夫です。エンジンがやります。

ゲームオブジェクトの中から作る場合

this をキャプチャしたラムダ式を登録したまま、そのゲームオブジェクトが死ぬと、削除済みのメンバ変数を触ってクラッシュします。DebugGuiPanel をメンバ変数として持つと、自動的に登録が解除されます。

class Player : public IGameObject {
public:
    bool Start() override;
    void Update() override;
private:
    int   m_hp = 100;
    float m_speed = 200.0f;
    DebugGuiPanel m_debugPanel;     // メンバ変数として持つ
};

bool Player::Start()
{
    m_debugPanel.Register("Game", "Player", [this]() {
        ImGui::Text("HP = %d", m_hp);
        ImGui::SliderFloat("speed", &m_speed, 0.0f, 500.0f);
        if (ImGui::Button("full heal")) {
            m_hp = 100;
        }
    });
    return true;
}

Player が破棄されると、m_debugPanel のデストラクタが呼ばれ、パネルの登録も自動的に消えます。（このやり方を RAII と呼びます。C++では非常によく使われる考え方です）

よく使う ImGui の部品

ImGui::Text("hp = %d", hp);                         // 文字
ImGui::SliderFloat("speed", &speed, 0.0f, 500.0f);  // スライダー
ImGui::DragFloat3("position", &pos.x, 1.0f);        // 座標（3つまとめて）
ImGui::Checkbox("invincible", &isInvincible);       // チェックボックス
ImGui::ColorEdit3("color", &color.x);               // 色
if (ImGui::Button("respawn")) { Respawn(); }        // ボタン
ImGui::Separator();                                 // 区切り線
ImGui::SameLine();                                  // 次を同じ行に置く

どんな部品があるか全部見たいときは、メニューの Debug → ImGui Demo を開いてください。ImGui でできることのカタログになっています。気になった部品の名前で imgui_demo.cpp を検索すれば、書き方がそのまま載っています。

6. 日本語を表示したいとき

ImGui に渡す文字列は UTF-8 でなければいけません。ところが Visual Studio で作ったソースファイルはたいてい Shift-JIS なので、そのまま書くと文字化けします。

ImGui::Text("敵の数 = %d", num);        // 文字化けする
ImGui::Text(U8("敵の数 = %d"), num);    // 正しく表示される

U8() で囲んでください。英数字だけの文字列や、すでに UTF-8 のファイルに書かれた文字列はそのまま素通しされるので、とりあえず付けておいても害はありません。

7. デバッグGUIを完全に外す

作品の提出用ビルドなどで、デバッグ機能を丸ごと消したいときは、k2EngineLow/dbg/DebugConfig.h にある定義をコメントアウトします。

//#define K2_ENABLE_DEBUG_GUI

これで初期化も描画も行われなくなり、登録したパネルの関数も一度も呼ばれなくなります。K2_PROFILE_SCOPE と、ドローコールの計測も、何もしないコードに置き換わります。

このため ImGui::〜 の呼び出しは、必ず登録したパネル関数の中に書いてください。Update() の中などに直接書くと、この定義を消したときにクラッシュします。

Game/system/system.cpp は変更していません。ウィンドウプロシージャはエンジン側から SetWindowLongPtr で差し替えているので、既存の Sample や学生のプロジェクトは何も直さずにそのまま動きます。

注意点

  • ImGui 用の SRV ディスクリプタヒープは、エンジンのヒープとは別に確保しています

（DebugGui.cpp の SrvDescriptorHeap、64 個）。デバッグで画像をたくさん表示したくなったら SRV_DESCRIPTOR_NUM を増やしてください。

  • ImGui の描画は K2EngineLow::EndFrame() の中、EndRender() の直前で行っています。

フレームバッファに対する描画の一番最後である必要があります。

  • Effekseer の中（ExEngine/effekseer/3rdParty/LLGI/examples/thirdparty/imgui）にも

古い ImGui が同梱されていますが、ビルド対象外です。インクルードパスを共有しないよう注意してください。

  • Dof と Ssr は、基底クラス PostEffectComponentBase の m_isEnable とは別に

自前の m_isEnable を持っていて、OnRender() の中で判定しています。そのため ON/OFF は Dof::Enable() / Ssr::Enable() 側を呼ぶ必要があります（基底クラスの Enable() は名前が隠されていて呼べません）。

  • SSAO は PostEffect::Render() で呼び出しがコメントアウトされたままです。

そのためパネルにも出していません。

  • 設定ファイルが JSON ではなく「キー = 値」形式なのは、

このソリューションに JSON ライブラリが含まれていないためです。パーサを自作するより、学生が直接読み書きできる単純な形式のほうが安全だと判断しました。

  • ImGui を更新するときは ExEngine/imgui/ のファイルを上書きコピーするだけです

（バージョンは ExEngine/imgui/IMGUI_VERSION.txt に記録）。
