02ベクトルとは「向きと長さ」

Vector3 は数字が3つ入っているだけの箱ですが、 使い方によって意味が変わります。

使い方意味例
位置原点からどこにいるかm_position
向きと距離AからBへどう行くかB - A
速度1秒でどれだけ動くかm_velocity

いちばん大事なのは「引き算」です。 B - A は「AからBへ向かうベクトル」になります。 その長さが、AとBの距離です。 

Vector3 diff = enemyPos - bulletPos;   // 弾から敵へ向かうベクトル
float distance = diff.Length();        // その長さ ＝ 距離

03円と円の当たり判定

bool IsHit(const Vector3& posA, float radiusA,
           const Vector3& posB, float radiusB)
{
    Vector3 diff = posB - posA;
    float distance = diff.Length();
    return distance < radiusA + radiusB;
}

04平方根をなくす

Length() の中では平方根の計算をしています。 これは、足し算やかけ算にくらべて重い処理です。

でも、よく見てください。やりたいのは大小の比較だけです。 距離そのものが欲しいわけではありません。 なら、両方を2乗したまま比べればいいのです。 

bool IsHit(const Vector3& posA, float radiusA,
           const Vector3& posB, float radiusB)
{
    Vector3 diff = posB - posA;

    float distanceSq = diff.LengthSq();          // 距離の2乗
    float radiusSum  = radiusA + radiusB;
    float radiusSumSq = radiusSum * radiusSum;   // 半径の和の2乗

    return distanceSq < radiusSumSq;
}
なぜ2乗のまま比べてよいのか 距離も半径も必ず0以上だからです。 0以上の2つの数は、2乗しても大小の関係が変わりません。 （3 < 5 なら 9 < 25）
これは、ゲームプログラミングでは常識レベルのテクニックです。 覚えておいてください。

05弾と敵の判定を書く

弾のほうから敵を探して判定します。 

void Bullet::Update()
{
    const float dt = g_gameTime->GetFrameDeltaTime();
    m_position.y += SPEED * dt;

    if (m_position.y > 600.0f) {
        DeleteGO(this);
        return;
    }

    CheckHitToEnemy();

    m_spriteRender.SetPosition(m_position);
    m_spriteRender.Update();
}

void Bullet::CheckHitToEnemy()
{
    const auto& enemies = FindGOs<Enemy>("enemy");
    for (auto enemy : enemies) {
        Vector3 diff = enemy->GetPosition() - m_position;
        float radiusSum = RADIUS + enemy->GetRadius();

        if (diff.LengthSq() < radiusSum * radiusSum) {
            // 当たった。
            enemy->TakeDamage(1);
            DeleteGO(this);
            return;              // ★ 自分を消したら、すぐ帰る
        }
    }
}
同じフレームで両方が消えるとどうなる？ 弾も敵も DeleteGO されますが、 メモリはまだ1フレーム残っています（2-05）。 この相打ちの扱いは 2-17 でくわしくやります。

06当たり判定の半径は絵より小さく

見た目のスプライトが64ピクセルでも、 当たり判定の半径は32より小さくします。

理由は、そのほうが遊んでいて気持ちいいからです。 「当たっていないように見えたのに死んだ」はストレスになりますが、 「当たったように見えたけど助かった」は気になりません。 シューティングゲームでは、自機の判定は極端に小さく作るのがふつうです。

判定を目で見えるようにする 判定用の円をデバッグ表示すると、調整がとても楽になります。 半透明の円のスプライトを、判定の大きさで重ねて描いてみてください。 2-23 で、表示のON/OFFをGUIから切り替えられるようにします。

07演習

演習1（まねる）

弾と敵の当たり判定を書いて、当たったら両方消えるようにする。

演習2（見えるようにする）

当たり判定の円を半透明で表示して、見た目とどれだけ違うか確かめる。

解答例を見る（まず自分でやってから）

半透明の白い円の画像を1枚用意して、判定の大きさに合わせて重ねます。 

// Enemy.h
private:
    SpriteRender m_debugCircle;
    static bool  s_isShowCollision;    // 全部の敵で共通のフラグ

// Enemy.cpp
bool Enemy::s_isShowCollision = false;

bool Enemy::Start()
{
    m_spriteRender.Init("Assets/sprite/enemy.dds", 64.0f, 64.0f);

    // 判定の直径ぴったりの大きさで読み込む。
    m_debugCircle.Init("Assets/sprite/circle.dds", RADIUS * 2.0f, RADIUS * 2.0f);
    m_debugCircle.SetMulColor({ 1.0f, 0.0f, 0.0f, 0.4f });   // 赤く半透明
    return true;
}

void Enemy::Render(RenderContext& rc)
{
    m_spriteRender.Draw(rc);
    if (s_isShowCollision) {
        m_debugCircle.Draw(rc);
    }
}

m_debugCircle も Update() で SetPosition → Update() するのを忘れないでください。

見て分かること 見た目の絵より、判定の円がずいぶん小さいはずです。 それが正しい状態です。 逆に、判定が絵からはみ出していると「当たっていないのに死んだ」になります。

表示のON/OFFを 2-23 の デバッグパネルから切り替えられるようにすると、調整がとても楽になります。

結果の予想と、実際

  • 弾500 × 敵100 ＝ 1フレームに5万回の判定です
  • いまのPCなら、どちらもコンマ数ミリ秒で終わります。 差が見えないことのほうが多いでしょう
  • それでも LengthSq() を使うのは、コストがゼロだからです。 同じ結果が得られて、確実に速いなら、そちらを選ばない理由がありません
この演習でいちばん大事なこと 「差が出なかった」という結果を、自分で確かめたことです。
LV5 でくわしくやりますが、 測らずに「速そう」で判断して、読みにくいコードを書くのが いちばんよくありません。 今回の LengthSq() は、読みやすさを損なわないので使うだけの話です。

08確認

  1. B - A というベクトルは何を表す？
  2. 円と円が当たっている条件を式で書くと？
  3. なぜ2乗のまま比べてよい？
  4. 当たり判定の半径を見た目より小さくするのはなぜ？
答え
  1. AからBへ向かうベクトル。その長さがAとBの距離。
  2. 中心の距離 < 半径A + 半径B
  3. 距離も半径も0以上なので、2乗しても大小の関係が変わらないから。
  4. 「当たっていないように見えたのに死んだ」を避けるため。遊び心地がよくなる。
