事故を起こしてみる ― 削除済みオブジェクトへのアクセス

01この章でできるようになること

  • 削除済みオブジェクトへのアクセスを自分で再現できる
  • クラッシュしたとき、デバッガで原因を特定できる
  • このバグがなぜ「たまにしか落ちない」のかを説明できる

02事故のコードを書く

敵を追いかけるミサイルを作ります。わざと危ない書き方をします。 

// Missile.h
#pragma once

class Enemy;

class Missile : public IGameObject {
public:
    bool Start() override;
    void Update() override;
    void Render(RenderContext& rc) override;
private:
    SpriteRender m_spriteRender;
    Vector3      m_position;
    Enemy*       m_target = nullptr;   // ★ 生ポインタで敵を覚えておく
};
// Missile.cpp
bool Missile::Start()
{
    m_spriteRender.Init("Assets/sprite/missile.dds", 32.0f, 32.0f);
    m_target = FindGO<Enemy>("enemy");   // 敵を探して覚える
    return true;
}

void Missile::Update()
{
    // ★ ここが事故の現場。
    //    m_target がもう死んでいても、そんなことは分からない。
    Vector3 toTarget = m_target->GetPosition() - m_position;
    toTarget.Normalize();
    m_position += toTarget * 400.0f * g_gameTime->GetFrameDeltaTime();

    m_spriteRender.SetPosition(m_position);
    m_spriteRender.Update();
}

そして、敵のほうは少ししたら自分で消えるようにします。

void Enemy::Update()
{
    m_frame++;
    if (m_frame == 120) {       // 2秒で消える
        DeleteGO(this);
        return;
    }
}

予想してください。 2秒後、何が起きますか？

  • ミサイルがクラッシュする？
  • ミサイルが止まる？
  • 何も起きない？

予想を決めてから、実行してください。

03何が起きたか

結果は、実行するたびに変わります。 次の3つのどれかになります。

04デバッガで原因を特定する

クラッシュしたら、あわてて「中断」を押して閉じないでください。 そこに答えが全部あります。

手順1 ― コールスタックを見る

Ctrl+Alt+C で呼び出し履歴を開きます。 いちばん上が、落ちた場所です。 

> Game.exe!Missile::Update()  行 24        ← ここで落ちた
  Game.exe!nsK2EngineLow::IGameObject::UpdateWrapper()
  Game.exe!nsK2EngineLow::GameObjectManager::ExecuteUpdate()
  ...

Missile::Update() の24行目。 m_target->GetPosition() の行です。

手順2 ― ポインタの中身を見る

m_target を選択して ウォッチに追加します（右クリック → ウォッチ式の追加）。 アドレスは入っているのに、中身がおかしいはずです。 

m_target        0x0000023f1c4a2e30 {...}       ← アドレスはある
m_target->m_position   {x=-4.31602e+08 y=-4.31602e+08 ...}   ← ゴミ

手順3 ― メモリウィンドウで確かめる

デバッグ → ウィンドウ → メモリ → メモリ1 を開き、 アドレス欄に m_target と打ちます。 

0x0000023F1C4A2E30  dd dd dd dd dd dd dd dd  dd dd dd dd dd dd dd dd
0x0000023F1C4A2E40  dd dd dd dd dd dd dd dd  dd dd dd dd dd dd dd dd
0xDD は「もう解放したメモリ」の印です Visual Studio の Debug ビルドは、delete したメモリを 0xDD で塗りつぶしてくれます。 ウォッチやメモリで 0xDD がずらっと並んでいたら、 それは「解放済みのものを触っている」という意味です。

ついでに覚えておくと得をする値： 0xCD = まだ初期化していないヒープ、 0xCC = まだ初期化していないスタック変数、 0xFD = 配列の外側（はみ出し検出用）。

05落ちないパターンも見てみる

ここが大事です。落ちないこともあることを、自分で確認します。 Enemy を消すタイミングを変えてみてください。 

if (m_frame == 120) {
    DeleteGO(this);
    return;
}

2-05 でやったとおり、DeleteGO の直後の1フレームは、 まだメモリが生きています。この間なら、ミサイルは 何事もなく正常に動きます。

  • GameObject List パネルで、敵が DEAD になっている
  • それでもミサイルは、その敵を正しく追いかけている
  • 次のフレームで敵の行が消えたあと、挙動がおかしくなる
「動いているから正しい」は成り立ちません このバグは、コンパイラも警告してくれませんし、実行しても止まりません。 だから、書き方のルールで防ぐしかありません。それが次の章です。

06同じ事故は、ほかにもいろいろな顔で出ます

「生ポインタで覚えておく」以外にも、同じ原因のバグはあります。 どれも「もういないものを、いると思って触る」です。

書き方何が起きるか
std::vector<Enemy*> m_enemies; に入れっぱなし 敵が死んでも配列にポインタが残り、次に回したときに落ちる
Start() で FindGO した結果を持ち続ける 相手が途中で死ぬと、同じ事故になる
親が子を DeleteGO、子も自分を DeleteGO 二重削除。解放済みメモリに書き込む
DeleteGO(this) のあとに return し忘れ 自分のメンバ変数を触り続ける

07演習

演習1（まねる）

本文のコードで実際にクラッシュさせ、コールスタックのスクリーンショットを撮る。 どの行で落ちたかを、自分の言葉でメモする。

演習2（観察する）

メモリウィンドウで 0xDD を自分の目で見る。 Release ビルドでも同じように 0xDD になるか、試して確かめる。

解答例を見る（まず自分でやってから）

Release ビルドでは 0xDD になりません。

0xDD で塗りつぶしているのは、Visual Studio の デバッグ用のメモリ管理（デバッグヒープ）です。 これは _DEBUG が定義されているときだけ働きます。 Release ビルドでは、解放したメモリの中身はそのまま残っているか、 別のものに使い回されるか、どちらかです。

ここが怖いところです Debug では落ちるのに Release では落ちない。あるいはその逆。 これが「提出したら動かなかった」の大きな原因のひとつです。
だから 2-24 の完成条件に 「Release ビルドでも動く」を入れています。

演習3（自分で書く）

m_target を触る前に if (m_target != nullptr) を足せば、 このバグは直るでしょうか。予想してから試してください。 直らないなら、それはなぜですか。

解答例を見る（まず自分でやってから）

直りません。

void Missile::Update()
{
    if (m_target != nullptr) {        // ← 意味がない
        m_target->GetPosition();      // ← やっぱり落ちる
    }
}

理由は単純です。DeleteGO(enemy) は、 あなたの m_target という変数に nullptr を代入しません。 DeleteGO は、あなたがどこにポインタを持っているかを知らないからです。

ポインタはただの数字です。指す先が消えても、その数字は変わりません。 「消えたことを、ポインタ自身は知らない」のがこの問題の本質です。

では、どうすれば「知っている人」に聞けるのか。 それが次の章の GOHandle です。

ヒント

DeleteGO は、あなたの m_target に nullptr を入れてくれるでしょうか？ DeleteGO は、そのポインタ変数がどこにあるか知りません。

08確認

  1. 削除済みのオブジェクトを触ったとき、起きうる3つの結末は？
  2. そのうち、いちばんたちが悪いのはどれ？ なぜ？
  3. メモリが 0xDD で埋まっているのは、どういう意味？
  4. nullptr チェックだけでは、なぜこのバグが防げない？
答え
  1. その場でクラッシュする／何事もなく動いてしまう／あとで別の場所で落ちる。
  2. 「何事もなく動いてしまう」。バグがあることに気づけず、 別の環境や、別の日に落ちるから。
  3. Debugビルドで delete 済みのメモリ。もう使ってはいけない領域。
  4. DeleteGO は、こちらが持っているポインタ変数に nullptr を代入してくれないから。 ポインタの値は、指す先が消えても変わらない。
