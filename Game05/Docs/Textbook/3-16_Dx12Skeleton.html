  • エンジンが隠していたものが、何だったか分かる
  • DirectX12 の用語が出てきても、話についていける
  • エンジンのコードを、自分で読み進められる
この章は「書く」章ではなく「読む」章です DirectX12 をゼロから書けるようになる必要はありません。 エンジンの中で何が起きているかを知り、用語を怖がらなくなるのが目的です。

02DirectX12 が難しいと言われる理由

ひとことで言うと、ドライバがやってくれていたことを、 全部自分でやるようになったからです。

DirectX 11 までDirectX 12
描画命令その場でGPUに送られる（ように見える） リストに積んで、まとめて送る
状態の設定1つずつ変えられる まとめて1つの塊にして、事前に作っておく
同期ドライバ任せ自分でやる
メモリドライバ任せ自分で管理
結果書きやすい／遅い 書きにくい／速い・予測しやすい

k2Engine は、この面倒な部分を全部引き受けています。 だから m_spriteRender.Draw(rc) の1行で絵が出るのです。

034つの登場人物

04RenderContext の正体

LV2 からずっと使ってきた RenderContext& rc。 これはコマンドリストの包み紙です。 

// あなたが書いてきたコード
m_spriteRender.Draw(rc);

// その中で、最終的にこうなっている
rc.SetPipelineState(...);        // どう描くか
rc.SetRootSignature(...);        // 何を渡すか
rc.SetVertexBuffer(...);         // 何を描くか
rc.SetIndexBuffer(...);
rc.DrawIndexed(...);             // 描け

「描け」と言った時点では、まだ何も描かれていません。 リストに積まれただけです。 1フレームぶん積み終えてから、まとめてGPUに送ります。

これで、3-15 の疑問が解けます GPUデバッガが「描画コマンドの一覧」を出せたのは、 本当にそういうリストが存在するからです。
あれは、このコマンドリストの中身そのものでした。

05エンジンのどこを読むか

読む順番が大事です。いきなり初期化から読むと挫折します。

順番ファイル見るもの
1k2EngineLow/graphics/RenderContext.h まずここ。関数名を眺めるだけでよい
2k2EngineLow/graphics/Sprite.cpp の Draw() いちばん短い「描く」の実装
3Sprite.cpp の Init() PSO とルートシグネチャを作っている
4k2EngineLow/graphics/GraphicsEngine.cpp の BeginRender/EndRender フレームの開始と終了。フェンスがここ
5GraphicsEngine.cpp の Init() 最後でよい。ここがいちばん長い
全部理解しようとしないでください 1回読んで分からないのが普通です。 必要になったときに、また戻ってくればいい。
「そういえばあのあたりに書いてあった」と思い出せるだけで、 充分に価値があります。

06知っておくと役に立つ用語

用語ひとことで
デバイス（Device）GPU そのもの。何かを作るときは必ず通る
スワップチェイン 画面に出すバッファの管理。 裏で描いて表と入れ替える
ディスクリプタヒープ 「このテクスチャはここ」という住所録
リソースバリア 「このテクスチャは、いまから読む用に使う」という宣言
レンダーターゲット 描き先（3-08）
ドローコール 「描け」の命令1回 （2-23 の Profiler）

リソースバリアは、DX12 らしさが出ている概念です。 GPU の中でも処理は並行して進むので、 「いま書き込み中のテクスチャを、別の処理が読んでしまう」 ことが起こりえます。 それを防ぐために、用途が変わるたびに宣言しているのです。

07演習

演習1（読む）

k2EngineLow/graphics/Sprite.cpp の Draw() を読む。rc. で始まる行だけを、順番に書き出してみる。

解答例を見る（まず自分でやってから）

書き出すと、だいたいこうなります（バージョンによって前後します）。 

rc.SetPipelineState(...)        // どう描くか
rc.SetPrimitiveTopology(...)    // 三角形として描く
rc.SetVertexBuffer(...)         // 頂点
rc.SetIndexBuffer(...)          // 頂点のつなぎ方
rc.SetDescriptorHeap(...)       // テクスチャ等の住所録
rc.DrawIndexed(...)             // 描け

気づいてほしいこと

  • 「描け」は最後の1行だけ。残りは全部「準備」
  • 準備の順番は、だいたい決まっている
  • DrawIndexed に K2_COUNT_DRAW_CALL が入っている （2-23 で数えていたのはここ）
3D のモデル描画も、同じ形をしています ModelRender はもっと長いですが、 やっていることは「準備 → 描け」の繰り返しです。 メッシュの数だけ繰り返しているだけ。

だからモデルの数を減らすとドローコールが減り、軽くなります。

演習2（対応させる）

3-15 でキャプチャした描画コマンドの一覧と、Sprite::Draw() のコードを突き合わせる。

解答例を見る（まず自分でやってから）

GPUデバッガに並んでいるコマンドと、 Sprite::Draw() の rc. の行が 一対一で対応しているのが見えるはずです。

C++ のコードデバッガでの表示（おおよそ）
rc.SetPipelineStateSetPipelineState
rc.SetVertexBufferIASetVertexBuffers
rc.SetIndexBufferIASetIndexBuffer
rc.DrawIndexedDrawIndexedInstanced

RenderContext は、DirectX12 の関数に 分かりやすい名前を付け直しているだけだと分かります。 （IA は Input Assembler の略です）

ここが LV3 のゴールです 自分が書いた1行が、GPU に届くところまで追えた。

m_spriteRender.Draw(rc) と書いたとき、 その先で何が起きているか、もう分かります。 エンジンはブラックボックスではなくなりました。

演習3（調べる）

「なぜ DirectX12 はコマンドリスト方式なのか」を調べて、自分の言葉で説明してみる。本文には答えがありません。

解答例を見る（まず自分でやってから）

いちばん大きな理由：複数のスレッドで同時に準備できるから

DirectX11 では、描画命令を出せるのは実質1つのスレッドだけでした。 CPU のコアが8つあっても、描画の準備には1つしか使えなかったのです。 

スレッド1 ―― 描画命令を全部積む ―――――――――――→ 遅い
スレッド2〜8 ―― 暇

DX12 では、コマンドリストをスレッドごとに作れます。 

スレッド1 ―― コマンドリストA（背景）  ┐
スレッド2 ―― コマンドリストB（敵）    ├→ まとめてキューへ
スレッド3 ―― コマンドリストC（UI）    ┘

ほかの理由

理由説明
ドライバの負担が減る DX11 はドライバが裏で最適化していた。 その処理が読めず、性能が予測できなかった
再利用できる 毎フレーム同じ描画なら、リストを使い回せる
PSO を事前に作れる DX11 は描画中に状態の組み合わせを見てシェーダを再コンパイルしていた。 これが突然のカクつきの原因だった
「明示的にする」という思想です DX12 の設計は、一貫して 「隠して自動でやる」のをやめて「書かせる」方向です。

書く量は増えますが、性能が読めるようになり、 遅い理由が自分のコードの中に見えるようになりました。

これは Vulkan や Metal も同じ方向です。 2010年代半ばのグラフィックスAPIは、揃ってこの選択をしました。

そして k2Engine は、その面倒さを引き受けています。

RenderContext も SpriteRender も、 DX12 の明示性を、また隠し直したものです。 学習用エンジンとしては正しい判断ですが、 隠されているものが何かを知った今なら、必要なときに自分で外せます。

08確認

  1. RenderContext の正体は？
  2. rc.DrawIndexed() を呼んだ瞬間、絵は描かれる？
  3. PSO（パイプラインステートオブジェクト）とは？
  4. フェンスは何のためにある？
答え
  1. コマンドリストの包み紙。DirectX12 の関数を使いやすくしたもの。
  2. 描かれない。リストに積まれるだけ。 フレームの終わりにまとめてGPUへ送られる。
  3. どのシェーダ・ブレンド・深度設定で描くかを、 まとめて1つにした塊。事前に作っておく。
  4. CPU が GPU の処理の完了を待つため。 使用中のリソースを壊さないように。

09LV3 を終えて

LV3 の始まりは、F1 を押してスライダーを動かすことでした。 終わりは、GPU に届く命令を読むことです。
