LV5 最適化 ／ 5-16

【研究課題】自分のゲームを2倍速くする

難易度 ／ 前提 5-01 , 5-13

行き詰まったら、完成形を見てください Sample/Goal_LV5 に、 この章に到達した状態のプロジェクトが入っています。
先に見てしまっても構いません。 読んで理解してから、自分のコードに戻ってください。
読む順番は Goal_LV5/readme.txt に書いてあります。 readme.txt には「測ったら、思っていたところが遅くなかった」という 計測の結果も書いてあります。そちらが本体です。

01やること

自分のゲームを、測って、速くして、レポートにまとめます。

4-16 が「設計」の総まとめだったように、 これは「性能」の総まとめです。

成果物は、速くなったゲームではなくレポートです 2倍にならなくても構いません。
「測って、仮説を立てて、試して、結果を記録した」 という過程が成果物です。

「試したが効果がなかった」も、立派な結果です。

02進め方

手順やること章
1 再現できる負荷テスト場面を作る 5-02
2 Release で測って、基準値を記録する 5-01
3CPU か GPU かを切り分ける 5-01
4いちばん重い場所を絞り込む 5-02

ルール：一度に変えるのは1つだけ 2つ変えて速くなっても、どちらが効いたか分かりません。
そして「片方は効いて、片方は遅くしていた」ということも起きます。

1つ変える → 測る → コミット。 4-13 と同じです。

03負荷テスト場面の作り方

毎回同じ条件で測れないと、比較になりません。 

// StressTest.cpp
namespace {

void DrawStressPanel()
{
    static int numEnemy  = 200;
    static int numBullet = 1000;

    ImGui::SliderInt(U8("敵の数"),   &numEnemy, 0, 1000);
    ImGui::SliderInt(U8("弾の数"),   &numBullet, 0, 5000);

    if (ImGui::Button(U8("この条件で配置"))) {
        ClearAll();
        srand(12345);                    // ★ 乱数の種を固定する
        for (int i = 0; i < numEnemy; i++) {
            CreateEnemy(enEnemyType_Zako, RandomPosition());
        }
        for (int i = 0; i < numBullet; i++) {
            FireBullet(RandomPosition(), RandomDirection());
        }
    }

    ImGui::Separator();
    if (ImGui::Button(U8("60フレーム測定"))) {
        BeginMeasure(60);
    }
    if (IsMeasureDone()) {
        ImGui::Text("平均 %.3f ms / 最大 %.3f ms",
                    GetAverageMs(), GetMaxMs());
    }
}

}
srand(12345) が大事です 乱数の種を固定すれば、毎回まったく同じ配置になります。
これがないと、測るたびに条件が変わって比較できません。

04仮説の立て方

「遅いから速くする」ではなく、 「なぜ遅いか」を先に言葉にしてください。

観察仮説の例試すこと
当たり判定が 6ms 弾×敵の総当たりで O(n²) まず範囲で絞る
敵を増やすと、比例以上に遅くなる キャッシュからあふれた SoA
Draw Call が 2000 1体ずつ描いている インスタンシング
ウィンドウを小さくすると速い GPU律速。ポストエフェクト 効果を切って確認
ボス出現時だけ跳ねる そこで読み込んでいる 先に読んでおく
長く遊ぶと遅くなる リークか断片化 5-14
仮説が外れることは、よくあります 外れたら、それも記録してください。
「SoA にしたが、0.02ms しか変わらなかった。 データが小さくて、もともとキャッシュに乗っていたため」
これは、成功と同じくらい価値のある記録です。

やること効果手間章

上から順に試してください 下のものほど、手間がかかって効果が小さい。
そして、下のものほど「やった感」があるので、 つい先にやりたくなります。

SIMD を書く前に、カリングが入っているか確認してください。

06レポートの形

# 最適化レポート

## 測定環境
CPU : Intel Core i7-12700 (12コア/20スレッド)
RAM : 32GB
GPU : NVIDIA RTX 3060
OS  : Windows 11
ビルド : Release x64

## 測定条件
敵 300体、弾 2000発（srand(12345) で固定配置）
60フレームの平均値。3回測って中央値を採用。

## 結果

| 段階 | 施策 | Frame(ms) | 改善 |
|------|------|-----------|------|
| 0 | 初期状態 | 34.2 | — |
| 1 | 画面外の敵を描画しない | 21.8 | -12.4 |
| 2 | FindGO をループの外へ | 18.1 | -3.7 |
| 3 | 弾をオブジェクトプールに | 16.4 | -1.7 |
| 4 | 当たり判定をグリッド分割 | 11.2 | -5.2 |
| 5 | 弾の位置・速度を SoA に | 10.1 | -1.1 |
| 6 | 星の描画をインスタンシングに | 8.4 | -1.7 |

**34.2ms → 8.4ms（4.1倍）**

## 各施策の詳細

### 1. 画面外の敵を描画しない（-12.4ms）
Draw Call が 1,842 → 605 に減少。
カメラ前方の内積判定と距離判定の2行を Render() に追加しただけ。
**いちばん効果が大きく、いちばん手間が少なかった。**

### 4. 当たり判定をグリッド分割（-5.2ms）
仮説：弾2000 × 敵300 = 60万回の総当たりが原因。
K2_PROFILE_SCOPE で Collision が 8.9ms を占めていることを確認。
画面を 100x100 のセルに分け、同じセルと隣接セルだけ判定するように変更。
60万回 → 約1.1万回。

## 効果がなかったもの

### 敵の SoA 化（効果 0.03ms）
仮説：敵の更新がキャッシュミスしている。
結果：ほぼ変化なし。
理由：敵は300体 × 約400バイト = 120KB で、L2キャッシュに収まっていた。
5-06 の「数千個以上でないと効かない」という条件を満たしていなかった。
**この変更は revert した。**

### SIMD による当たり判定（効果 0.04ms）
グリッド分割で1.1万回まで減っていたため、
SIMD 化しても絶対時間が小さく、効果が出なかった。
コードが読みにくくなるだけなので採用しなかった。

## 残った課題
- Frame 8.4ms のうち、5.1ms が GPU（ポストエフェクト）
  → ウィンドウを小さくすると 4.2ms になることを確認済み
- ボス出現時に 42ms のスパイクが残っている
  → モデルの先読みで解決できるはずだが、未実装

## 学んだこと
測る前に「当たり判定が重いはずだ」と思い込んでいたが、
実際にいちばん重かったのは描画だった。
5-01 の「推測するな、測れ」を身をもって理解した。

1. カリング

void Enemy::Render(RenderContext& rc)
{
    Vector3 toMe = m_position - g_camera3D->GetPosition();
    if (toMe.Dot(g_camera3D->GetForward()) < -m_radius) { return; }
    if (toMe.LengthSq() > DRAW_DIST * DRAW_DIST)        { return; }
    m_modelRender.Draw(rc);
}

2. FindGO を外に

// 探して置き換える
// Ctrl+Shift+F で "FindGO" を検索し、for の中にあるものを探す

// Enemy.h にハンドルを持たせる
GOHandle<Player> m_player;

// Update の先頭で1回だけ
Player* p = m_player.Get();
if (p == nullptr) {
    p = FindGO<Player>("player");
    if (p) { m_player = GOHandle<Player>(p); }

コミットハッシュを書いておいてください 「この変更で本当に速くなったのか」を、 あとから確かめ直せます。

効果がなかった変更を revert するときにも使えます。
遊べなくなっていないか、毎回確認してください 速くなっても、ゲームが壊れていたら意味がありません。

4-14 のテストパネルがあれば、 変更のたびに1クリックで確認できます。

特にカリングは「見えるべきものが消える」という 壊れ方をします。必ず目で確認してください。

演習3（まとめる）

最適化レポートを書く。「効果がなかったもの」の節を、必ず入れること。

解答例を見る（まず自分でやってから）

レポートに必ず入れるもの

項目なぜ必要か
測定環境 他のPCでは違う結果になる。数字に意味を持たせるため
測定条件 再現できないと、検証できない
施策ごとの数字どれがどれだけ効いたか
仮説と結果 「なぜそうしたか」が無いと、ただの作業記録
効果がなかったもの これがいちばん価値がある
残った課題客観的に見られていることを示す

なぜ「効果がなかったもの」が重要なのか

  • 測っていないと書けない（＝測ったことの証明になる）
  • 「知っている技術を、闇雲に適用していない」ことが伝わる
  • 条件が合わないと効かない、という理解を示せる
  • revert したという判断力が伝わる
面接で、これがいちばん効きます 「SIMD を使いました」より、 「SIMD も試しましたが、グリッド分割で判定回数が十分減っていたので、 効果が 0.04ms しかなく、読みにくくなるだけなので採用しませんでした」 のほうが、圧倒的に評価されます。

前者は知識、後者は判断力です。

08この教材を終えて

同じゲームを、4回作りました。

作った目的判断基準
LV2 動かす遊べるか
LV3 見せる見栄えがするか
LV4 壊れにくくする変更しやすいか
LV5 速くする速いか

そして、LV4 と LV5 の判断基準は、しばしば対立しました。 カプセル化とSoA。読みやすさと速さ。

どちらかが正しいのではありません 「いま、どちらが必要か」を測って決められること。
それが、この教材で最後に身につけてほしいものです。

最初は「かゆいところに手が届かない」でした。
いまは、手が届くうえに、 「どこに手を伸ばすべきか」を自分で決められます。

ここから先は、教材の外です。 自分の作りたいものを作ってください。
