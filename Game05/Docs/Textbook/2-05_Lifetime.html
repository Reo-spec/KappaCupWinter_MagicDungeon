DeleteGO とオブジェクトの寿命

難易度 ／ 前提 2-03

00入場チェック

この章に入る前に、次の質問に答えられますか。

  • NewGO<Player>(3, "player") は何をしている？ → 答えられないなら 2-03 へ戻る
  • new したメモリは、誰が delete する責任を持つ？ → 答えられないなら 1-15 へ戻る

分からないまま進まないでください。ここを飛ばすと必ずあとで詰まります。

01この章でできるようになること

  • ゲームオブジェクトがいつ生まれて、いつ消えるのかを説明できる
  • DeleteGO() が「その場で消す関数」ではないことを説明できる
  • 「誰が DeleteGO する責任を持つのか」を決めてからコードを書ける

02なぜこれが必要なのか

弾を撃つゲームを作ると、弾は1秒に何十個も生まれて、画面の外に出たら消えます。 この「消す」をきちんと理解していないと、次の2つが必ず起きます。

  • 消し忘れ — 弾がどんどん溜まって、だんだん重くなる
  • 消したものを触る — ある日とつぜんクラッシュする

2つめのほうが、はるかにやっかいです。 なぜなら 「消したはずなのに、しばらく動いてしまう」 からです。 その理由を、この章で見ていきます。

03生まれるとき ― NewGO

NewGO の中身は、エンジンの k2EngineLow/gameObject/GameObjectManager.h にあります。 難しいことはしていません。 

template<class T>
T* NewGameObject(int prio, const char* objectName)
{
    T* newObject = new T();                           // ← ここで new
    newObject->SetName(objectName);
    m_nextInstanceId++;
    newObject->m_instanceId = m_nextInstanceId;       // ← 番号を振る
    m_instanceIdMap.insert({ m_nextInstanceId, newObject });
    m_gameObjectListArray.at(prio).push_back(newObject);  // ← 優先度のリストに登録
    return newObject;
}

new して、名前と番号をつけて、優先度ごとのリストに並べているだけです。 この「番号（インスタンスID）」が、あとで効いてきます。 いま覚えておいてください。

04消えるとき ― DeleteGO は何をしているか

では DeleteGO はどうでしょうか。

void DeleteGameObject(IGameObject* gameObject)
{
    if (gameObject != nullptr)
    {
        gameObject->Dead();     // ← これだけ
    }
}

そして Dead() の中身は、

void Dead()
{
    m_isDead = true;            // ← フラグを立てるだけ
}
DeleteGO は delete していない DeleteGO() がやっているのは 「このオブジェクトはもう要らない」という予約（死亡フラグ）を立てることだけです。 メモリはまだそこにあります。

では、本当に delete されるのはいつでしょうか。 GameObjectManager::ExecuteUpdate() のいちばん先頭です。 

void GameObjectManager::ExecuteUpdate()
{
    // 死亡フラグがついているゲームオブジェクトを破棄する。
    for (auto& goList : m_gameObjectListArray) {
        goList.remove_if([&](IGameObject* go) {
            if (go->IsDead()) {
                m_instanceIdMap.erase(go->GetInstanceID());
                delete go;                    // ← 本当に消えるのはここ
                return true;
            }
            return false;
        });
    }

    // このあとで Start() と Update() が呼ばれる
    ...
}

051フレームの中で、何がどの順に起きるか

なぜ Update と Render が呼ばれなくなるのかは、 IGameObject を読めば分かります。 

void UpdateWrapper()
{
    if (m_isActive && m_isStart && !m_isDead) {   // ← ここで弾かれる
        Update();
    }
}

06確かめてみる

本当にそうなっているか、自分の目で確認します。 自分のゲームオブジェクトに、次のコードを入れてください。 

void Enemy::Update()
{
    m_frame++;
    // 出力ウィンドウに出す。
    char text[256];
    sprintf_s(text, "Enemy::Update  frame=%d\n", m_frame);
    OutputDebugStringA(text);

    if (m_frame == 60) {
        OutputDebugStringA("--- DeleteGO を呼ぶ ---\n");
        DeleteGO(this);
        // ここで return しないと、この下の処理が続いてしまう
        return;
    }
}

Enemy::~Enemy()
{
    OutputDebugStringA("--- Enemy のデストラクタ ---\n");
}

Visual Studio の出力ウィンドウ（Ctrl+Alt+O） を見ながら実行してください。こう出るはずです。 

Enemy::Update  frame=59
Enemy::Update  frame=60
--- DeleteGO を呼ぶ ---
--- Enemy のデストラクタ ---     ← 次のフレームの先頭
  • DeleteGO を呼んだあと、Update がもう呼ばれていない
  • デストラクタは DeleteGO の直後ではなく、少し遅れて呼ばれている
DeleteGO(this) の直後は必ず return DeleteGO(this) を呼んでも、その関数はそこで終わりません。 下に処理が続いていれば、そのまま実行されます。 「自分を消したら、すぐ帰る」を習慣にしてください。

07誰が DeleteGO するのか ― 所有のルール

消し忘れも、二重消しも、原因は同じです。 「誰が消す係なのか」を決めていないこと。

ルール意味
1. 自分で自分を消す 弾や敵は、画面外に出たとき・やられたときに DeleteGO(this) する。一番かんたんで、間違いが少ない
2. 作った人が消す NewGO した側が DeleteGO する責任を持つ。シーンが自分の中のオブジェクトを片づけるときなど
3. 消す係はひとりだけ 「敵も自分を消す、シーンも敵を消す」はダメ。どちらか片方に決める

シーンが終わるときに、自分が出したオブジェクトを全部片づける例です。 

class GameScene : public IGameObject {
    std::vector<Enemy*> m_enemies;   // 自分が NewGO した敵
};

GameScene::~GameScene()
{
    // 自分が作ったものは、自分で片づける。
    for (auto enemy : m_enemies) {
        DeleteGO(enemy);
    }
    m_enemies.clear();
}

この書き方をするなら、Enemy 側は自分で DeleteGO(this) してはいけません。 両方が消そうとすると、m_enemies の中に死んだポインタが残ります。 それがまさに次の章以降で扱う事故です。

08よくあるエラー

弾を撃つとだんだん重くなる

原因：弾が画面外に出ても DeleteGO していない。 見えないだけで、ずっと Update され続けています。
直し方：画面外に出たら DeleteGO(this); return; する。 本当に消えているかは、次の章の GameObject List パネルで確認できます。

デストラクタが呼ばれない

原因：DeleteGO を呼んでいないか、 delete を直接呼んでいる。
直し方：NewGO で作ったものは、必ず DeleteGO で消します。 delete を直接書いてはいけません。 マネージャのリストにポインタが残ったままになります。

同じオブジェクトを2回 DeleteGO してしまう

原因：消す係が2人いる。
直し方：上の「所有のルール」を決める。 なお DeleteGO はフラグを立てるだけなので、 同じフレームのうちなら2回呼んでも落ちません。 ですが、これは運がいいだけです。 次のフレームまたぎで2回呼ぶと、解放済みメモリに書き込むことになります。

09演習

演習1（まねる）

上の「確かめてみる」のコードを自分のプロジェクトで動かし、 出力ウィンドウでデストラクタが1フレーム遅れて呼ばれることを確認する。

演習2（数字を変える）

DeleteGO(this); のうしろの return; を消すと何が起きるか、 予想してから試す。Update の残りの処理は実行されるか？

解答例を見る（まず自分でやってから） 
void Enemy::Update()
{
    if (m_frame == 60) {
        DeleteGO(this);
        // return; を消してみる
    }
    m_frame++;
    m_position.x += 1.0f;      // ← これは実行されてしまう
    OutputDebugStringA("この行も実行される\n");
}

Update() の残りは、全部そのまま実行されます。 DeleteGO は「予約」をするだけで、関数を終わらせる力はありません。

このフレームでは、メンバ変数はまだ生きているので落ちません。 だから気づきにくいのです。 たとえば「死んだのにスコアがもう一度入る」「死んだのに弾を撃つ」 といった形でバグになります。

DeleteGO(this); と return; は必ずセットで書いてください。

演習3（自分で書く）

画面の外に出たら自分を消す弾クラスを作る。 本文には答えがありません。 GameObject List パネル（次の章）で、弾がちゃんと消えているか確認できるようにしておくこと。

解答例を見る（まず自分でやってから） 
// Bullet.cpp
void Bullet::Update()
{
    const float dt = g_gameTime->GetFrameDeltaTime();
    m_position.y += 1200.0f * dt;

    // 画面の外に出たら消える。
    // 画面の上端は 540。少し余裕をもたせて 600 で判定する。
    if (m_position.y > 600.0f) {
        DeleteGO(this);
        return;
    }

    m_spriteRender.SetPosition(m_position);
    m_spriteRender.Update();
}

上下左右すべて見るなら、こう書きます。 

if (m_position.y >  600.0f || m_position.y < -600.0f
 || m_position.x > 1020.0f || m_position.x < -1020.0f) {
    DeleteGO(this);
    return;
}

判定の値を画面ぴったり（540 や 960）にすると、 画面の端で消える瞬間が見えてしまいます。 少し外側で消すのがコツです。

10確認

次の質問に、声に出して説明できますか。

  1. DeleteGO() を呼んだ瞬間、そのオブジェクトのメモリはどうなっている？
  2. 本当に delete されるのは、いつ・どこ？
  3. DeleteGO したのに画面から消えるのはなぜ？
  4. DeleteGO(this) のあとに return; を書くのはなぜ？
答え
  1. まだ残っている。死亡フラグ（m_isDead）が立つだけ。
  2. 次のフレームの GameObjectManager::ExecuteUpdate() のいちばん先頭。
  3. UpdateWrapper() と RenderWrapper() が m_isDead を見て、呼び出しをスキップするから。
  4. DeleteGO は関数を終わらせないので、書かないと下の処理が続いてしまうから。
