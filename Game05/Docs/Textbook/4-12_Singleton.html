Singletonの何が悪いのか

難易度 ／ 前提 4-04

01この章でできるようになること

  • Singleton が嫌われる理由を、具体的に説明できる
  • それでも使ってよい場面が分かる
  • 代わりの手段を持っている
k2Engine も Singleton を使っています GameObjectManager、PhysicsWorld、 GraphicsEngine。全部そうです。
「使うな」という話ではありません。 何を引き換えにしているかを知る章です。

02Singleton とは

class SoundManager {
public:
    static SoundManager* GetInstance()
    {
        static SoundManager instance;
        return &instance;
    }
    void Play(const char* name);

private:
    SoundManager() {}
};

// どこからでも呼べる
SoundManager::GetInstance()->Play("shot");

「1つしか存在しない」「どこからでも触れる」の2つを 同時に満たすものです。

便利です。だから困ります。

03問題1 ― 依存が見えない

class Player : public IGameObject {
public:
    void Damage(int amount);
    // ★ .h を見ても、何に依存しているか分からない
};
// .cpp を開いて、はじめて分かる
void Player::Damage(int amount)
{
    m_hp -= amount;
    SoundManager::GetInstance()->Play("damage");
    EffectManager::GetInstance()->Spawn("hit", m_position);
    SaveData::GetInstance()->AddDamageCount();
    Statistics::GetInstance()->Report("player_damaged");
}

Player は4つのクラスに依存しています。 でも .h にはその手がかりがありません。

4-08 の FindGO だらけの話と、根は同じです。 ただし Singleton のほうが見つけにくいです。 引数にも、メンバにも、何も現れないからです。

04問題2 ― テストできない

// Player だけをテストしたい
TEST(PlayerTest, DamageReducesHp)
{
    Player player;
    player.Damage(10);
    EXPECT_EQ(player.GetHp(), 90);
}

これは動きません。 Damage() の中で SoundManager が呼ばれ、 その中で DirectX の音声デバイスを触るからです。

HPの計算を確かめたいだけなのに、 サウンドデバイスの初期化が必要になります。

これが 4-14 の話につながります 「テストしやすい設計」とは、 一部分だけを切り出して動かせる設計のことです。
Singleton は、その切り出しを妨げます。

05問題3 ― 初期化と破棄の順番

static SoundManager instance;     // ★ いつ作られ、いつ壊れるか

関数内 static は最初に呼ばれたときに作られ、 プログラム終了時に壊れます。

問題は「壊れる順番が決まっていない」ことです。 

SoundManager::~SoundManager()
{
    // ★ ここで LogManager を使っていたら？
    LogManager::GetInstance()->Write("SoundManager 終了");
}

LogManager が先に壊れていたら、 解放済みのオブジェクトを使うことになります。

「終了時にだけ落ちる」の、よくある原因です ゲームは正常に動くのに、閉じるときだけクラッシュする。 Singleton の破棄順を疑ってください。
k2Engine が CreateInstance() / DeleteInstance() を 明示的に呼ぶ形にしているのは、この順番を自分で決めるためです。

k2EngineLow/gameObject/GameObjectManager.h を見てください。 static 変数ではなく、 CreateInstance() を明示的に呼ぶ形になっています。 これは、上の問題を避けるための設計です。

06それでも使ってよい場面

条件例
本当に1つしかありえない GPU、ウィンドウ、オーディオデバイス
状態を持たない、または読み取り専用 設定の読み込み、定数テーブル
エンジンの最下層 GraphicsEngine、PhysicsWorld
テストする予定がない デバッグ用のログ

逆に、こういうものは Singleton にしないでください。

  • ScoreManager — 2人プレイになったら?
  • GameManager — 何をするクラスなのか分からない
  • Player — 2Pが出せなくなる
  • ゲームのルールに関わるもの全般
「1つしかない」と「1つしか作らない」は違います いまは1人プレイでも、将来2人になる可能性があるなら、 それは「1つしかありえない」ものではありません。
GPUは本当に1つです。スコアはそうではありません。

07代わりの手段

やり方書き方向いている場面
引数で渡す Player(SoundManager& sound) いちばん素直。まずこれを検討
Observer 4-08 複数が反応するとき
FindGO FindGO<Sound>("sound") k2Engine 流。Singleton よりはまし
Service Locator 後述 差し替えたいとき

FindGO が Singleton より良い点

  • nullptr が返るので、いない場合を扱える
  • 名前で複数持てる（"player1" / "player2"）
  • 寿命がはっきりしている

k2Engine で書くなら、Singleton を自作する理由はほとんどありません。 IGameObject にして FindGO で足ります。 

// Service Locator ― 差し替えたいとき
class Services {
public:
    static void Provide(ISound* sound) { s_sound = sound; }
    static ISound& Sound() { return *s_sound; }
private:
    static ISound* s_sound;
};

// テストのときは、何もしない実装に差し替えられる
Services::Provide(&g_nullSound);
Service Locator も、依存が見えないのは同じです 差し替えられるようになっただけです。 「どこからでも触れる」問題は解決していません。
テストのためだけに導入するなら、引数で渡すほうが素直です。

08演習

演習1（数える）

自分のコードの GetInstance() と FindGO を数える。どのクラスがいちばん依存されているか。

演習2（書き直す）

Singleton にしていたクラスを1つ選び、IGameObject にして FindGO で取る形に書き直す。

解答例を見る（まず自分でやってから）

書き直す前

class ScoreManager {
public:
    static ScoreManager* GetInstance()
    {
        static ScoreManager instance;
        return &instance;
    }
    void AddScore(int s) { m_score += s; }
    int  GetScore() const { return m_score; }
private:
    ScoreManager() {}
    int m_score = 0;
};

// 使うとき
ScoreManager::GetInstance()->AddScore(100);

書き直したあと

class ScoreManager : public IGameObject {
public:
    bool Start()  override;
    void Update() override;
    void Render(RenderContext& rc) override;

    void AddScore(int s) { m_score += s; }
    int  GetScore() const { return m_score; }
    void Reset() { m_score = 0; }        // ★ これが書けるようになる

private:
    int m_score = 0;
    FontRender m_fontRender;
};

// 作る
NewGO<ScoreManager>(enPriority_UI, "score");

// 使う
ScoreManager* score = FindGO<ScoreManager>("score");
if (score != nullptr) {
    score->AddScore(100);
}

何が良くなったか

SingletonIGameObject + FindGO
寿命プログラム終了まで残る シーンと一緒に消える
リトライ時Reset() を呼び忘れると点が残る 作り直せば自動的に 0
2人プレイできない "score1"／"score2" で可能
描画自前で呼び出しを書く Render() が自動で呼ばれる
nullptr チェック要らない要る
「リトライしたらスコアが引き継がれる」バグが消えます Singleton はシーンをまたいで生き残ります。 リトライのたびに Reset() を呼ぶ必要があり、 どこかで忘れます。

IGameObject なら、シーンを作り直せば 新品の ScoreManager ができます。 忘れようがありません。

nullptr チェックが面倒なとき

// 呼び出し側を短く書くヘルパを用意する
void AddScore(int s)
{
    if (ScoreManager* m = FindGO<ScoreManager>("score")) {
        m->AddScore(s);
    }
}

これなら AddScore(100); の1行で済み、 しかも安全です。

演習3（説明する）

「Singletonの何が悪いんですか」と聞かれたときの答えを、3つの問題に触れながら90秒ぶん書く。面接で聞かれます。

解答例を見る（まず自分でやってから）

答え方の骨組み

1. 何が便利か、まず認める（15秒）
2. 具体的な問題を3つ（45秒）
3. 自分はどう判断しているか（30秒）

例

Singleton は「どこからでも触れて、1つしかない」ので、 書くのはとても楽です。実際、私も最初はスコア管理を Singleton にしていました。

ただ、3つ困ったことがありました。

1つめは依存が見えないことです。 Player.h を見ても何に依存しているか分からず、 .cpp を開くと4つの Singleton を呼んでいました。 影響範囲が読めなくなります。

2つめはテストできないことです。 HPの計算を確かめたいだけなのに、 中でサウンドマネージャを呼んでいるので、 音声デバイスの初期化が必要になってしまいました。

3つめは寿命です。 Singleton はシーンをまたいで残るので、 リトライしたときにスコアが引き継がれるバグを出しました。 リセットを呼び忘れていたんです。

いまは、GPUやウィンドウのように本当に1つしかないものだけ Singleton にしています。 ゲームのルールに関わるものは、 エンジンのゲームオブジェクトにして名前で取る形にしました。 シーンと一緒に作り直されるので、さっきのバグは起きなくなりました。

この答えが強い理由
  • 自分が実際に踏んだバグの話が入っている
  • 「悪い」と決めつけず、使ってよい条件も言っている
  • 代わりに何をしたかまで話している

「Singleton はアンチパターンなのでダメです」だけだと、 本で読んだ知識に聞こえます。
面接で気をつけること 「k2Engine も Singleton を使っています」と 付け加えられると、なお良いです。

「使っているものを否定せず、なぜそこでは妥当なのかを説明できる」 というのは、実務でいちばん求められる態度です。

09確認

  1. Singleton の3つの問題は？
  2. 「終了時にだけ落ちる」の原因として疑うのは？
  3. FindGO が Singleton より良い点を2つ。
  4. ScoreManager を Singleton にすると、どんなバグが出やすい？
答え
  1. 依存が見えない／テストできない／初期化と破棄の順番が決まらない。
  2. Singleton の破棄順。片方が先に壊れたあとに、 もう片方のデストラクタから使われている。
  3. nullptr が返るのでいない場合を扱える。 名前で複数持てる。寿命がはっきりしている。
  4. リトライしてもスコアが引き継がれる（リセット忘れ）。
