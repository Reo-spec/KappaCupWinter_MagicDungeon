ECSを自作して比較する

難易度 ／ 前提 5-06 , 4-07

01この章でできるようになること

  • ECS が何を解決するものか説明できる
  • 継承ベースとの違いを、数字で言える
  • 自分のゲームに必要かどうか、判断できる
先に結論を書いておきます 学生作品に ECS は、たいてい要りません。
この章は「なぜ現代のエンジンが ECS に向かったか」を 体で理解するための章です。

02ECS とは

頭文字名前正体
EEntity ただの ID（整数）。データも処理も持たない
CComponent データだけ。関数を持たない
SSystem 処理だけ。データを持たない

4-07 のコンポーネントと似ていますが、 決定的に違うのは「コンポーネントが関数を持たない」ことです。 

// 4-07 のコンポーネント（データ＋処理）
class HealthComponent {
public:
    void Update(float dt);      // ★ 処理を持つ
    bool Damage(int amount);
private:
    int m_hp;
};

// ECS のコンポーネント（データだけ）
struct Health {
    int hp;
    int maxHp;
    float invincibleTimer;
};                              // ★ 関数なし。struct でよい
// 処理は System 側にまとめる
void HealthSystem(World& w, float dt)
{
    // ★ Health を持つ全エンティティを、まとめて処理する
    for (auto& h : w.healths) {
        if (h.invincibleTimer > 0.0f) {
            h.invincibleTimer -= dt;
        }
    }
}

03なぜ速いのか

5-06 の SoA を、 設計レベルまで徹底したものだからです。

継承ベースECS
データの配置 オブジェクトごとにバラバラ 種類ごとに連続
処理の呼び方 1個ずつ仮想関数 System が配列を一気になめる
不要なデータ オブジェクト全体が運ばれる 必要な配列だけ
並列化難しい System 単位で分けやすい
読みやすさ直感的 慣れが要る
デバッグやさしい 「この Entity は何者か」が見えにくい

04最小の ECS を作る

本格的な ECS は複雑ですが、 「考え方だけ」なら100行で書けます。 

// MiniEcs.h
#pragma once
#include <vector>

using Entity = int;

/// <summary>コンポーネント（データだけ）</summary>
struct Transform { Vector3 position; Vector3 velocity; };
struct Health    { int hp; int maxHp; };
struct Renderable{ int modelId; };

/// <summary>
/// 世界。コンポーネントごとに配列を持つ。
/// </summary>
/// <remarks>
/// 本物の ECS は「どのエンティティがどのコンポーネントを持つか」を
/// もっと賢く管理するが、ここでは有無のフラグだけで表す。
/// </remarks>
class World {
public:
    Entity Create()
    {
        Entity e = (Entity)m_alive.size();
        m_alive.push_back(true);
        m_transforms.push_back({});
        m_healths.push_back({});
        m_hasTransform.push_back(false);
        m_hasHealth.push_back(false);
        return e;
    }

    void AddTransform(Entity e, const Transform& t)
    {
        m_transforms[e]   = t;
        m_hasTransform[e] = true;
    }
    void AddHealth(Entity e, const Health& h)
    {
        m_healths[e]   = h;
        m_hasHealth[e] = true;
    }

    // System から使う
    size_t Size() const { return m_alive.size(); }

    std::vector<Transform>& Transforms()    { return m_transforms; }
    std::vector<Health>&    Healths()       { return m_healths; }
    const std::vector<char>& HasTransform() const { return m_hasTransform; }
    const std::vector<char>& HasHealth()    const { return m_hasHealth; }

private:
    std::vector<char>      m_alive;
    std::vector<Transform> m_transforms;
    std::vector<Health>    m_healths;
    std::vector<char>      m_hasTransform;
    std::vector<char>      m_hasHealth;
};
// System（処理だけ）
void MoveSystem(World& w, float dt)
{
    auto& ts = w.Transforms();
    const auto& has = w.HasTransform();

    // ★ 配列を、頭から一気になめる
    for (size_t i = 0; i < ts.size(); i++) {
        if (!has[i]) { continue; }
        ts[i].position += ts[i].velocity * dt;
    }
}

void HealthSystem(World& w)
{
    auto& hs = w.Healths();
    const auto& has = w.HasHealth();

    for (size_t i = 0; i < hs.size(); i++) {
        if (!has[i]) { continue; }
        if (hs[i].hp > hs[i].maxHp) { hs[i].hp = hs[i].maxHp; }
    }
}
これは「ECS もどき」です 本物の ECS は、 コンポーネントの組み合わせが同じエンティティを、 ひとかたまりにまとめて保存します（アーキタイプ）。
そうすると if (!has[i]) continue; すら不要になり、 さらに速くなります。

ただし、実装は一気に複雑になります。 ここでは考え方が分かれば充分です。

05継承ベースとの比較

// 継承ベース（k2Engine の形）
for (auto& goList : m_gameObjectListArray) {   // ★ list を辿る
    for (auto& go : goList) {                  // ★ ポインタを辿る
        go->UpdateWrapper();                   // ★ 仮想関数
    }
}

// ECS
MoveSystem(world, dt);        // ★ 配列を1本なめるだけ
HealthSystem(world);          // ★ 別の配列を1本
ShotSystem(world, dt);
10万体を更新時間の目安
std::list<IGameObject*> ＋ 仮想関数 20〜40 ms
std::vector<Obj*> ＋ 仮想関数 8〜15 ms
std::vector<Obj>（値で持つ） 2〜4 ms
ECS（SoA） 0.5〜1.5 ms
10万体のときの話です 1000体なら、どれも 0.1ms 以下です。差は測れません。
ECS が意味を持つのは、「万」の桁からです。

06ECS の代償

失うもの具体的に
デバッグのしやすさ 「Entity 4271」を見ても、何者か分からない
コードの直感性 player->Damage(10) と書けない
1個だけの特別扱い ボスのような「1体だけ特殊」が書きにくい
学習コストチーム全員が理解する必要がある
実装量 まともな ECS は、それだけで数千行
現実的な折衷案 大量のものだけ ECS 風（SoA）にして、 残りは IGameObject のまま。
これが 5-06 の BulletSystem でやったことです。

実質、それで充分なことがほとんどです。

07それでも ECS を知る意味

理由説明
面接で聞かれる Unity DOTS、Unreal の Mass など、話題にのぼる
考え方が応用できる 「データ指向」の発想は、ECS でなくても使える
並列化しやすい 5-12 で効いてくる
大量のものを扱う設計が身につく 弾幕、群衆、パーティクル
「データ指向」とは 「オブジェクトはどうあるべきか」ではなく、 「データがどう並んでいると速いか」から設計する考え方です。

ECS は、その考え方をいちばん徹底した形のひとつにすぎません。
ECS を使わなくても、この発想は使えます。

08演習

演習1（作る）

上の最小 ECS を実際に書いて動かす。エンティティを10万作って、MoveSystem を回す。

演習2（比べる）

同じ処理を、継承ベースと ECS で書いて、時間を比べる。1000体・1万体・10万体で測る。

解答例を見る（まず自分でやってから） 
#include "Bench.h"

//================= 継承ベース =================
class ObjBase {
public:
    virtual ~ObjBase() {}
    virtual void Update(float dt) = 0;
    Vector3 m_position = Vector3::Zero;
    Vector3 m_velocity = { 1.0f, 2.0f, 3.0f };
    int     m_hp = 100;
    int     m_maxHp = 100;
    char    m_pad[64] = {};        // 実際のゲームオブジェクトに近い大きさ
};

class ObjMover : public ObjBase {
public:
    void Update(float dt) override
    {
        m_position += m_velocity * dt;
    }
};

//================= ECS =================
struct EcsWorld {
    std::vector<Vector3> positions;
    std::vector<Vector3> velocities;
    std::vector<int>     hps;
};

void EcsMoveSystem(EcsWorld& w, float dt)
{
    const size_t n = w.positions.size();
    for (size_t i = 0; i < n; i++) {
        w.positions[i] += w.velocities[i] * dt;
    }
}

//================= 比較 =================
void CompareEcs(int N)
{
    const float dt = 1.0f / 60.0f;
    const int LOOP = 100;

    char head[64];
    sprintf_s(head, "---- N = %d ----\n", N);
    OutputDebugStringA(head);

    //--- 継承 + ポインタの vector ---
    std::vector<ObjBase*> objs;
    objs.reserve(N);
    for (int i = 0; i < N; i++) { objs.push_back(new ObjMover()); }

    {
        BENCH("  継承 + vector<T*>");
        for (int k = 0; k < LOOP; k++) {
            for (ObjBase* o : objs) { o->Update(dt); }
        }
    }

    //--- 継承 + list（k2Engine の形）---
    std::list<ObjBase*> objList(objs.begin(), objs.end());
    {
        BENCH("  継承 + list<T*>");
        for (int k = 0; k < LOOP; k++) {
            for (ObjBase* o : objList) { o->Update(dt); }
        }
    }

    //--- ECS ---
    EcsWorld w;
    w.positions.resize(N, Vector3::Zero);
    w.velocities.resize(N, { 1.0f, 2.0f, 3.0f });
    w.hps.resize(N, 100);

    {
        BENCH("  ECS (SoA)");
        for (int k = 0; k < LOOP; k++) {
            EcsMoveSystem(w, dt);
        }
    }

    // 消されないように
    char buf[128];
    sprintf_s(buf, "  check %f / %f\n\n",
              objs[0]->m_position.x, w.positions[0].x);
    OutputDebugStringA(buf);

    for (ObjBase* o : objs) { delete o; }
}

void RunAll()
{
    CompareEcs(1000);
    CompareEcs(10000);
    CompareEcs(100000);
}

典型的な結果（Release、100回ループ）

---- N = 1000 ----
  継承 + vector<T*>          :    0.412 ms
  継承 + list<T*>            :    0.688 ms
  ECS (SoA)                  :    0.094 ms      （4.4倍）

---- N = 10000 ----
  継承 + vector<T*>          :    5.930 ms
  継承 + list<T*>            :   12.104 ms
  ECS (SoA)                  :    0.921 ms      （6.4倍）

---- N = 100000 ----
  継承 + vector<T*>          :  118.442 ms
  継承 + list<T*>            :  312.775 ms
  ECS (SoA)                  :    9.238 ms      （12.8倍）
数が増えるほど、差が開きます 1000体では 4倍、10万体では 13倍。

データがキャッシュに収まっているうちは差が小さく、 あふれると一気に開く―― 5-05 の実験3で見た階段と同じ現象です。
1フレームあたりに直してください 上は100回ループの合計です。1フレームあたりは100分の1。 

N = 1000  のとき
  継承 : 0.0041 ms   ECS : 0.0009 ms   → 差は 0.003 ms
N = 100000 のとき
  継承 : 1.18 ms     ECS : 0.09 ms     → 差は 1.1 ms
1000体なら、16.6ms の予算からすれば誤差です。 だから「学生作品に ECS は要らない」と言えるのです。

演習3（判断する）

自分のゲームに ECS が必要か、数字を根拠に判断する。必要でないなら、「なぜ必要でないか」を書く。

解答例を見る（まず自分でやってから）

判断の手順

  1. 自分のゲームで、いちばん数が多いものは何個か
  2. それを更新するのに、いま何ミリ秒かかっているか（5-02）
  3. それが 16.6ms の何%か
  4. ECS にして10倍速くなったとして、何ms浮くか
  5. その ms のために、設計を全部書き換える価値があるか

記録の例

== ECS 導入の検討 ==

【現状】
いちばん数が多いもの : 敵弾（最大 800発）
その更新時間         : 0.31 ms（Profiler、Release）
フレーム全体         : 11.2 ms
割合                 : 2.8%

【ECS にした場合の見積もり】
10倍速くなったとして 0.031 ms → 0.28 ms 浮く
フレーム全体は 11.2 → 10.9 ms（2.7%改善）
FPS は 60 のまま（そもそも上限に張り付いている）

【判断】
導入しない。

【理由】
1. 現状 60FPS 出ており、改善の余地が体感に結びつかない
2. 弾の更新は全体の 2.8% で、ボトルネックではない
   （いちばん重いのは描画の 5.9ms）
3. 既存の IGameObject 設計を全部書き換えるコストが見合わない
4. デバッグしやすさを失うデメリットのほうが大きい

【代わりにやったこと】
5-06 の SoA を、弾にだけ部分適用した。
位置と速度だけ別配列にして、0.31ms → 0.14ms になった。
IGameObject の枠組みは残したままなので、デバッグしやすさは保てている。

【将来 ECS を検討する条件】
弾が 5000発を超える弾幕シューを作るなら、そのとき検討する。
この「導入しない」という判断が、この章のゴールです ECS を実装できることより、 「測って、割に合わないと判断した」ほうが価値があります。

面接でも、この記録をそのまま話せます。 「知っているが、自分のゲームには要らないと判断した」というのは、 知識と判断力の両方を示せる、いちばん強い答え方です。
逆に、必要だと判断したなら いきなり全部を ECS にしないでください。

4-13 の ストラングラーパターンで、 いちばん数が多いものから1つずつ移してください。

そして、移すたびに測ってください。 思ったほど速くならないことも、よくあります。

09確認

  1. ECS の Component が、4-07 のコンポーネントと違う点は？
  2. ECS が速い理由は？
  3. ECS で失うものを2つ。
  4. ECS が意味を持つのは、だいたい何個くらいから？
答え
  1. 関数を持たない。データだけ。処理は System 側にある。
  2. 同じ種類のデータが連続して並び（SoA）、 仮想関数もポインタ追跡もないから。
  3. デバッグのしやすさ、コードの直感性、 1個だけの特別扱いのしやすさ。
  4. 1万個以上。千個程度では差が測れない。
