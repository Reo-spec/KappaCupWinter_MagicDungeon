new/delete のコストとアロケータ自作

難易度 ／ 前提 1-15 , 5-04

01この章でできるようになること

  • new が何をしているか説明できる
  • プールアロケータを自作して、比較できる
  • メモリの断片化がなぜ問題か分かる

02new は何をしているのか

1-15 では 「メモリを借りる」と説明しました。 その中身を見ます。

やっていることコスト
1. 必要なサイズが入る空き領域を探す 探索。断片化していると遅い
2. 管理情報を書き込む（サイズなど） 数バイト〜数十バイトの上乗せ
3. 使用中の印を付ける小
4. スレッド間で取り合わないようロックする これが地味に重い
5. 足りなければ、OSに追加を要求する システムコール。非常に重い

1回あたり、だいたい 50〜200 ナノ秒です。 1フレームに1万回呼べば、0.5〜2ms。無視できません。

それに、置かれる場所がバラバラです 5-06 で見たとおり、 バラバラに確保したオブジェクトをなめるのは、非常に遅い。
new のコストより、こちらのほうが効くことも多いです。

03断片化

確保：  [A][B][C][D][E]
解放：  [A][ ][C][ ][E]      ← B と D を解放
確保：  大きいものを置きたい → 隙間が小さくて入らない
        → 全体の空きは充分あるのに、確保できない／後ろに置くしかない

これが断片化です。

起きること影響
空き領域の探索が遅くなる new がだんだん遅くなる
使うメモリが広い範囲に散る キャッシュに乗りにくくなる
メモリ使用量が増える 実際に使っている量より多く確保される
「長く遊ぶと重くなる」の原因のひとつです 起動直後は 60FPS なのに、1時間遊ぶと 50FPS になる。
Profiler の Memory が、じわじわ増えていないか見てください。 （5-14）

04プールアロケータ ― いちばん単純なもの

「同じ大きさのものだけを扱う」と決めると、極端に速くなります。 

// PoolAllocator.h
#pragma once
#include <vector>
#include <cstdint>

/// <summary>
/// 同じ大きさのブロックを、あらかじめ確保して貸し出す。
/// </summary>
/// <remarks>
/// 空きブロックの中に「次の空きブロックの場所」を書いておく（フリーリスト）。
/// だから、管理用のメモリが別途要らない。
/// </remarks>
class PoolAllocator {
public:
    /// <param name="blockSize">1個の大きさ。ポインタより小さくはできない</param>
    /// <param name="count">個数</param>
    void Init(size_t blockSize, size_t count)
    {
        if (blockSize < sizeof(void*)) {
            blockSize = sizeof(void*);
        }
        m_blockSize = blockSize;
        m_buffer.resize(blockSize * count);

        // 全部つないで、フリーリストを作る
        m_freeHead = m_buffer.data();
        uint8_t* p = m_buffer.data();
        for (size_t i = 0; i < count - 1; i++) {
            *reinterpret_cast<void**>(p) = p + blockSize;
            p += blockSize;
        }
        *reinterpret_cast<void**>(p) = nullptr;   // 最後
    }

    /// <summary>1個借りる。</summary>
    void* Allocate()
    {
        if (m_freeHead == nullptr) {
            return nullptr;                       // 空きなし
        }
        void* p = m_freeHead;
        m_freeHead = *reinterpret_cast<void**>(p);   // ★ 次へ進めるだけ
        return p;
    }

    /// <summary>返す。</summary>
    void Free(void* p)
    {
        if (p == nullptr) { return; }
        *reinterpret_cast<void**>(p) = m_freeHead;   // ★ 先頭につなぐだけ
        m_freeHead = p;
    }

private:
    std::vector<uint8_t> m_buffer;
    void*  m_freeHead  = nullptr;
    size_t m_blockSize = 0;
};
Allocate も Free も、数行です 探索がありません。ポインタを付け替えるだけ。
だいたい 2〜5 ナノ秒。new の 20〜50倍速いです。

そして確保されるメモリは、全部ひとつながりなので、 キャッシュにも乗りやすくなります。

05使い方

class Particle {
public:
    // このクラス専用の new / delete を用意する
    static void* operator new(size_t size)
    {
        void* p = s_pool.Allocate();
        if (p == nullptr) {
            return ::operator new(size);      // あふれたら、ふつうの new
        }
        return p;
    }
    static void operator delete(void* p)
    {
        // ★ プールのものか、ふつうの new のものか区別が要る
        s_pool.Free(p);
    }

    static void InitPool() { s_pool.Init(sizeof(Particle), 10000); }

private:
    static PoolAllocator s_pool;
    ...
};
上のコードには問題があります あふれたとき ::operator new で確保したものを、 s_pool.Free() に渡してしまいます。 プールの範囲外のポインタをフリーリストにつなぐので、壊れます。

正しくは、ポインタがプールの範囲内かを確認します。 
bool Contains(void* p) const
{
    auto* b = m_buffer.data();
    return p >= b && p < b + m_buffer.size();
}

static void operator delete(void* p)
{
    if (s_pool.Contains(p)) { s_pool.Free(p); }
    else                    { ::operator delete(p); }
}
正直に言うと、ここまでやる必要はほぼありません 4-06 のオブジェクトプールで、 同じ効果が、もっと安全に得られます。
そもそも new を呼ばなければ、 アロケータを速くする必要もありません。

この章の価値は、「new の中で何が起きているか」を 知ることそのものにあります。

06実務でよく使われる手

手法考え方使いどころ
オブジェクトプール そもそも作り直さない まずこれ（4-06）
reserve() vector の再確保を防ぐ タダで効く。必ずやる
フレームアロケータ フレーム終わりに、まとめて全部捨てる 一時的な作業領域
プールアロケータ同じ大きさ専用 パーティクルなど
アリーナ用途ごとに領域を分ける 大規模なエンジン

フレームアロケータは、発想が面白いので紹介します。 

class FrameAllocator {
public:
    void Init(size_t size) { m_buffer.resize(size); m_used = 0; }

    void* Allocate(size_t size)
    {
        // 8バイト境界にそろえる
        size = (size + 7) & ~size_t(7);
        if (m_used + size > m_buffer.size()) { return nullptr; }

        void* p = m_buffer.data() + m_used;
        m_used += size;               // ★ 進めるだけ
        return p;
    }

    /// <summary>フレームの終わりに1回呼ぶ。</summary>
    void Reset() { m_used = 0; }      // ★ 解放は、これだけ

private:
    std::vector<uint8_t> m_buffer;
    size_t m_used = 0;
};
個別の解放をあきらめると、こんなに単純になります 確保は「ポインタを進めるだけ」。解放は「0に戻すだけ」。
数ナノ秒どころか、1ナノ秒を切ります。

「このフレームの中でしか使わない」データには最適です。 描画用の一時リスト、当たり判定の候補リストなど。
デストラクタが呼ばれません Reset() はメモリを再利用するだけで、 デストラクタを呼びません。
だから、std::string や std::vector を 含む型を置くと、リークします。
単純な構造体（POD）だけに使ってください。

07演習

演習1（測る）

new/delete を10万回繰り返す時間を測る。1回あたり何ナノ秒か。

演習2（作る）

プールアロケータを作って、new と比べる。何倍速いか。

解答例を見る（まず自分でやってから） 
void CompareAllocator()
{
    const int N = 100000;
    struct Obj { float a, b, c, d; int e, f; };   // 32バイト

    std::vector<Obj*> ptrs(N);

    //----- ふつうの new / delete -----
    {
        BENCH("new/delete x100000");
        for (int i = 0; i < N; i++) { ptrs[i] = new Obj(); }
        for (int i = 0; i < N; i++) { delete ptrs[i]; }
    }

    //----- プールアロケータ -----
    PoolAllocator pool;
    pool.Init(sizeof(Obj), N);

    {
        BENCH("pool x100000");
        for (int i = 0; i < N; i++) {
            ptrs[i] = (Obj*)pool.Allocate();
        }
        for (int i = 0; i < N; i++) {
            pool.Free(ptrs[i]);
        }
    }

    //----- 交互にやる（断片化しやすい条件）-----
    {
        BENCH("new/delete 交互");
        for (int i = 0; i < N; i++) {
            Obj* p = new Obj();
            if (i % 2 == 0) { ptrs[i / 2] = p; }
            else            { delete p; }
        }
        for (int i = 0; i < N / 2; i++) { delete ptrs[i]; }
    }
}

典型的な結果（Release）

new/delete x100000           :   14.230 ms    （1回あたり 71 ns）
pool x100000                 :    0.612 ms    （1回あたり  3 ns）
new/delete 交互              :   18.905 ms

→ プールは new の約 23倍速い

さらに ― なめる速さも比べる

// 確保したあと、全部なめる時間も測る
{
    BENCH("new で確保したものをなめる");
    float sum = 0;
    for (int i = 0; i < N; i++) { sum += ptrs[i]->a; }
    if (sum < 0) { OutputDebugStringA("never\n"); }
}
new で確保したものをなめる   :    2.180 ms
pool で確保したものをなめる  :    0.094 ms     ← 23倍

→ 確保が速いだけでなく、あとで使うときも速い
2つめの差のほうが、実は大事です プールで確保したものは、メモリ上でひとつながりです。

5-04 のとおり、 連続していればキャッシュに乗ります。

「確保が速い」より「確保したあとが速い」ほうが、 ゲーム全体への効果は大きいことが多いです。
この実験では、コンストラクタを呼んでいません pool.Allocate() はメモリを返すだけです。

本当に使うなら、placement new でコンストラクタを呼ぶ必要があります。 
void* mem = pool.Allocate();
Obj* p = new (mem) Obj();      // placement new

p->~Obj();                     // デストラクタを明示的に呼ぶ
pool.Free(p);
この面倒さが、4-06 の オブジェクトプールを勧める理由です。

演習3（考える）

4-06 のオブジェクトプールと、この章のプールアロケータの違いを説明する。自分のゲームには、どちらが必要か。

解答例を見る（まず自分でやってから）

違い

オブジェクトプール（4-06）プールアロケータ（5-07）
何を再利用するオブジェクトそのもの メモリだけ
コンストラクタ1回だけ（Start()） 毎回呼ぶ（placement new）
初期化のコストゼロ（Reset() だけ） 毎回かかる
使うのが難しいかやさしい placement new が必要。難しい
型ごとに必要か型ごとサイズが同じなら共用できる
k2Engine と相性 良い（Activate/Deactivate） 普通

オブジェクトプールのほうが、たいてい優れています

理由：Init() のコストまで省けるからです。 

// プールアロケータ（メモリだけ再利用）
void* mem = pool.Allocate();           // 3 ns
Bullet* b = new (mem) Bullet();        // コンストラクタ
b->Init("Assets/sprite/bullet.dds");   // ★ これが重い（数千 ns）

// オブジェクトプール（オブジェクトごと再利用）
Bullet* b = m_pool.Acquire();          // 数 ns
b->Reset(pos, vel);                    // ★ 値を代入するだけ
ゲームで重いのは new ではなく Init() です テクスチャの設定、シェーダのバインド、バッファの作成。

new が 71ns でも、Init() が 5000ns なら、 最適化すべきはそちらです。

だから 5-01 のとおり、 まず測るのです。

自分のゲームにはどちらが必要か

状況選ぶもの
弾やエフェクトを大量に作る オブジェクトプール（4-06）
毎フレーム一時的な配列を作る フレームアロケータ、または reserve()
パーティクルを10万個扱う SoA ＋ 固定長配列。 そもそも new しない
上のどれでもない何もしなくてよい
学生作品で、アロケータの自作が必要になることは、まずありません この章は「知識」の章です。

面接で「new のコストは？」と聞かれたときに、 中で何が起きているかを説明できることのほうが、 実際にアロケータを書くことより価値があります。

そして「自作しませんでした。オブジェクトプールで足りたので」 と言えるのが、いちばん良い答えです。

08確認

  1. new が時間を使っている、主な理由を2つ。
  2. 断片化が進むと、何が起きる？
  3. プールアロケータの Allocate は、何をしている？
  4. フレームアロケータの制約は？
答え
  1. 空き領域の探索と、スレッド間のロック。
  2. new が遅くなる。メモリが散ってキャッシュに乗りにくくなる。 使用量も増える。
  3. フリーリストの先頭を取り出して、次に進めるだけ。
  4. 個別に解放できない。デストラクタが呼ばれないので、 単純な構造体にしか使えない。
