難易度 ／ 前提 4-02

01この章でできるようになること

  • 継承で破綻する理由を説明できる
  • 「持つ」で書き直せる
  • それでも継承を使ってよい場面が分かる

02ありがちな破綻

敵を作ります。共通部分を Enemy にまとめました。 ここまでは、うまくいきます。 

Enemy
 ├ ZakoEnemy          // まっすぐ進む雑魚
 └ ShooterEnemy       // 弾を撃つ敵

次に「弾を撃ちながら、まっすぐ進む敵」が欲しくなります。

…どちらを継承すればいいでしょうか。

03なぜ継承だと増えるのか

継承は1本の木です。親は1つしか選べません （C++は多重継承もできますが、話がもっと複雑になります）。

ところがゲームの敵は、いくつもの軸の組み合わせで決まります。

軸種類
動き方まっすぐ / ジグザグ / 追尾 / 止まる
撃ち方撃たない / 単発 / 3方向 / 全方位
耐久1発 / 数発 / 大量

この3軸だけで、4 × 4 × 3 = 48通り。 継承で表そうとすると、48個のクラスが要ります。

部品として持てば、4 + 4 + 3 = 11個で足ります。

04もうひとつの落とし穴 ― 親を直すと子が壊れる

// あるとき、Enemy の Update に処理を足した
void Enemy::Update()
{
    Move();
    CheckScreenOut();     // ★ 画面外に出たら DeleteGO するようにした
}

便利だと思って足しました。ところが BossEnemy は 画面外に一度出てから戻ってくる演出をしていました。

ボスが消えました。

これを「脆い基底クラス問題」といいます 親を直したとき、影響が及ぶ範囲が見えません。 子クラスが10個あれば、10個分を頭の中で確認することになります。
継承が深くなるほど、親に手を入れるのが怖くなります。

05「持つ」に書き直す

// 動き方を、部品として切り出す
class IMover {
public:
    virtual ~IMover() {}
    virtual void Move(Vector3& position, float dt) = 0;
};

class StraightMover : public IMover {
public:
    void Move(Vector3& position, float dt) override
    {
        position.y -= 200.0f * dt;
    }
};

class ZigzagMover : public IMover {
public:
    void Move(Vector3& position, float dt) override
    {
        m_time += dt;
        position.y -= 150.0f * dt;
        position.x  = m_baseX + sinf(m_time * 3.0f) * 200.0f;
    }
private:
    float m_time  = 0.0f;
    float m_baseX = 0.0f;
};
// 敵は1つだけ。部品を持つ
class Enemy : public IGameObject {
public:
    void SetMover(std::unique_ptr<IMover> mover)
    {
        m_mover = std::move(mover);
    }

    void Update() override
    {
        const float dt = g_gameTime->GetFrameDeltaTime();
        if (m_mover) {
            m_mover->Move(m_position, dt);
        }
        ...
    }

private:
    std::unique_ptr<IMover> m_mover;
};
// 使うとき
Enemy* e = NewGO<Enemy>(enPriority_Enemy, "enemy");
e->SetMover(std::make_unique<ZigzagMover>());
これは Strategy パターンです 名前は 4-09 で出てきます。 いまは「動き方を部品にして、差し替えられるようにした」 とだけ分かっていれば充分です。

06では、継承はいつ使うのか

継承が悪いわけではありません。 使いどころが決まっているだけです。

インターフェースの継承実装の継承
親の中身ほぼ空（純粋仮想関数だけ） 実際の処理が入っている
目的「同じように扱える」ことの宣言 コードの使い回し
例IGameObject、IMover Enemy → ZakoEnemy
評価どんどん使ってよい 2段までにとどめる

IGameObject を継承するのは、まったく問題ありません。 親にはほとんど実装がなく、 「Start / Update / Render が呼ばれる」 という約束だけを決めているからです。

判断の合言葉 「〜である（is-a）」なら継承、「〜を持つ（has-a）」ならメンバ。
敵は「移動方法である」わけではなく、「移動方法を持つ」のです。 だからメンバにします。

07演習

演習1（数える）

自分のコードの継承の段数を調べる。3段以上あるものはどれか。

演習2（書き直す）

敵の動き方を IMover として切り出し、2種類以上の動きを差し替えられるようにする。

解答例を見る（まず自分でやってから）

IMover.h（1ファイルにまとめてよい）

#pragma once

/// <summary>敵の動き方。</summary>
class IMover {
public:
    virtual ~IMover() {}

    /// <summary>
    /// 1フレーム分、位置を動かす。
    /// </summary>
    /// <param name="position">動かす対象。書き換える。</param>
    /// <param name="dt">前のフレームからの秒数。</param>
    virtual void Move(Vector3& position, float dt) = 0;
};

/// <summary>まっすぐ下に進む。</summary>
class StraightMover : public IMover {
public:
    explicit StraightMover(float speed) : m_speed(speed) {}

    void Move(Vector3& position, float dt) override
    {
        position.y -= m_speed * dt;
    }
private:
    float m_speed;
};

/// <summary>左右に揺れながら下に進む。</summary>
class ZigzagMover : public IMover {
public:
    ZigzagMover(float speed, float width, float cycle)
        : m_speed(speed), m_width(width), m_cycle(cycle) {}

    void Move(Vector3& position, float dt) override
    {
        if (m_isFirst) {
            m_baseX  = position.x;       // 最初のX座標を覚えておく
            m_isFirst = false;
        }
        m_time += dt;
        position.y -= m_speed * dt;
        position.x  = m_baseX + sinf(m_time * m_cycle) * m_width;
    }
private:
    float m_speed, m_width, m_cycle;
    float m_time  = 0.0f;
    float m_baseX = 0.0f;
    bool  m_isFirst = true;
};

/// <summary>プレイヤーを追いかける。</summary>
class ChaseMover : public IMover {
public:
    explicit ChaseMover(float speed) : m_speed(speed) {}

    void Move(Vector3& position, float dt) override
    {
        Player* player = FindGO<Player>("player");
        if (player == nullptr) {
            position.y -= m_speed * dt;    // いなければ、まっすぐ
            return;
        }
        Vector3 toPlayer = player->GetPosition() - position;
        toPlayer.Normalize();
        position += toPlayer * m_speed * dt;
    }
private:
    float m_speed;
};

使い方

// Spawner.cpp
Enemy* e = NewGO<Enemy>(enPriority_Enemy, "enemy");
e->SetPosition({ x, 600.0f, 0.0f });

switch (type) {
case 0: e->SetMover(std::make_unique<StraightMover>(200.0f)); break;
case 1: e->SetMover(std::make_unique<ZigzagMover>(150.0f, 200.0f, 3.0f)); break;
case 2: e->SetMover(std::make_unique<ChaseMover>(120.0f)); break;
}
数値をコンストラクタで渡すのがコツです 同じ ZigzagMover でも、 振れ幅と周期を変えれば別の敵に見えます。

クラスを増やす前に、「数値を変えるだけで済まないか」を考えてください。
仮想デストラクタを忘れずに virtual ~IMover() {} を書かないと、 unique_ptr<IMover> が破棄されるとき 派生クラスのデストラクタが呼ばれません。

基底クラスを作ったら、まず仮想デストラクタ。反射で書いてください。

演習3（考える）

IGameObject を継承するのは問題ないのに、Enemy を3段継承するとまずいのはなぜか、自分の言葉で説明する。

解答例を見る（まず自分でやってから）

違いは「親に実装があるかどうか」です。

IGameObject3段継承した Enemy
親の中身 ほぼ空。virtual bool Start() { return true; } 程度 移動・描画・当たり判定…実処理がびっしり
親を直したとき 直すことがほぼ無い 子全部に影響する
子が知るべきこと 「Update が毎フレーム呼ばれる」だけ 親が何をしているか全部
段数1段3段。実処理が3か所に散る

3段継承の具体的な困りごと

Enemy → MovingEnemy → ShootingEnemy → BossEnemy
  • BossEnemy::Update() を読んでも、何が起きるか分からない。 4つのファイルを行き来する必要がある
  • デバッガでステップ実行すると、 知らない親の関数に何度も入る
  • Enemy に1行足すと、BossEnemy まで影響が届く。 しかも影響したことに気づけない
  • 「ボスだけ、この処理を通したくない」となったとき、 親にフラグを足すことになる。そして親がさらに複雑になる
見分け方：親のコードを読まずに子が読めるか IGameObject は、中身を読まなくても使えます。 「Start が最初に1回、Update が毎フレーム」―― それだけ知っていれば書けます。

3段継承の BossEnemy は、親3つを読まないと理解できません。 これが決定的な差です。

「継承は1段まで」を目安にしてよいです。

2段目が欲しくなったら、「それは持たせられないか」を先に考える。 それでも継承がきれいなら使う。 思考の順番を変えるだけで、だいぶ変わります。

08確認

  1. 継承で組み合わせを表すと、クラス数はどう増える？
  2. 脆い基底クラス問題とは？
  3. 「is-a」と「has-a」、それぞれどう書く？
  4. 基底クラスを作ったとき、必ず書くものは？
答え
  1. 軸の数だけ掛け算で増える（4×4×3＝48など）。
  2. 親を直すと、子クラス全部に影響が及ぶこと。 しかも影響範囲が見えない。
  3. is-a は継承、has-a はメンバとして持つ。
  4. 仮想デストラクタ（virtual ~Base() {}）。
