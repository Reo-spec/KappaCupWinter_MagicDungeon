LV5 最適化 ／ 5-01

計測せずに最適化するな

難易度 ／ 前提 2-24

01LV5 は何をするところか

LV4 の判断基準は「読みやすさ」と「変更しやすさ」でした。
LV5 の判断基準は「速さ」です。

そして、この2つはしばしば対立します。 どちらが正しいという話ではありません。 場面ごとに選べるようになるのが目標です。

LV5 でいちばん大事なのは、この章です 以降の章で出てくる技術は、全部「使いどころを間違えると害になる」ものです。 測ることを覚えないまま先に進まないでください。

02なぜ「計測せずに」がダメなのか

人間の推測は、驚くほど当たりません。

よくある推測実際
ループが多いから、そこが重い ループの中身が軽ければ、何ともない
当たり判定が重い たいてい描画のほうが重い
sqrt が重い いまのCPUでは、たいした問題ではない
関数呼び出しが重い Release ではインライン化されて消える
ここが原因に違いない まったく別の場所だった
最適化は、コードを悪くします 速いコードは、たいてい読みにくくなります。 4-16 でせっかく整理したものを、 また崩すことになります。
それに見合う効果があるかどうかは、測らないと分かりません。

03まず Profiler パネルを開く

F1 → Profiler パネルです。

04数字の読み方

表示意味目安
xx.xx ms (xx.x fps) 1フレームにかかった時間 16.6ms 以内で 60FPS
max xx.xx ms 履歴の中でいちばん遅かったフレーム 平均より、こちらが大事
グラフフレーム時間の推移 とがっているところが引っかかり
Section / Time K2_PROFILE_SCOPE の計測結果 5-02
EndFrame(Present/Wait) 60FPSに合わせるための「待ち時間」 長いほど余裕がある
Draw call「描け」と命令した回数 5-08
Instance実際に描かれたモデルの数 インスタンシングを使うと Draw call より大きくなる
GameObject 生きているゲームオブジェクトの数 増え続けていたら DeleteGO 忘れ
Memoryプロセスのメモリ使用量 5-14
VRAMビデオメモリ使用量 予算を超えると急に重くなる

パネルの項目にマウスを乗せると、説明が出ます。 覚えなくても、その場で読めます。

平均ではなく max を見てください 平均 8ms でも、ときどき 40ms のフレームがあれば、 プレイヤーには「カクつく」と感じられます。
平均が良いことより、最悪値が悪くないことのほうが、 体感には効きます。
Section は 0.25秒ごとの平均値です 毎フレームの生の値ではありません。 数字がぶれずに読めるように、ならしてあります。
だから一瞬のスパイクは、Section ではなくグラフと max で見ます。

05EndFrame が、いちばん分かりやすい余裕の指標です

EndFrame(Present/Wait) は、 「60FPSに間に合ったので、次のフレームまで何もせず待っている時間」です。

EndFrame の値状態
14 ms（フレームの大半） 非常に余裕がある。最適化は不要
8 ms余裕あり
2 msぎりぎり。そろそろ危ない
0 ms 間に合っていない。FPSが落ちている
Frame の数字だけ見ていると、危機に気づけません FPS制限があるので、処理が軽くても重くても Frame は 16.6ms 前後に張り付きます。

16.6ms のままでも、EndFrame が 14ms から 3ms に減っていたら、 裏では処理が 11ms 増えているということです。
FPSが落ち始める前に気づけます。
GameObject の数も、毎回見る癖をつけてください 増え続けていたら DeleteGO の消し忘れです （5-14）。
内訳は F1 → GameObject List で見られます （2-06）。

0616.6ms という数字

目標FPS1フレームの予算
60 FPS16.6 ms
30 FPS33.3 ms
120 FPS8.3 ms

「1フレームに使える時間の予算」と考えてください。 16.6ms のうち、

  • ゲームの更新に 5ms
  • 描画の準備に 4ms
  • GPU待ちに 6ms
  • 余裕 1.6ms

…といった配分になります。1ms は、決して小さくありません。 全体の6%です。

「0.01ms 速くなりました」は、意味がありません 16.6ms のうちの 0.01ms は、0.06% です。 誤差に埋もれます。
最適化は「1ms 以上の効果があるか」を基準にしてください。

07CPU と GPU、どちらが遅いのか

最初に切り分けるべきことです。 対策がまったく違います。

試すこと速くなったら
ウィンドウを小さくする GPU が原因（ピクセルの処理）
オブジェクトを半分に減らす 両方ありうる
F1 でポストエフェクトを全部切る GPU が原因
描画だけ止めて、更新は動かす 切り分けとして、いちばん確実

ウィンドウサイズを変えて速くなるなら、 CPU側をいくら最適化しても無駄です。 3-15 の PIX で GPU 側を見てください。

LV5 は、ほとんど CPU 側の話です GPU 側の話は 5-08 だけです。
まず、自分のゲームがどちらで詰まっているか確かめてください。

08最適化の順番

順やること効き方
1 そもそもやらない（画面外の処理を飛ばす、など） いちばん効く
2アルゴリズムを変える（O(n²) → O(n)） 桁で効く
3データの並べ方を変える 5-06。数倍
4並列化する 5-12。コア数ぶん
5細かい書き方を変える 数%。最後でよい
多くの人が、5番から始めてしまいます i++ を ++i にする、 sqrt を避ける、といったことです。
効果はほぼありません。コンパイラがやってくれます。
1番と2番を先にやってください。

09演習

演習1（見る）

F1 → Profiler を開いて、いまの Frame / Max / FPS を記録する。

演習2（切り分ける）

ウィンドウを小さくして、速くなるか試す。自分のゲームは CPU と GPU、どちらで詰まっているか。

解答例を見る（まず自分でやってから）

やり方

  1. いちばん重くなる場面（弾幕、敵が大量、など）を作る
  2. その状態で Frame(ms) を記録
  3. ウィンドウを4分の1くらいの大きさにする
  4. 同じ場面で、もう一度記録

判定

結果意味次に読む章
18ms → 6ms（大きく速くなった） GPU律速。ピクセルの処理が重い 5-08、 3-15
18ms → 17ms（ほぼ変わらない） CPU律速。更新処理が重い LV5 のほぼ全部
18ms → 13ms（少し速い） 両方。まず大きいほうから両方

さらに確実な切り分け ― 描画だけ止める

// Game.cpp
#ifdef _DEBUG
if (g_pad[0]->IsPress(enButtonBack)) {
    return;                 // ★ 描画をまるごと飛ばす
}
#endif
m_gameObjectManager->ExecuteRender(rc);

これを押している間だけ速くなるなら、描画（GPUまたは描画準備）が原因です。 押しても変わらないなら、更新処理（CPU）が原因です。

ポストエフェクトを切ってみるのも速いです F1 → Post Effect パネルで、 Bloom / DoF / SSR / FXAA を全部オフにしてください （3-01）。

これで劇的に速くなるなら、GPU の負荷はポストエフェクトです。 そして、それは設定で切れるようにしておけばよいだけの話です。

演習3（探す）

グラフがとがっているところを探す。ゲーム中のどの操作をしたときに、フレーム時間が跳ねるか。本文には答えがありません。

解答例を見る（まず自分でやってから）

探し方

グラフを見ながら、いろいろ操作してみてください。 とがった瞬間に何をしていたかをメモします。

よくある「とがる」場所

とがるタイミング原因効く章
シーン切り替えの瞬間 テクスチャ・モデルの読み込み 先に読んでおく（プリロード）
ボスが出てくる瞬間大量の NewGO と初期化 4-06
爆発エフェクトが出た瞬間 .efk の読み込み、大量のパーティクル 4-06
弾幕が濃くなったとき当たり判定の O(n²) 5-06
一定間隔で定期的に メモリの断片化、GCのような処理 5-07
初回だけシェーダのコンパイル、ファイルキャッシュ 2回目以降が本当の値

記録の例

== スパイクの記録 ==

1. ボス出現時       : 16ms → 89ms  ★最大
   → ボスのモデルとアニメを、そこで初めて読んでいる
2. 爆発が5個同時    : 16ms → 34ms
   → Explosion を毎回 NewGO している
3. ステージ2に切替  : 16ms → 210ms
   → シーン切り替えで全部読み直し。暗転でごまかしている
4. 弾200発超        : 16ms → 22ms
   → 当たり判定が弾×敵の総当たり
スパイクは、平均より体感に効きます 平均 16ms でも、ボス出現時に 89ms かかると、 プレイヤーには「一瞬止まった」とはっきり分かります。

そして、そういう瞬間は「ボスが出てくる」という いちばん盛り上がる場面だったりします。
いちばん効く対策は「先に読んでおく」 読み込みのスパイクは、 ゲーム開始時やロード画面中にまとめてやってしまえば消えます。

4-06 のプールも、 「あとで必要になるものを、先に作っておく」という同じ考え方です。

LV5 の最適化の中で、いちばん効果が大きく、 いちばんコードを汚さないのがこれです。

10確認

  1. 60FPS のための、1フレームの予算は？
  2. 平均より Max を見るのはなぜ？
  3. CPU か GPU かを切り分ける、手軽な方法は？
  4. 最適化の順番で、いちばん効くのは？
答え
  1. 16.6 ミリ秒。
  2. ときどき跳ねるフレームがあると、 平均が良くてもカクついて感じられるから。
  3. ウィンドウを小さくする。速くなれば GPU 律速。
  4. そもそもやらないこと（処理を飛ばす、先に読んでおく）。
