マルチスレッド① まず壊す

難易度 ／ 前提 5-03

01この章でやること

正しい書き方を覚える前に、わざと壊します。

2-08 で 削除済みオブジェクトにアクセスして壊したのと、同じ方針です。 自分で壊した経験がないと、なぜ危ないかが身につきません。

マルチスレッドのバグは、いちばん厄介な種類です 再現しない。デバッガで止めると起きない。 Release でだけ起きる。1000回に1回だけ起きる。
だから「動いたから大丈夫」が、まったく通用しません。

02スレッドとは

同じプログラムの中で、同時に走る処理の流れです。

共有するもの別々に持つもの
スレッド メモリ（グローバル変数、ヒープ） スタック、レジスタ

メモリを共有しているのが、便利であり、危険でもあります。 

#include <thread>

void Work(int id)
{
    for (int i = 0; i < 3; i++) {
        char buf[64];
        sprintf_s(buf, "thread %d : %d\n", id, i);
        OutputDebugStringA(buf);
    }
}

void Run()
{
    std::thread t1(Work, 1);
    std::thread t2(Work, 2);

    t1.join();      // ★ 終わるまで待つ
    t2.join();
}
join() を忘れると、プログラムが落ちます std::thread は、 join() も detach() もしないまま破棄されると、 std::terminate() が呼ばれます。
「なぜか終了時に落ちる」の、よくある原因です。

03実験1 ― カウンタを壊す

#include <thread>
#include <vector>

int g_counter = 0;      // ★ 共有される

void CountUp()
{
    for (int i = 0; i < 1000000; i++) {
        g_counter++;          // ★ ここが問題
    }
}

void BreakCounter()
{
    g_counter = 0;

    std::vector<std::thread> threads;
    for (int i = 0; i < 4; i++) {
        threads.emplace_back(CountUp);
    }
    for (auto& t : threads) { t.join(); }

    char buf[128];
    sprintf_s(buf, "期待値 4000000 / 実際 %d\n", g_counter);
    OutputDebugStringA(buf);
}

期待値は 4,000,000 です。実行してみてください。 

期待値 4000000 / 実際 1284713
期待値 4000000 / 実際 1519022
期待値 4000000 / 実際 1402886      ← 毎回違う

04なぜ数が合わないのか

g_counter++ は、1つの命令ではありません。 3段階に分かれています。 

1. メモリから g_counter を読む     （レジスタへ）
2. 1 を足す
3. メモリへ書き戻す

2つのスレッドが、同時にここを実行すると： 

            スレッドA              スレッドB           g_counter
時刻1   読む（100 を得る）                                100
時刻2                          読む（100 を得る）         100
時刻3   +1 して 101                                       100
時刻4                          +1 して 101                100
時刻5   書き戻す                                          101
時刻6                          書き戻す                   101   ★ 2回足したのに +1
これを「データ競合（data race）」といいます 複数のスレッドが、同じ場所に、 片方でも書き込みながらアクセスすると起きます。
C++ の規格上、データ競合があるプログラムは 「何が起きても文句が言えない（未定義動作）」と決められています。
「たまたま正しい値が出た」も、正しさの証明にはなりません。

05実験2 ― もっとひどく壊す

#include <vector>
#include <thread>

std::vector<int> g_list;

void PushMany()
{
    for (int i = 0; i < 10000; i++) {
        g_list.push_back(i);        // ★ 絶対にやってはいけない
    }
}

void BreakVector()
{
    g_list.clear();

    std::thread t1(PushMany);
    std::thread t2(PushMany);
    t1.join();
    t2.join();

    char buf[128];
    sprintf_s(buf, "期待値 20000 / 実際 %zu\n", g_list.size());
    OutputDebugStringA(buf);
}
これは、たいてい「クラッシュ」します push_back は、容量が足りなくなると 新しい領域を確保して、全部コピーして、古いほうを解放します。

その最中に別のスレッドが push_back すると、 解放済みのメモリに書き込みます。
数が合わないどころではありません。

標準ライブラリのコンテナは、 複数スレッドからの同時書き込みに対応していません。 std::vector、std::map、 std::string、全部そうです。

06実験3 ― 再現しないことを確かめる

void BreakCounterMany()
{
    for (int trial = 0; trial < 20; trial++) {
        g_counter = 0;
        std::vector<std::thread> threads;
        for (int i = 0; i < 4; i++) { threads.emplace_back(CountUp); }
        for (auto& t : threads) { t.join(); }

        char buf[128];
        sprintf_s(buf, "%2d 回目 : %d\n", trial, g_counter);
        OutputDebugStringA(buf);
    }
}

20回とも違う値が出るはずです。 そしてときどき、正解に近い値が出ることもあります。

Debug ビルドだと、正解が出ることがあります 最適化が違うため、タイミングが変わるからです。
「Debug では動くが Release で落ちる」というバグの、 典型的な原因のひとつがこれです。

ブレークポイントを置くと再現しなくなるのも同じ理由です。 止めているあいだに、片方のスレッドが終わってしまいます。

07ゲームでよくある危ない場所

やりたいこと危ないところ
別スレッドでファイルを読む 読み終わったあと、NewGO してしまう
当たり判定を並列化 ヒットしたとき、共有のリストに追加する
敵の更新を並列化 敵が別の敵の状態を読む
スコア加算を並列化 実験1そのもの
ログ出力 OutputDebugStringA は安全だが、 自作のログバッファは危ない
エンジンの関数を、別スレッドから呼ばないでください NewGO、DeleteGO、 FindGO、ModelRender の各種関数。
k2Engine は、シングルスレッド前提で書かれています。

別スレッドでやってよいのは、 「自分が用意した配列の中だけで完結する計算」だけだと 考えてください。

演習2（もっと壊す）

実験2を動かす。何が起きたか記録する。Debug と Release で違いがあるか。

解答例を見る（まず自分でやってから）

起きること

ビルドよくある結果
Debug アサートで止まる（vector iterators incompatible など）
または「ヒープが壊れています」
Release アクセス違反でクラッシュ
または、数が合わないまま動き続ける

Debug のほうが、親切に壊れます

Visual Studio の Debug ビルドは、 標準ライブラリに検査コードを埋め込みます （イテレータデバッグ）。 だから、おかしいことをすると、その場で教えてくれます。

Release にはそれがないので、壊れたまま走り続けて、 まったく別の場所で落ちます。

「Release でだけ落ちる」の理由が、ここにあります Debug で落ちなかったから安全、ではありません。

Debug は検査してくれる。Release は検査しない。 それだけの違いです。

マルチスレッドのコードは、必ず Release でも長時間動かして 確認してください。

もっとひどい壊れ方を見る

// あらかじめ容量を確保しておくと、再確保が起きなくなる
g_list.reserve(20000);      // ★ これを入れると…

クラッシュしなくなることがあります。 でも、数は合いません。 

期待値 20000 / 実際 13847
これがいちばん危ない状態です クラッシュしないので、バグに気づけません。

「落ちないから正しい」は、マルチスレッドではまったく成り立ちません。

push_back は 「size を読む → 書き込む → size を増やす」 という複数の手順なので、再確保が起きなくても競合します。

演習3（探す）

自分のゲームに、並列化できそうな処理があるか探す。「共有データに書き込まない」処理はどれか。本文には答えがありません。

解答例を見る（まず自分でやってから）

並列化できる条件

  1. ほかのスレッドが書く場所を、読まない
  2. ほかのスレッドが読む場所に、書かない
  3. エンジンの関数を呼ばない
  4. 並列化する価値があるほど重い（目安：1ms 以上）

自分のゲームでの候補

処理並列化できる？理由
弾の位置更新できる 弾 i は、弾 i のデータしか触らない
パーティクルの更新できる 同上。しかも数が多い
当たり判定（判定だけ）できる 結果の書き込み方に注意
敵のAI（他の敵を見ない場合）できる—
敵のAI（他の敵と連携する）難しい 互いの状態を読む
スコア加算できない共有変数に書く
NewGO / DeleteGO 絶対にできない エンジンの内部状態を触る
描画できない RenderContext は共有

「判定だけ並列、結果は後でまとめる」というパターン

// ★ 危ない：共有のリストに直接追加
void CheckHitParallel()
{
    parallel_for(i) {
        if (IsHit(i)) {
            g_hitList.push_back(i);      // ★ データ競合
        }
    }
}

// ○ 安全：スレッドごとの配列に書いて、あとで合流
void CheckHitParallel()
{
    std::vector<std::vector<int>> results(NUM_THREAD);

    parallel_for(t) {
        for (自分の担当ぶん i) {
            if (IsHit(i)) {
                results[t].push_back(i);   // ★ 自分専用の配列
            }
        }
    }

    // 全部終わってから、1スレッドでまとめる
    for (auto& r : results) {
        for (int i : r) { OnHit(i); }
    }
}
この「スレッドごとに持って、あとで合流」が定石です ロックを一切使わずに済みます。

5-11 で mutex を学びますが、 そもそも共有しないで済むなら、そのほうがずっと速くて安全です。
候補が見つからなくても、それでよいです 2Dシューティングで、1ms を超える単一の処理がなければ、 並列化する意味はありません。

スレッドを起動するだけで、数十マイクロ秒かかります。

0.1ms の処理を並列化しても、遅くなるだけです。

09確認

  1. スレッド間で共有されるものは？
  2. g_counter++ が危ないのはなぜ？
  3. データ競合があるプログラムは、C++ の規格上どう扱われる？
  4. Debug では動いて Release で落ちるのはなぜ？
答え
  1. メモリ（グローバル変数、ヒープ）。 スタックとレジスタは別々。
  2. 「読む・足す・書く」の3段階なので、 途中で別スレッドが割り込むと結果が失われる。
  3. 未定義動作。何が起きても文句が言えない。
  4. 最適化でタイミングが変わる。 また Debug には標準ライブラリの検査があるが、Release には無い。
