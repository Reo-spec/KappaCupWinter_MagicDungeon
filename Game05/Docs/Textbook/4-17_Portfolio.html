LV4 設計 ／ 4-17

ポートフォリオと技術面接

難易度 ／ 前提 4-16

01この章でできるようになること

  • 設計の理由を90秒で説明できる
  • ポートフォリオに何を載せるべきか分かる
  • 技術面接で聞かれることの見当がつく
この章は、教材の中でいちばん賞味期限が短いです 採用の傾向は変わります。 会社によっても違います。
「こういう観点で見られる」という目安として読んでください。

02何が見られているのか

「すごいものを作れるか」ではありません。

見られていることなぜ
一緒に働けそうか 技術より、こちらが先に見られます
自分で調べて解決できるか 教えることはできるが、手取り足取りは無理
最後まで作りきれるか 途中でやめる人が、思った以上に多い
他人のコードを読めるか 入社後、書くより読む時間のほうが長い
判断の理由を言えるか ここで差がつきます
LV4 でやったことは、全部ここに効きます ゲームの出来より、 4-16 の REFACTOR_LOG.md のほうが刺さることは珍しくありません。
「動くものを作った」人は大勢います。 「動くものを、壊さずに作り替えた」人は多くありません。

03ポートフォリオに載せるもの

載せる備考
動画（30秒〜1分） 最初に見られる。いちばん大事
実行ファイル一式 ダブルクリックで動くこと。これができていない人が多い
ソースコード（Git）履歴も見られます
1枚の技術資料 設計図、工夫した点、苦労した点
操作説明1枚。動かせないと評価できません
素材のクレジット 素材の用意のしかた
「動かない」が、いちばんもったいない落とし方です 必ず、自分の開発マシン以外で動かして確認してください。
よくある原因対策
Assets フォルダを入れ忘れ Release フォルダごと固める
Debug ビルドを配布 Release にする。Debug は動かない環境がある
VC++ 再頒布パッケージが無い readme に必要なものを書く
絶対パスでファイルを読んでいる C:\Users\自分\... を探す

04技術資料に書くこと

1〜2枚で充分です。長いものは読まれません。 

# ○○（ゲーム名）技術資料

## 概要
C++ / DirectX12（k2Engine）/ 個人制作 / 制作期間3か月

## 全体構成
（クラス図を1枚。ツールは何でもよい。手描きでも可）

## 工夫した点（3つまで）

### 1. 敵の追加を、表に1行書くだけにした
種類ごとにクラスをコピペしていて、敵を1体足すのに
3ファイル触る必要があり、追加漏れのバグを出していた。
移動と攻撃を Strategy として切り出し、敵の定義をテーブルにした。
結果、追加作業が40分から3分になった。

### 2. 弾をプールにして、1000発でも60FPSを維持した
毎フレーム NewGO/DeleteGO していたため、弾幕時に22FPSまで落ちていた。
Profiler で Shot 関数に 0.42ms かかっていることを確認し、
200発のプールを用意して Activate/Deactivate で使い回す形に変更。
0.03ms になり、1000発でも60FPSを維持できるようになった。

## 苦労した点

Observer パターンを導入したとき、購読を解除せずに
オブジェクトを削除してしまい、再現性のないクラッシュに数日悩んだ。
デストラクタで自動的に解除される RAII のクラスを作って解決した。

## やらなかったこと

汎用のコンポーネントシステムは作らなかった。
実行中に機能を付け外しする必要が無く、
dynamic_cast のコストと、コンパイル時の検査が効かなくなる点が
割に合わないと判断したため。
「数字」と「やらなかったこと」が効きます 数字があると、測ったことが伝わります。
やらなかったことがあると、判断したことが伝わります。
どちらも、ただ作っただけでは書けません。

0590秒で説明する練習

「このゲームで工夫したところを教えてください」 — 必ず聞かれます。

配分話すこと
15秒何に困っていたか
15秒どう調べ、どう判断したか
30秒何をしたか
20秒 結果（数字で）
10秒残った課題
「困っていたこと」から始めてください 「Strategy パターンを使いました」から始めると、 『なぜ？』と聞き返されます。
「敵を足すのに3ファイル触る必要があって、 追加漏れのバグを出したんです」から始めると、 聞き手が納得した状態で解決策を聞けます。

07答えられないときの答え方

知らないことは必ず聞かれます。 そこで何を見られているかというと、知識ではなく態度です。

だめよい
（黙る） 「分かりません。〜だとは思うのですが」
知ったかぶりをする 「使ったことはありませんが、〜という理解です」
「勉強不足です」で終わる 「調べてみます。どのあたりから見るとよいですか」
知ったかぶりは、ほぼ確実にばれます 面接官は、その分野の専門家です。 一段深く聞かれた瞬間に分かります。
「知らない」と言える人のほうが、一緒に働きやすいと判断されます。

08演習

演習1（まとめる）

4-16 の REFACTOR_LOG.md をもとに、技術資料を1〜2枚書く。

演習2（話す）

工夫した点を、90秒で声に出して説明する。録音して聞き返す。

解答例を見る（まず自分でやってから）

やり方

  1. スマホで録音する
  2. 原稿を見ずに話す
  3. 聞き返す（ここがつらいが、いちばん効く）
  4. 3回繰り返す

聞き返すときのチェック

チェックよくある失敗
90秒に収まっているか 3分話している。長い＝要点が絞れていない
困っていたことから始まっているか いきなり「Strategy パターンを使って」から始めている
数字が入っているか 「速くなりました」だけ。何msから何msか
専門用語を説明なしで使っていないか 相手が別分野の人のこともある
「えーと」「なんか」が多くないか 2回目以降、自然に減ります

90秒の例

弾幕を撃つと、フレームレートが22まで落ちる問題がありました。【困っていたこと・15秒】

まず推測で直そうとしたんですが、 先に測るべきだと思って Profiler を入れました。 そうしたら、描画ではなく Shot 関数に 0.42ms かかっていて、 毎フレーム弾を生成・破棄しているのが原因だと分かりました。【調べ方・20秒】

そこで、起動時に200発ぶん作っておいて、 使い回すオブジェクトプールを作りました。 k2Engine に Activate / Deactivate があったので、 削除する代わりに非アクティブにして、貸出待ちに戻す形にしています。【やったこと・30秒】

結果、Shot 関数が 0.03ms になって、 1000発出しても60FPSを維持できるようになりました。【結果・15秒】

ただ、使っていない弾もメモリを占有し続けるので、 プールのサイズをどう決めるかは、まだ勘で決めています。【残った課題・10秒】

「まず推測で直そうとした」を入れているところ 失敗を1つ挟むと、話に厚みが出ます。

「最初から正しくやりました」より、 「間違えて、気づいて、直しました」のほうが信用されます。 実際の仕事も、そういうものだからです。
「残った課題」を必ず入れてください これがあると、自分の成果を客観的に見られる人だと伝わります。

そして面接官が次の質問をしやすくなります。 会話が続くほうが、印象は良くなります。

演習3（確かめる）

他人のPCで、自分のゲームを動かす。手順書だけ渡して、何も説明せずに遊んでもらう。

解答例を見る（まず自分でやってから）

これは、想像よりずっと重要な演習です。

よく見つかること

見つかること頻度
そもそも起動しないかなり多い
Assets が無くて落ちる多い
操作が分からない非常に多い
ゲームパッドが無いと遊べない多い
解像度が合わない／画面外に出るたまに
最初のステージが難しすぎるほぼ必ず

配布物のチェックリスト

□ Release ビルドである
□ Assets フォルダが入っている
□ dxcompiler.dll / dxil.dll など、必要な DLL が入っている
□ 絶対パス（C:\Users\...）でファイルを読んでいない
□ readme.txt に操作方法が書いてある
□ readme.txt に必要な環境が書いてある
   （Windows 10 以降 / DirectX12 対応GPU / VC++ 再頒布パッケージ）
□ ゲームパッドが無くてもキーボードで遊べる
□ 素材のクレジットを書いた
□ 解凍してすぐ exe をダブルクリックで動く

渡し方

MyGame_v1.0.zip
├ MyGame.exe
├ readme.txt          ← 操作方法・必要環境
├ CREDITS.txt         ← 素材の出どころ
├ Assets/
└ (必要な dll)
説明せずに渡してください 横で「あ、そこはこう操作するんだけど」と言った瞬間に、 この演習の意味が消えます。

面接官は、あなたが横にいない状態で動かすかもしれません。 readme.txt だけで伝わるかを試すのが目的です。

遊んでもらったら、聞くこと

  • 最初の30秒で、何をすればいいか分かったか
  • どこで詰まったか
  • いちばん面白かったところはどこか
  • やめようと思ったのはいつか
最後の質問が、いちばん残酷で、いちばん役に立ちます 自分が時間をかけた部分と、 遊ぶ人が面白いと感じる部分は、たいてい一致しません。

それを知ってから作るかどうかで、次の作品が変わります。

09LV4 を終えて

できるようになったこと章
自分のコードの問題を、言葉にできる 4-01、 4-04
変更に強い形で書ける 4-05〜 4-11
動いているコードを、壊さずに作り替えられる 4-13、 4-16
人と一緒に作れる 4-15
判断の理由を説明できる この章

LV4 で一貫して聞いてきたのは 「なぜそう書いたのか」という問いでした。

次は LV5 です LV4 の判断基準は「読みやすさ」と「変更しやすさ」でした。
LV5 の判断基準は「速さ」です。 そしてこの2つは、しばしば対立します。

LV4 できれいに分けたコードが、 LV5 では「遅い原因」として出てきます。
どちらが正しいという話ではありません。 両方を知ったうえで、場面ごとに選べるようになるのが目標です。
