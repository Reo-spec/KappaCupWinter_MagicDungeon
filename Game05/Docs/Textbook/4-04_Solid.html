LV4 設計 ／ 4-04

SOLID原則で自分のコードを点検する

難易度 ／ 前提 4-03

01この章でできるようになること

  • 5つの原則を、自分のコードに当てて点検できる
  • 原則の名前を、面接で説明できる
  • ただし原則に従いすぎると逆効果だと知っている
原則は「守るもの」ではなく「点検する道具」です 全部きれいに守ったコードが、いちばん良いとは限りません。 この章は「自分のコードのどこが危ういか」を言葉にするために読んでください。

025つの原則

記号名前ひとことで
S単一責任（SRP） 1つのクラスは、1つの理由でだけ変わる
O開放閉鎖（OCP） 機能追加のとき、既存のコードを書き換えない
Lリスコフの置換（LSP） 子は、親のふりをしてもおかしくないこと
Iインターフェース分離（ISP） 使わない関数を、実装させられない
D依存性逆転（DIP） 具体ではなく、抽象に依存する

いちばん効くのは S と D です。 残りは、この2つを意識していると自然に付いてきます。

03S ― 単一責任

「1つのことだけやる」とよく説明されますが、 正確には「変更理由が1つ」です。 

// Player が抱えているもの
class Player : public IGameObject {
    void Update() override
    {
        Move();           // 入力と移動
        Shot();           // 弾を撃つ
        UpdateAnim();     // アニメーション
        CheckHit();       // 当たり判定
        UpdateUi();       // HPバーの更新
        PlaySe();         // 効果音
    }
};

このクラスが書き換わる理由は、6つあります。

こうなったらPlayer を触ることになる
操作性を変えたいはい
弾の仕様を変えたいはい
UIのデザインを変えたいはい（おかしい）
効果音を差し替えたいはい（おかしい）

UIのデザインを変えるのに Player.cpp を開く、 というのが不自然だと感じられれば、それが SRP の感覚です。

分け方は 4-07、 つなぎ方は 4-08 でやります。

04O ― 開放閉鎖

// 敵を増やすたびに、この switch を書き換える
void Spawner::Spawn(int type)
{
    switch (type) {
    case 0: NewGO<ZakoEnemy>(...);    break;
    case 1: NewGO<ShooterEnemy>(...); break;
    case 2: NewGO<TankEnemy>(...);    break;
    // ★ 敵が増えるたび、ここに1行足す
    }
}

「機能追加には開いていて、変更には閉じている」のが理想です。 新しい敵を足すのに既存のファイルを触らずに済む形にできる、 ということです。

やり方は 4-10 でやります。

switch が常に悪いわけではありません 敵の種類が3つで、これ以上増えないと分かっているなら、 switch のほうが読みやすいです。
「この先も増え続けるか」で判断してください。

05L ― リスコフの置換

親として扱ったとき、子がおかしな振る舞いをしないこと。 

class Enemy {
public:
    virtual void Damage(int amount) { m_hp -= amount; }
};

// 無敵の敵を作りたくて…
class InvincibleEnemy : public Enemy {
public:
    void Damage(int amount) override
    {
        // 何もしない
    }
};

一見よさそうですが、呼び出し側がこう書いていたら困ります。 

enemy->Damage(10);
if (enemy->GetHp() <= 0) {
    AddScore(100);
}
// ★ 無敵の敵には、永遠にスコアが入らない
// ★ 「倒すまでループ」を書いていたら、無限ループ
見分け方：子クラスの override が「何もしない」なら赤信号 「この機能だけは使えません」という子は、 たいてい親が間違っています。
無敵かどうかは、継承ではなくフラグやコンポーネントで表すべきです。

06I ― インターフェース分離

// 全部入りのインターフェース
class IEnemy {
public:
    virtual void Move() = 0;
    virtual void Shot() = 0;        // ★ 撃たない敵も実装させられる
    virtual void Talk() = 0;        // ★ 喋らない敵も実装させられる
};

class ZakoEnemy : public IEnemy {
    void Move() override { ... }
    void Shot() override {}         // ★ 空っぽ
    void Talk() override {}         // ★ 空っぽ
};

空の実装が並び始めたら、インターフェースが大きすぎる合図です。 小さく分けます。 

class IMover   { public: virtual void Move() = 0; };
class IShooter { public: virtual void Shot() = 0; };

// 撃つ敵だけ、両方持つ
class ShooterEnemy : public IMover, public IShooter { ... };

あるいは 4-03 のように、 部品として持たせるほうが素直なことも多いです。

07D ― 依存性逆転

5つのなかで、いちばん効きます。 

// 具体に依存している
class Player {
    void Damage(int amount)
    {
        m_hp -= amount;
        FindGO<HpBar>("hpBar")->SetHp(m_hp);        // ★ HpBar を知っている
        FindGO<SoundManager>("sound")->Play("hit"); // ★ SoundManager を知っている
    }
};

Player が、UIと音のクラスを知ってしまっています。 こうなると：

  • HpBar の名前を変えると Player が壊れる
  • Player だけをテストできない （UIも音も用意しないと動かない）
  • UIのないシーンで Player を使うと落ちる
// 抽象に依存する
class IDamageListener {
public:
    virtual ~IDamageListener() {}
    virtual void OnDamaged(int hp) = 0;
};

class Player {
public:
    void AddListener(IDamageListener* l) { m_listeners.push_back(l); }

    void Damage(int amount)
    {
        m_hp -= amount;
        for (auto* l : m_listeners) {
            l->OnDamaged(m_hp);        // ★ 相手が誰かは知らない
        }
    }
private:
    std::vector<IDamageListener*> m_listeners;
};

これが 4-08 Observer です。 Player は「誰かに知らせる」ことだけを知っていて、 相手が UI なのか音なのかを知りません。

「逆転」の意味 ふつうは 上位（Player）が下位（HpBar）を呼ぶので、 上位が下位を知っています。
インターフェースをはさむと、下位が上位の決めた形に合わせる 形になります。依存の向きが逆になるので「逆転」です。

08やりすぎの害

原則を守るほど、ファイルとクラスが増えます。

やりすぎると何が起きるか
クラスを細かく分けすぎる 1つの処理を追うのに10ファイル開く
何にでもインターフェースを付ける 実装が1つしかない IXxx が量産される
将来を見越して抽象化する その将来は、たいてい来ない
判断のしかた 「実際に2回目の変更が来てから、抽象化する」 くらいで、ちょうどよいです。
1回目はコピペで構いません。 2回目に「またか」と思ったら、そこが抽象化どきです。

09演習

演習1（点検する）

自分の Player クラスが書き換わる理由を、思いつくだけ書き出す。いくつあったか。

演習2（説明する）

5つの原則を、自分のコードの例を使って説明する文章を書く。1つにつき3行程度。面接で使えます。

解答例を見る（まず自分でやってから）

教科書の例ではなく自分のコードを引くのが要点です。 「読んだことがある」と「やったことがある」は、聞けば分かります。

書き方の例

== S（単一責任） ==
自分の Player は Update に移動・射撃・UI更新・効果音が入っていて、
書き換わる理由が6つありました。UIのデザインを変えるのに
Player.cpp を開くのが不自然だと気づいて、Observer で分けました。

== O（開放閉鎖） ==
敵を追加するたびに Spawner の switch に1行足していました。
Factory に登録する形にしたので、いまは敵のファイルを追加するだけで、
Spawner は触らずに済みます。

== L（リスコフの置換） ==
無敵の敵を InvincibleEnemy として Damage を空 override していました。
「倒したらスコア加算」のコードが動かなくなったので、
継承ではなく無敵フラグで表すように直しました。

== I（インターフェース分離） ==
IEnemy に Move/Shot/Talk を全部入れていたので、
雑魚敵に空の Shot() と Talk() が並んでいました。
IMover と IShooter に分けて、必要なものだけ実装するようにしました。

== D（依存性逆転） ==
Player が FindGO<HpBar> を直接呼んでいました。
IDamageListener をはさんだので、Player は相手が誰かを知りません。
おかげで UI の無いテスト用シーンでも Player が動くようになりました。
面接で強いのは「失敗した話」です 「こう書いて、こう困って、こう直した」という順で話せると、 実際に手を動かしたことが伝わります。

逆に「SOLIDとは〜という原則です」という説明だけだと、 本で読んだだけと区別が付きません。

4-17 で、これをポートフォリオに使います。 いま書いたものは、消さずに取っておいてください。

演習3（探す）

自分のコードからLSP に違反している場所を探す。（ヒント：中身が空の override）本文には答えがありません。

解答例を見る（まず自分でやってから）

探し方

Ctrl+Shift+F で override を検索し、 中身が空か、1行だけのものを見ていきます。

見つかりやすいパターン違反かどうか
void Update() override {} 違反ではない。「何もしない」が正しい動作
void Damage(int) override {} 違反。ダメージを与えたのに何も起きない
void Shot() override {}（撃たない敵） ISP の問題。インターフェースが大きすぎる
void Save() override { assert(false); } 明確な違反。親として使えない

もうひとつの見つけ方：呼び出し側の if

// これも LSP 違反のにおい
for (auto* enemy : enemies) {
    if (enemy->GetType() == enType_Boss) {
        // ボスだけ特別扱い
    } else {
        enemy->Damage(10);
    }
}

「親として扱えるはずなのに、子の種類で分岐している」 ―― これは、親の設計が合っていない合図です。

直し方の方向

症状方向
一部の子が、ある機能を持たない その機能を別のインターフェースに分ける
一部の子だけ振る舞いが違う 継承ではなくデータ（フラグ・パラメータ）で表す
呼び出し側が種類で分岐している 分岐の中身を仮想関数にして子に持たせる
見つからなくても、それでよいです LSP 違反は、継承を深くしていないと起きにくいものです。

4-03 のとおり「持つ」で書いていれば、 そもそもこの問題は発生しません。 見つからなかったなら、それは良い知らせです。

10確認

  1. SRP の「1つの責任」とは、正確には何のこと？
  2. LSP 違反を見つけるいちばん簡単な手がかりは？
  3. DIP の「逆転」とは、何の向きが逆になる？
  4. 抽象化するタイミングの目安は？
答え
  1. 変更理由が1つであること。
  2. 中身が空の override。 また、呼び出し側が子の種類で分岐していること。
  3. 依存の向き。上位が下位を知るのではなく、 下位が上位の決めた形に合わせる。
  4. 2回目の変更が来てから。1回目はコピペでよい。
