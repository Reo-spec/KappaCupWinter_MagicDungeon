LV5 最適化 ／ 5-15

ビルド時間を短くする

難易度 ／ 前提 1-13

01この章でできるようになること

  • ビルドを待つ時間を、半分にできる
  • ヘッダの書き方が、ビルド時間を決めることが分かる
  • 効果を数字で測れる
これは「実行速度」ではなく「開発速度」の最適化です 1回2分のビルドを、1日30回やれば1時間です。
それが1分になれば、毎日30分が手に入ります。
LV5 の中で、いちばん確実に元が取れる章かもしれません。

02まず測る

ビルド時間も、推測ではなく計測です。 

ツール → オプション → プロジェクトおよびソリューション → VC++ プロジェクトの設定
  → ビルドのタイミング → はい

ビルド後、出力ウィンドウにファイルごとの時間が出ます。 

1>  Player.cpp     (2.104 秒)
1>  Enemy.cpp      (1.982 秒)
1>  GameScene.cpp  (8.441 秒)     ← 遅い
1>  Bullet.cpp     (1.877 秒)

もっと詳しく見るなら： 

プロパティ → C/C++ → コマンドライン → 追加オプション
  /d1reportTime

「どのヘッダの解析に何秒かかったか」まで出ます。

03なぜ遅いのか ― ヘッダは何度も読まれる

Player.cpp     → #include "Enemy.h" → #include <vector> → ...
Enemy.cpp      → #include "Player.h" → #include <vector> → ...
GameScene.cpp  → 両方 → ...

.cpp ごとに、インクルードしたヘッダが 全部展開されます。 100個の .cpp があれば、同じヘッダが100回解析されます。 

// 前処理後のサイズを見てみる
プロパティ → C/C++ → プリプロセッサ → ファイルの前処理 → はい (/P)

.i ファイルができます。 数行の .cpp が、数万行になっていることがあります。

<windows.h> は特に巨大です 単体で数万行あります。
<vector> や <string> も、 テンプレートなのでヘッダに全部書いてあります。

04対策1 ― プリコンパイル済みヘッダ（pch）

k2Engine では、すでに使われています。 Game/stdafx.h がそれです。

「めったに変わらないヘッダを、あらかじめ解析しておく」 仕組みです。 

// stdafx.h
#pragma once

#include <windows.h>
#include <vector>
#include <string>
#include <memory>
#include "k2EngineLowPreCompile.h"
#include "k2EnginePreCompile.h"
pch に入れるもの入れてはいけないもの
標準ライブラリ 自分が編集中のヘッダ
Windows SDK Player.h など、ゲームのクラス
エンジンのヘッダ—
外部ライブラリ—
pch に自分のヘッダを入れると、逆効果です Player.h を1文字直すたびに、 pch が作り直され、全ファイルが再ビルドされます。
これが「フルビルドが毎回走る」の、いちばんの原因です。

05対策2 ― 前方宣言

// ★ 遅い：ヘッダで include している
// Enemy.h
#pragma once
#include "Player.h"            // ★ Enemy.h を読む人全員が Player.h を読む

class Enemy : public IGameObject {
    void ChaseTo(Player* p);
};
// ○ 速い：前方宣言
// Enemy.h
#pragma once

class Player;                  // ★ 「そういうクラスがある」とだけ伝える

class Enemy : public IGameObject {
    void ChaseTo(Player* p);   // ★ ポインタなら、中身を知らなくてよい
};

// Enemy.cpp
#include "stdafx.h"
#include "Enemy.h"
#include "Player.h"            // ★ 実際に使うのは .cpp だけ
使い方前方宣言で足りる？
Player*（ポインタ）足りる
Player&（参照）足りる
引数・戻り値の型足りる
Player m_player;（実体） 足りない。サイズが要る
継承する足りない
メンバを呼ぶ足りない
「ヘッダでは include しない」を基本にしてください ヘッダに書く #include は、 本当に必要なものだけ。
残りは .cpp に書く。

これだけで、ビルド時間が半分になることもあります。

07演習

演習1（測る）

ビルドのタイミングを有効にして、フルビルドの時間を測る。いちばん遅い .cpp はどれか。

演習2（設定する）

/MP が有効か確認する。無効なら有効にして、ビルド時間を比べる。

解答例を見る（まず自分でやってから）

確認と設定

プロジェクトを右クリック → プロパティ
  → 構成プロパティ → C/C++ → 全般
  → 「マルチプロセッサによるコンパイル」→ はい (/MP)

Debug と Release、両方の構成で設定してください。 （構成のドロップダウンで「すべての構成」を選ぶと一度で済みます）

効果の例（8コア）

== フルビルド ==
/MP なし     : 2分 48秒
/MP あり     :    41秒       ← 4.1倍
コア数ぶんそのまま速くはなりません リンクは並列化できません。 また、ファイルごとの時間がばらばらなので、 最後の1つを待つ時間が出ます。

それでも 3〜4倍は期待できます。
/Gm（最小リビルド）とは同時に使えません 古いプロジェクトだと /Gm が有効なことがあります。 警告が出たら、/Gm を無効にしてください。 

C/C++ → コード生成 → 最小リビルドを有効にする → いいえ (/Gm-)
/Gm は非推奨になっており、/MP のほうが はるかに効果があります。

ついでに確認しておくとよい設定

設定場所おすすめ
マルチプロセッサコンパイルC/C++ → 全般 はい
最小リビルドC/C++ → コード生成いいえ
プリコンパイル済みヘッダーC/C++ → プリコンパイル済みヘッダー 使用（/Yu）
インクリメンタルリンクリンカー → 全般 Debug は「はい」
デバッグ情報の生成リンカー → デバッグ Release でも「はい」（5-14）

演習3（減らす）

ヘッダの #include を、前方宣言に置き換える。5つ以上やって、ビルド時間を比べる。

解答例を見る（まず自分でやってから）

手順

  1. フルビルドの時間を記録する
  2. すべての .h を開いて、#include を見る
  3. ポインタ・参照でしか使っていないものを前方宣言に
  4. その #include を .cpp に移す
  5. ビルドが通ることを確認
  6. また測る

置き換えの例

// Enemy.h（前）
#pragma once
#include "Player.h"
#include "Bullet.h"
#include "BulletPool.h"
#include "GameScene.h"
#include "EffectManager.h"

class Enemy : public IGameObject {
public:
    void ChaseTo(Player* target);
    void SetPool(BulletPool* pool);
private:
    BulletPool*    m_pool = nullptr;
    GameScene*     m_scene = nullptr;
};
// Enemy.h（後）
#pragma once

class Player;
class BulletPool;
class GameScene;

class Enemy : public IGameObject {
public:
    void ChaseTo(Player* target);
    void SetPool(BulletPool* pool);
private:
    BulletPool*    m_pool = nullptr;
    GameScene*     m_scene = nullptr;
};
// Enemy.cpp
#include "stdafx.h"
#include "Enemy.h"
#include "Player.h"           // ★ 実際に使うのはここ
#include "BulletPool.h"
#include "GameScene.h"
#include "EffectManager.h"

効果の例

== フルビルド（/MP あり）==
前方宣言なし   : 41秒
5ファイル修正  : 34秒
全ファイル修正 : 22秒        ← 46%減

== 1ファイル変更後のビルド ==
前            : 18秒
後            :  4秒        ← こちらのほうが効く
2つめの数字のほうが、日常では効きます フルビルドは1日数回ですが、 1ファイル直してビルドは1日何十回もやります。

ヘッダの include を減らすと、 「そのヘッダを直したときに再ビルドされるファイル」が減ります。

これが「依存を減らす」ことの、目に見える効果です。
前方宣言できないもの 
class Player;

class Enemy {
    Player m_player;        // ★ 実体はダメ。サイズが分からない
    std::vector<Player> v;  // ★ これもダメ
};
std::unique_ptr<Player> は、 宣言だけならできますが、デストラクタを .cpp に 書く必要があります。

迷ったら、ビルドエラーを見て判断してください。 「不完全な型は使用できません」と出たら、include が必要です。
LV4 の設計とも、つながっています 「ヘッダで include が多い」＝「そのクラスが多くを知りすぎている」 ということです。

4-04 の D（依存性逆転）や、 4-08 の Observer は、 この依存を減らす手段でもあります。

設計が良くなると、ビルドも速くなる。 これは偶然ではありません。

08確認

  1. ヘッダが何度も解析されるのはなぜ？
  2. pch に入れてはいけないものは？
  3. 前方宣言で足りるのは、どんな使い方？
  4. 設定1つでいちばん効くのは？
答え
  1. .cpp ごとに独立して展開されるから。 100個の .cpp があれば100回解析される。
  2. 自分が編集中のヘッダ。 変えるたびに pch が作り直され、全ファイル再ビルドになる。
  3. ポインタ、参照、引数や戻り値の型として使う場合。
  4. マルチプロセッサコンパイル（/MP）。
