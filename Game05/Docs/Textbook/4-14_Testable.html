テストしやすい設計

難易度 ／ 前提 4-13

01この章でできるようになること

  • 動作確認を、毎回手でプレイしなくて済むようにできる
  • テストしやすい形と、しにくい形の違いが分かる
  • ゲームで、どこまでテストすべきか判断できる

02ゲームのテストは難しい

正直に言っておきます。 ゲームは、自動テストが書きにくい分野です。

テストしにくい理由説明
「面白いか」は測れない これは人間がやるしかない
見た目が正しいか測れない 絵が出ているかは、目で見るしかない
状態が多い フレーム、入力、乱数の組み合わせ
エンジンに依存している DirectXの初期化が必要
だからこそ、テストできる部分を切り分ける価値があります 「ダメージ計算」「スコア計算」「弾の軌道」「当たり判定」は、 エンジンが無くても動くはずの処理です。
そこだけでも切り出せれば、確認が一瞬で終わります。

03テストしやすい形とは

しにくいしやすい
void Update()（引数なし・戻り値なし） int CalcDamage(int atk, int def)
中で FindGO / GetInstance を呼ぶ 必要なものを引数で受け取る
中で g_gameTime を読む dt を引数で受け取る
中で rand() を呼ぶ 乱数を引数で受け取る
描画や音を出す値を返すだけ

まとめると「入力を引数で受け取り、結果を戻り値で返す関数」が いちばんテストしやすい形です。 

// テストしにくい
void Player::Damage(int amount)
{
    m_hp -= amount * (100 - m_defense) / 100;
    if (m_hp < 0) { m_hp = 0; }
    SoundManager::GetInstance()->Play("damage");
}

// 計算だけ切り出す
namespace GameRule {
    /// <summary>防御力を考慮したダメージを計算する。</summary>
    int CalcDamage(int attack, int defense)
    {
        int d = attack * (100 - defense) / 100;
        return (d < 1) ? 1 : d;         // 最低1は入る
    }
}

void Player::Damage(int amount)
{
    m_hp -= GameRule::CalcDamage(amount, m_defense);
    if (m_hp < 0) { m_hp = 0; }
    SoundManager::GetInstance()->Play("damage");
}
これだけで、テストできる範囲ができました CalcDamage() は、DirectXもゲームオブジェクトも要りません。 ただの関数なので、どこからでも呼べます。

04手軽な始め方 ― テスト用のパネル

テストフレームワークを導入する前に、これを試してください。 F1 のデバッグパネルに、確認を並べるだけです。 

// TestPanel.cpp
namespace {

struct TestResult {
    const char* name;
    bool        passed;
};

std::vector<TestResult> g_results;

void Check(const char* name, bool condition)
{
    g_results.push_back({ name, condition });
}

void RunAllTests()
{
    g_results.clear();

    // ダメージ計算
    Check("防御0なら、そのまま入る",      GameRule::CalcDamage(100, 0) == 100);
    Check("防御50なら、半分",             GameRule::CalcDamage(100, 50) == 50);
    Check("防御100でも、最低1は入る",     GameRule::CalcDamage(100, 100) == 1);
    Check("攻撃0でも、最低1は入る",       GameRule::CalcDamage(0, 0) == 1);

    // スコア計算
    Check("コンボ1倍",  GameRule::CalcScore(100, 1) == 100);
    Check("コンボ10倍", GameRule::CalcScore(100, 10) == 1000);

    // 当たり判定
    Check("重なっていれば当たる",
        GameRule::IsHit({0,0,0}, 10.0f, {5,0,0}, 10.0f) == true);
    Check("離れていれば当たらない",
        GameRule::IsHit({0,0,0}, 10.0f, {100,0,0}, 10.0f) == false);
    Check("ちょうど接しているときは当たる",
        GameRule::IsHit({0,0,0}, 10.0f, {20,0,0}, 10.0f) == true);
}

void DrawTestPanel()
{
    if (ImGui::Button(U8("テストを実行"))) {
        RunAllTests();
    }

    int ng = 0;
    for (const auto& r : g_results) {
        if (!r.passed) { ng++; }
    }

    if (g_results.empty()) {
        ImGui::TextDisabled(U8("まだ実行していません"));
    } else if (ng == 0) {
        ImGui::TextColored(ImVec4(0.3f, 0.9f, 0.4f, 1.0f),
            U8("全部 OK （%d件）"), (int)g_results.size());
    } else {
        ImGui::TextColored(ImVec4(1.0f, 0.4f, 0.4f, 1.0f),
            U8("%d件 失敗 / %d件中"), ng, (int)g_results.size());
    }

    ImGui::Separator();
    for (const auto& r : g_results) {
        if (r.passed) {
            ImGui::TextColored(ImVec4(0.3f, 0.9f, 0.4f, 1.0f), "OK  ");
        } else {
            ImGui::TextColored(ImVec4(1.0f, 0.4f, 0.4f, 1.0f), "NG  ");
        }
        ImGui::SameLine();
        ImGui::TextUnformatted(U8(r.name));
    }
}

}  // namespace

void RegisterTestPanel()
{
    nsDbg::DebugGui::RegisterPanel(U8("テスト"), DrawTestPanel);
}
これで充分、価値があります ダメージ計算を変えたあと、 ボタンを1回押すだけで確認が終わります。
手でプレイして「だいたい合ってそう」と確認するより、 ずっと速くて確実です。

05境界値を試す

バグは、真ん中ではなく端っこに出ます。

試すべき値例
0攻撃力0、HP0、敵0体
1残機1、コンボ1
最大値HP満タン、コンボ上限
最大値+1上限を超えたとき
マイナスありえないはずの値
ちょうど境界半径の和とぴったり同じ距離

「ちょうど接しているとき、当たる？ 当たらない？」 — この手の質問に、コードを見ずに答えられますか。 答えられないなら、テストを書く価値があります。

06どこまでやるか

対象テストする？
計算（ダメージ、スコア、当たり判定） する。いちばん効く
データの読み込み（4-10） する。壊れたファイルで落ちないか
状態遷移（4-05） 余裕があれば
描画しない。目で見る
操作感しない。遊んで決める
面白さしない。人に遊んでもらう
テストを書くこと自体が目的にならないように 学生作品で、カバレッジ100%を目指す必要はまったくありません。
「何度も手で確認していて、面倒だと感じたところ」 だけテストにしてください。それが正しい判断基準です。

07本格的にやるなら

Visual Studio には、テスト用のプロジェクトを作る機能があります。

やり方手間備考
デバッグパネル小 まずこれ
ネイティブ単体テストプロジェクト中 VS標準。テストエクスプローラーで動かせる
Google Test大 業界標準。導入にひと手間かかる
テストプロジェクトを作るときの注意 テスト対象の .cpp が、 エンジンに依存していないことが条件です。
GameRule.cpp のような 「純粋な計算だけのファイル」を作っておけば、 テストプロジェクトから簡単に参照できます。
逆に Player.cpp をテストしようとすると、 エンジン全体をリンクすることになり、たいてい挫折します。

08演習

演習1（切り出す）

GameRule という名前空間を作って、ダメージ計算・スコア計算・当たり判定をそこに移す。エンジンに一切依存しない形で。

演習2（パネルを作る）

テストパネルを作って、境界値を含めて10個以上の確認を並べる。

解答例を見る（まず自分でやってから）

GameRule.h（エンジンに依存しないこと）

#pragma once

// ★ k2Engine のヘッダをインクルードしない
//    Vector3 だけは使いたいので、最小限の構造体を自前で持つか、
//    引数を float で受け取る形にする

namespace GameRule {

/// <summary>防御力を考慮したダメージ。最低1。</summary>
int CalcDamage(int attack, int defense);

/// <summary>コンボ倍率をかけたスコア。</summary>
int CalcScore(int baseScore, int combo);

/// <summary>円どうしが重なっているか。接している場合も true。</summary>
bool IsHitCircle(float ax, float ay, float ar,
                 float bx, float by, float br);

/// <summary>残り時間からボーナスを求める。</summary>
int CalcTimeBonus(float remainSec);

}  // namespace GameRule
// GameRule.cpp
#include "GameRule.h"

namespace GameRule {

int CalcDamage(int attack, int defense)
{
    if (defense >= 100) { return 1; }
    if (defense < 0)    { defense = 0; }

    int d = attack * (100 - defense) / 100;
    return (d < 1) ? 1 : d;
}

int CalcScore(int baseScore, int combo)
{
    if (combo < 1) { combo = 1; }
    return baseScore * combo;
}

bool IsHitCircle(float ax, float ay, float ar,
                 float bx, float by, float br)
{
    float dx = bx - ax;
    float dy = by - ay;
    float distSq = dx * dx + dy * dy;      // ★ 平方根を取らない
    float rSum   = ar + br;
    return distSq <= rSum * rSum;          // ★ 接している場合も当たり
}

int CalcTimeBonus(float remainSec)
{
    if (remainSec <= 0.0f) { return 0; }
    return (int)(remainSec * 10.0f);
}

}  // namespace GameRule

テスト（境界値を含めて）

void RunAllTests()
{
    g_results.clear();

    //----- ダメージ -----
    Check("防御0 → そのまま",       CalcDamage(100, 0)   == 100);
    Check("防御50 → 半分",          CalcDamage(100, 50)  == 50);
    Check("防御99 → 1",             CalcDamage(100, 99)  == 1);
    Check("防御100 → 最低1",        CalcDamage(100, 100) == 1);
    Check("防御101 → 最低1",        CalcDamage(100, 101) == 1);
    Check("攻撃0 → 最低1",          CalcDamage(0, 0)     == 1);
    Check("防御がマイナス → 0扱い", CalcDamage(100, -50) == 100);

    //----- スコア -----
    Check("コンボ1",      CalcScore(100, 1)  == 100);
    Check("コンボ10",     CalcScore(100, 10) == 1000);
    Check("コンボ0 → 1扱い", CalcScore(100, 0) == 100);
    Check("スコア0",      CalcScore(0, 10)   == 0);

    //----- 当たり判定 -----
    Check("完全に重なる",   IsHitCircle(0,0,10,  0,0,10)   == true);
    Check("少し重なる",     IsHitCircle(0,0,10, 15,0,10)   == true);
    Check("ちょうど接する", IsHitCircle(0,0,10, 20,0,10)   == true);
    Check("わずかに離れる", IsHitCircle(0,0,10, 20.1f,0,10) == false);
    Check("遠い",           IsHitCircle(0,0,10, 100,0,10)  == false);
    Check("斜め方向",       IsHitCircle(0,0,10, 14,14,10)  == true);
    Check("半径0どうし",    IsHitCircle(0,0,0,   0,0,0)    == true);

    //----- タイムボーナス -----
    Check("残り10秒",   CalcTimeBonus(10.0f) == 100);
    Check("残り0秒",    CalcTimeBonus(0.0f)  == 0);
    Check("時間切れ",   CalcTimeBonus(-5.0f) == 0);
}
この作業で、たぶんバグが1つ2つ見つかります 「防御がマイナスのとき」「コンボが0のとき」を 考えていなかった、というのはよくあります。

テストを書くことの半分の価値は、 「書いているうちに、考えていなかったケースに気づく」ことです。
IsHitCircle が平方根を取っていないこと sqrtf() は重い処理です。 距離を比べるだけなら、両辺を2乗したまま比べれば同じ結果になります。

2-15 でも触れましたが、 テストを書くと「最適化しても結果が変わらない」ことを 確認できるようになります。これは LV5 で効いてきます。

演習3（守る）

4-13 のリファクタリングを、テストパネルで確認しながらやってみる。作り替える前と後で、全部のテストが通るか。

解答例を見る（まず自分でやってから）

これが、テストのいちばんの使いどころです。

1. リファクタリング前に、テストを実行 → 全部 OK
2. コードを整理する
3. テストを実行 → 全部 OK なら、動きは変わっていない
4. コミット

4-13 の定義は 「外から見た動きを変えずに、中身を整理すること」でした。 テストは、その「動きを変えていない」を機械的に確かめる道具です。

やってみると分かること

状況意味
全部 OK のまま安心して次に進める
1つ NG になった いま変えたところが原因。範囲が狭いのですぐ見つかる
整理前から NG がある もともとバグがあった。先にそれを直す（別コミットで）
「こまめにビルドする」が、さらに強くなります 4-13 では 「1つ直す → ビルド → 動かす → コミット」と書きました。

テストがあると、この「動かす」が数秒で終わります。 手でプレイして確認していたときと比べて、 リファクタリングの速度が何倍にもなります。

起動時に自動実行しておく

// GameScene.cpp
bool GameScene::Start()
{
#ifdef _DEBUG
    RunAllTests();          // ★ 起動のたびに走る
#endif
    ...
}
// 失敗があったら、目立たせる
void DrawTestPanel()
{
    ...
    if (ng > 0) {
        // 失敗があるときは、パネルを勝手に開く
        ImGui::SetNextWindowFocus();
    }
}

これで「気づいたらテストが壊れていた」を防げます。

テストが邪魔になったら、見直してください 仕様を変えるたびにテストを直すはめになるなら、 そのテストは細かすぎます。

「この挙動は今後も変わらない」と言えるものだけ テストにしてください。

たとえば「防御100でも最低1ダメージ」は仕様です。 「防御50のとき、ちょうど50ダメージ」はバランス調整で変わるかもしれません。 後者は、テストにしないほうが身軽です。

09確認

  1. テストしやすい関数の形は？
  2. ゲームでテストすべきもの、すべきでないものは？
  3. 境界値として試すべき値を3つ。
  4. テストとリファクタリングの関係は？
答え
  1. 入力を引数で受け取り、結果を戻り値で返す。 中で FindGO や rand() を呼ばない。
  2. すべき：計算、データ読み込み。 すべきでない：描画、操作感、面白さ。
  3. 0、1、最大値、最大値+1、マイナス、ちょうど境界。
  4. テストは「動きを変えていない」ことを 機械的に確かめる道具。リファクタリングの安全網になる。
