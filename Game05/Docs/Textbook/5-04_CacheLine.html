02メモリは階層になっている

03キャッシュライン ― なぜ64バイトなのか

CPUは、1バイトだけを運んできたりしません。 必ず64バイトのかたまりで運びます。 このかたまりをキャッシュラインといいます。 

int a = array[0];     // ★ array[0] だけが欲しい

実際には、array[0] から 64バイトぶんが まとめてキャッシュに運ばれます。 int なら 16個ぶんです。 

int sum = 0;
for (int i = 0; i < 16; i++) {
    sum += array[i];    // ★ 1回目だけ遅い。2〜16回目はキャッシュにある
}
これが「連続して並べると速い」の正体です 16個読むのに、メモリアクセスは1回だけ。
バラバラの場所にある16個なら、メモリアクセスは16回です。

なぜ64バイトか — ハードウェアの設計上の決めごとです。 小さすぎると運ぶ回数が増え、大きすぎると無駄が増えます。 x86系では、この20年ほど64バイトで固定されています。

04vector と list の差

std::vector<int> v;     // ★ メモリ上で連続して並ぶ
std::list<int>   l;     // ★ 1個ずつバラバラの場所。ポインタでつながっている
std::vectorstd::list
メモリ配置連続バラバラ
全部なめる速さ速い 10〜50倍遅いことがある
真ん中への挿入（計算量）O(n)O(1)
真ん中への挿入（実測） 要素数が数千までなら、たいてい vector が速い
1要素あたりの余計なメモリ0 前後のポインタで16バイト
計算量だけで選ぶと、間違えます list の挿入は O(1) ですが、 「挿入する場所まで辿る」のに O(n) かかります。 しかも、辿るたびにキャッシュミスします。

vector の挿入は O(n) ですが、 メモリをまとめてずらすだけなので、 CPUがいちばん得意な処理です。

迷ったら vector を使ってください。

05k2Engine を見てみる

k2EngineLow/gameObject/GameObjectManager.h に、こう書いてあります。 

enum { GAME_OBJECT_PRIO_MAX = 255 };

typedef std::list<IGameObject*>  GameObjectList;
std::array<GameObjectList, GAME_OBJECT_PRIO_MAX>  m_gameObjectListArray;

優先度ごとの std::list が、255本。 そして毎フレーム、全部をなめます。 

void GameObjectManager::ExecuteUpdate()
{
    ...
    for (auto& goList : m_gameObjectListArray) {      // ★ 255回
        for (auto& go : goList) {                     // ★ ポインタを辿る
            go->UpdateWrapper();                      // ★ 仮想関数
        }
    }
}
ここで起きていることコスト
空のリストを255本チェックする小さい
list のノードを辿る ノードごとにキャッシュミス
その先の IGameObject 本体へ飛ぶ さらにキャッシュミス
仮想関数を呼ぶvtable を引く
これは「エンジンが悪い」という話ではありません この設計は、途中で DeleteGO しても 安全にループを続けられるなど、扱いやすさのための選択です。 学習用エンジンとして妥当です。

ただし「オブジェクトが数千個になると遅くなる」という性質は持っています。 それを知ったうえで、大量のものは自分で持つ （4-06）という判断ができるのが、 LV5 の力です。

06構造体のサイズを意識する

struct Bad {
    bool  a;      // 1バイト … だが、次が int なので 3バイト詰め物が入る
    int   b;      // 4バイト
    bool  c;      // 1バイト … また 3バイト詰め物
    int   d;      // 4バイト
};                // 合計 16バイト

struct Good {
    int   b;      // 4
    int   d;      // 4
    bool  a;      // 1
    bool  c;      // 1
};                // 合計 12バイト（末尾に2バイト詰め物）

大きい型から順に並べると、隙間が減ります。 1000個持つなら、16KB と 12KB の差になります。 

// 確認するには
printf("Bad  = %zu\n", sizeof(Bad));
printf("Good = %zu\n", sizeof(Good));
効くのは「大量に持つもの」だけです 1個しかないクラスのメンバ順を並べ替えても、意味はありません。
弾、パーティクル、頂点のように、 何千個も並べるものだけ気にしてください。

演習1（測る）

sizeof() で、自分の Bullet やEnemy のサイズを表示する。1000個でどれくらいになるか。

演習2（比べる）

std::vector<int> と std::list<int> に100万個入れて、全部足す時間を比べる。

解答例を見る（まず自分でやってから） 
#include <vector>
#include <list>
#include <chrono>
#include <cstdio>

void CompareVectorList()
{
    const int N = 1000000;

    std::vector<int> v;
    std::list<int>   l;
    v.reserve(N);
    for (int i = 0; i < N; i++) {
        v.push_back(i);
        l.push_back(i);
    }

    using Clock = std::chrono::high_resolution_clock;

    // vector
    auto t0 = Clock::now();
    long long sumV = 0;
    for (int x : v) { sumV += x; }
    auto t1 = Clock::now();

    // list
    long long sumL = 0;
    for (int x : l) { sumL += x; }
    auto t2 = Clock::now();

    auto msV = std::chrono::duration<double, std::milli>(t1 - t0).count();
    auto msL = std::chrono::duration<double, std::milli>(t2 - t1).count();

    char buf[256];
    sprintf_s(buf, "vector : %.3f ms (sum=%lld)\n", msV, sumV);
    OutputDebugStringA(buf);
    sprintf_s(buf, "list   : %.3f ms (sum=%lld)\n", msL, sumL);
    OutputDebugStringA(buf);
    sprintf_s(buf, "list は vector の %.1f 倍\n", msL / msV);
    OutputDebugStringA(buf);
}

典型的な結果（Release）

vector : 0.412 ms (sum=499999500000)
list   : 8.734 ms (sum=499999500000)
list は vector の 21.2 倍

なぜこんなに違うのか

vectorlist
1要素のサイズ4バイト 約32バイト（値4＋前後のポインタ16＋管理）
64バイトに入る個数16個2個
100万個を読むメモリアクセス 約 62,500 回約 500,000 回
配置連続。先読みも効く バラバラ。先読みできない
「先読み（プリフェッチ）」が効くかどうかが、大きい CPUは「連続して読んでいるな」と気づくと、 次に必要になるであろう領域を、勝手に先読みします。

vector はこれが完全に効きます。 list は次のノードの場所が予測できないので、まったく効きません。

表の「62,500回」すら、実際にはほぼ待ち時間ゼロになります。
Debug で測ると差が小さく出ます Debug では vector 側にも範囲チェックなどが入るので、 差が縮まります。

必ず Release で測ってください（5-02）。

演習3（並べ替える）

自分の構造体のメンバの順番を、大きい型から並べ替える。sizeof() がどれくらい減るか。

解答例を見る（まず自分でやってから）

並べ替えの規則

  1. 大きい型から順に並べる（double → ポインタ → int/float → short → char/bool）
  2. bool やフラグは最後にまとめる
  3. それでもサイズが減らなければ、それ以上は無理

例

// 前
struct Particle {
    bool    m_isActive;      // 1  (+3 詰め物)
    Vector3 m_position;      // 12
    bool    m_isFadeOut;     // 1  (+3 詰め物)
    float   m_lifeTime;      // 4
    Vector3 m_velocity;      // 12
    char    m_type;          // 1  (+3 詰め物)
    float   m_scale;         // 4
};
// sizeof = 44
// 後
struct Particle {
    Vector3 m_position;      // 12
    Vector3 m_velocity;      // 12
    float   m_lifeTime;      // 4
    float   m_scale;         // 4
    bool    m_isActive;      // 1
    bool    m_isFadeOut;     // 1
    char    m_type;          // 1  (+1 詰め物)
};
// sizeof = 36

44 → 36。18%減。

10,000個なら  440KB → 360KB
64バイトに入る個数  1.45個 → 1.78個（約22%多く入る）

確認のしかた

// コンパイル時に確認する
static_assert(sizeof(Particle) <= 36, "Particle が大きくなりました");

これを入れておくと、あとでメンバを足したときに気づけます。

やりすぎないでください 並べ替えると、意味的なまとまりが崩れます。

m_isActive と m_lifeTime は 関係が深いのに、離れた場所に置かれることになります。

読みやすさを犠牲にする価値があるのは、 「何千個も並べるもの」だけです。 5-01 のとおり、 まず測って、そこがボトルネックだと分かってからにしてください。
それでもサイズが減らないとき そもそもメンバが多すぎるのかもしれません。

5-06 でやる SoA は、 「必要なメンバだけを別の配列にする」という、 もっと踏み込んだやり方です。

08確認

  1. キャッシュラインは何バイト？ なぜそれが効く？
  2. list が遅い理由を2つ。
  3. k2Engine の ExecuteUpdate() で、 キャッシュミスが起きる箇所は？
  4. 構造体のメンバを並べ替える効果があるのは、どんなとき？
答え
  1. 64バイト。1回のメモリアクセスで、 隣接する複数の要素がまとめて運ばれるから。
  2. ノードがバラバラに配置されてキャッシュに乗らない。 先読みが効かない。1要素あたりのメモリも大きい。
  3. list のノードを辿るところと、 その先の IGameObject 本体へ飛ぶところ。
  4. 何千個も並べて持つとき。1個しかないものでは意味がない。
