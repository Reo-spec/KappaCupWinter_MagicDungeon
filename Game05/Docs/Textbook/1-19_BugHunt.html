LV1 入門 ／ 1-19

制作課題バグ取り演習10本

難易度 ／ 前提 1-18

これが LV1 の関門です 新しいことは学びません。ここまでの18章を使って、 壊れたコードを10本直してください。
デバッガを使って、原因を特定してから直すこと。 当てずっぽうで書き換えて直っても、意味がありません。

01やりかた

  1. コードを読んで、どこがおかしいか予想する
  2. 自分のプロジェクトに書き写して、実際に動かす
  3. デバッガで原因を確かめる
  4. 直す
  5. それから解答例を開く
「探し方」まで読んでください 解答例には、デバッガでどう突き止めるかも書いてあります。 答えそのものより、そちらのほうが大事です。 この先、答えを教えてくれる人はいません。

0210本のバグ

バグ 1 ― 画面に何も出ない

症状：ビルドは通る。実行しても画面に何も出ない。

bool Game::Start()
{
    m_spriteRender.Init("Assets/sprite/player.dds", 64.0f, 64.0f);
    return true;
}

void Game::Update()
{
    m_spriteRender.SetPosition(m_position);
}

void Game::Render(RenderContext& rc)
{
}
解答例を見る（まず自分で直してから）

Render() の中で Draw() を呼んでいません。

void Game::Render(RenderContext& rc)
{
    m_spriteRender.Draw(rc);      // ★ 追加
}

ついでに、Update() で m_spriteRender.Update() も 呼んでいません。両方必要です（2-11）。

探し方：Render() にブレークポイントを置く。 呼ばれてはいるが、中で何もしていないことが分かる。

バグ 2 ― 動かしたのに動かない

症状：ビルドが通らない。あるいは、位置を変えても画面のスプライトが動かない。

void Game::Update()
{
    m_position.x += 2.0f;
    m_spriteRender.Draw(rc);
}
解答例を見る（まず自分で直してから）

2つ問題があります。

  1. Update() には rc という引数がありません。 Draw() は Render() で呼びます
  2. SetPosition() と m_spriteRender.Update() を呼んでいません
void Game::Update()
{
    m_position.x += 2.0f;
    m_spriteRender.SetPosition(m_position);   // ★
    m_spriteRender.Update();                  // ★
}

void Game::Render(RenderContext& rc)
{
    m_spriteRender.Draw(rc);
}

「位置を変えたのに動かない」の9割は m_spriteRender.Update() の呼び忘れです。

バグ 3 ― 1回しか動かない

症状：スプライトが少しずれた位置に出るだけで、動かない。

bool Game::Start()
{
    m_spriteRender.Init("Assets/sprite/player.dds", 64.0f, 64.0f);

    m_position.x += 5.0f;
    m_spriteRender.SetPosition(m_position);
    m_spriteRender.Update();
    return true;
}
解答例を見る（まず自分で直してから）

移動の処理を Start() に書いています。

Start() は最初の1回しか呼ばれません （1-04）。 

bool Game::Start()
{
    m_spriteRender.Init("Assets/sprite/player.dds", 64.0f, 64.0f);
    return true;
}

void Game::Update()          // ★ こちらに移す
{
    m_position.x += 5.0f;
    m_spriteRender.SetPosition(m_position);
    m_spriteRender.Update();
}

探し方： Start() と Update() の両方にブレークポイントを置く。 Start() は1回しか止まらないことが確認できる。

バグ 4 ― HPがマイナスになる

症状：Aボタンを押すと、HPが一瞬でマイナスまで落ちる。

void Game::Update()
{
    if (g_pad[0]->IsPress(enButtonA)) {
        m_hp -= 1;
    }

    wchar_t text[256];
    swprintf_s(text, 256, L"HP %d", m_hp);
    m_fontRender.SetText(text);
}
解答例を見る（まず自分で直してから）

2つ問題があります。

  1. IsPress なので1秒に60回減ります （2-10）
  2. 0で止める処理がありません
void Game::Update()
{
    if (g_pad[0]->IsTrigger(enButtonA)) {   // ★ Trigger にする
        m_hp -= 1;
    }
    if (m_hp < 0) {                         // ★ 下限を作る
        m_hp = 0;
    }
    ...
}

「値には必ず上限と下限を考える」のは、 バグを防ぐいちばん基本の習慣です。

バグ 5 ― 条件が効かない

症状：HPが100あるはずなのに、いつのまにか0になっている。そして m_isAlive は true のまま。

void Game::Update()
{
    if (m_hp = 0) {
        m_isAlive = false;
    }

    wchar_t text[256];
    swprintf_s(text, 256, L"HP %d  alive %d", m_hp, m_isAlive);
    m_fontRender.SetText(text);
}
解答例を見る（まず自分で直してから）

== が = になっています。 （1-08）

if (m_hp = 0)       // m_hp に 0 を代入して、その結果(0=false)で判定
if (m_hp == 0)      // ★ 正しい

何が起きているか

  1. m_hp に 0 が代入される（HPが破壊される）
  2. 代入の結果は 0 ＝ false
  3. だから if の中は実行されず、m_isAlive は変わらない
エラーも警告も出ないことがあります C++でいちばん有名な落とし穴のひとつです。 「なぜか値が書き換わる」ときは、if の中の = を疑ってください。

探し方： m_hp をウォッチに入れて F10 で1行ずつ進める。 if の行を通った瞬間に 0 になるのが見える。

バグ 6 ― ときどきクラッシュする

症状：合計が 150 になるはずなのに、変な数字が出る。ときどきクラッシュする。

void Game::Update()
{
    int scores[5] = { 10, 20, 30, 40, 50 };
    int total = 0;

    for (int i = 0; i <= 5; i++) {
        total += scores[i];
    }

    wchar_t text[256];
    swprintf_s(text, 256, L"total %d", total);
    m_fontRender.SetText(text);
}
解答例を見る（まず自分で直してから）

i <= 5 なので、scores[5] を読んでいます。 配列は [0] 〜 [4] しかありません （1-11）。

for (int i = 0; i < 5; i++) {      // ★ <= ではなく <
    total += scores[i];
}

これを「オフバイワンエラー」と呼びます。 1つだけずれる間違い。ベテランでもやります。

もっと安全な書き方

for (int score : scores) {      // 範囲for なら、そもそも間違えられない
    total += score;
}

探し方： i をウォッチに入れて、ループを回す。 i が 5 のときに scores[i] が おかしな値になっているのが見える。

バグ 7 ― 関数が呼ばれない

症状：ビルドは通る。でも何も動かない。

// Game.h
class Game : public IGameObject
{
public:
    bool Start();
    void Updete();        // ← ここ
    void Render(RenderContext& rc);
};

// Game.cpp
void Game::Updete()
{
    m_position.x += 2.0f;
    ...
}
解答例を見る（まず自分で直してから）

Update が Updete になっています。

エンジンが呼ぶのは Update() です。 Updete() はまったく別の、誰も呼ばない関数として作られました。 

void Update() override;      // ★ override を付ける
override を書いていれば、これは起きません override を付けておくと、 親に Updete という仮想関数が無いのでコンパイルエラーになります （1-16）。
だから override は必ず書いてください。

探し方： Updete() にブレークポイントを置く。一度も止まらない。 「呼ばれていない」と分かれば、名前を疑える。

バグ 8 ― 値を変えたのに反映されない

症状：Aボタンを押しても、HPが減らない。エラーも出ない。

void Game::AddDamage(int hp)
{
    hp -= 10;
}

void Game::Update()
{
    if (g_pad[0]->IsTrigger(enButtonA)) {
        AddDamage(m_hp);
    }

    wchar_t text[256];
    swprintf_s(text, 256, L"HP %d", m_hp);
    m_fontRender.SetText(text);
}
解答例を見る（まず自分で直してから）

値渡しなので、コピーを減らしているだけです。 （1-14）

void Game::AddDamage(int& hp)      // ★ 参照にする
{
    hp -= 10;
}

あるいは、そもそもメンバ変数なので引数が不要です。

void Game::AddDamage(int damage)
{
    m_hp -= damage;                 // ★ 直接メンバを触る
}
...
AddDamage(10);

こちらのほうが素直です。 自分のクラスのメンバなのに、わざわざ引数で受け取る必要はありません。

探し方： AddDamage() に F11 で入る。 中の hp は減るのに、戻ると m_hp が変わっていない のが見える。

バグ 9 ― ゲームが固まる

症状：実行した瞬間、ウィンドウが真っ白になって応答しなくなる。

void Game::Update()
{
    int i = 0;
    while (i < 10) {
        m_position.x += 1.0f;
    }
    ...
}
解答例を見る（まず自分で直してから）

i を増やしていないので、無限ループです。 （1-09）

while (i < 10) {
    m_position.x += 1.0f;
    i++;                     // ★ 追加
}

そもそも、回数が決まっているなら for のほうが安全です。

for (int i = 0; i < 10; i++) {      // 増やし忘れようがない
    m_position.x += 1.0f;
}

探し方： Ctrl+Alt+Break で中断する。 while の中で止まる。ローカルウィンドウで i がずっと 0 のままなのが決定的な証拠。

バグ 10 ― たまにしか落ちない

症状：2秒くらい経つと、落ちることがある。落ちないこともある。別のPCだと必ず落ちる。

// Game.h
private:
    Enemy* m_enemy = nullptr;

// Game.cpp
bool Game::Start()
{
    m_enemy = new Enemy();
    return true;
}

void Game::Update()
{
    if (m_frameCount == 120) {
        delete m_enemy;
    }
    m_frameCount++;

    m_enemy->Update();
}
解答例を見る（まず自分で直してから）

解放したメモリを使い続けています。 （1-15）

delete m_enemy; したあとも、m_enemy には 古いアドレスが残ったままです。 nullptr にはなりません。 

if (m_frameCount == 120) {
    delete m_enemy;
    m_enemy = nullptr;        // ★ 必ずセットで
}
m_frameCount++;

if (m_enemy != nullptr) {     // ★ 使う前に確認
    m_enemy->Update();
}
これが「たまにしか落ちない」理由 解放されたメモリがまだ書き換えられていなければ、何事もなく動いてしまいます。 書き換えられていたら落ちます。
どちらになるかは運です。 自分のPCでは動いて、提出先で落ちる。 これがC++でいちばんやっかいなバグです。

探し方： Debugビルドで m_enemy をウォッチに入れる。 delete のあと、中身が 0xDD だらけになっている。 これが「解放済み」の印です。

この事故は 2-08 で、 もっとじっくり扱います。 そして 2-09 で、 k2Engine での正しい対処法を学びます。

03合格の条件

  • 10本すべてを、自分の手で直した
  • それぞれについて、「なぜそうなるのか」を人に説明できる
  • 少なくとも3本は、解答例を見る前に自力で直せた
  • デバッガのブレークポイント・ウォッチ・コールスタックを実際に使った
全部自力で直せなくても大丈夫です バグ5・8・10 あたりは、経験がないと難しいものです。 解答例を読んで「あぁ、そういうことか」と思えたなら、それで合格です。
大事なのは、次に同じバグに出会ったとき気づけることです。
