LV1 入門 ／ 1-15

new / delete と「所有」

難易度 ／ 前提 1-14

01この章でできるようになること

  • スタックとヒープの違いを説明できる
  • 「誰が解放する責任を持つのか」を考えられる
  • k2Engine では new を直接書かない理由が分かる

02変数が置かれる2つの場所

03new と delete

Enemy* e = new Enemy();     // ヒープに作る
e->TakeDamage(10);          // ポインタなので「->」で使う
delete e;                   // 使い終わったら消す
e = nullptr;                // 消したら nullptr を入れておく
. と -> の使い分け 
Enemy  e;     e.TakeDamage(10);      // 実体なので「.」
Enemy* p;     p->TakeDamage(10);     // ポインタなので「->」
p->x は (*p).x の短い書き方です。 毎回 (*p). と書くのは面倒なので、-> があります。

04消し忘れ ― メモリリーク

void Game::Update()
{
    Enemy* e = new Enemy();      // 毎フレーム作って
    // delete していない！
}

1秒に60個、消えない敵が溜まっていきます。 10分遊べば36000個。やがてメモリを使い切って落ちます。

これをメモリリークと呼びます。 エラーは出ません。ただ、じわじわ重くなって、いつか落ちます。

05二重解放 ― もっと悪い

delete e;
delete e;      // ★ 2回目。クラッシュする

すでに返した場所を、もう一度返そうとする。 メモリリークより危険です。

対策は簡単で、delete したら nullptr を入れることです。 

delete e;
e = nullptr;

delete e;      // nullptr を delete しても、何も起きない（安全）

06「誰が消すのか」を決める

これがこの章でいちばん大事なことです new したものには、必ず「消す係」を1人決めてください。
これを「所有」と言います。
消す係がいない → メモリリーク
消す係が2人いる → 二重解放
決め方例
作った人が消す シーンが敵を作ったなら、シーンが消す
自分で自分を消す 弾が画面外に出たら、自分で消える

どちらでもよいのですが、混ぜてはいけません。 この話は 2-05 でもう一度、 k2Engine の NewGO / DeleteGO を題材にやります。

07k2Engine では new を書きません

ここまで勉強しておいて何ですが、 k2Engine のゲームオブジェクトでは new / delete を 直接書きません。 

// ×  自分で new する
Enemy* e = new Enemy();

// ○  エンジンに頼む
Enemy* e = NewGO<Enemy>(3, "enemy");
...
DeleteGO(e);

NewGO で作ると、エンジンが毎フレーム Update() と Render() を呼んでくれます。 自分で new しても、誰も呼んでくれません。

では、なぜ new を勉強したのか
  • NewGO の中身が new だから。 仕組みが分かっていないと、2-05 が理解できません
  • 「所有」の考え方は、new を使わなくても必要だから
  • ゲームオブジェクト以外では、ふつうに使うから

解答例を見る（まず自分でやってから） 
void Game::Update()
{
    // わざと漏らす（実験が終わったら必ず消すこと）
    Enemy* e = new Enemy();

}

タスクマネージャー（Ctrl+Shift+Esc）で Game.exe のメモリを見ると、じわじわ増え続けます。

Visual Studio も教えてくれます。 Debug ビルドで実行して正常に終了すると、 出力ウィンドウにこう出ることがあります。 

Detected memory leaks!
Dumping objects ->
{1234} normal block at 0x0000023F..., 16 bytes long.
エラーではないので、見逃しがちです メモリリークは、動いている間は何も起きません。 だから気づきにくく、長時間遊んだ人だけが落ちます。

演習3（考える）

次のコードには問題があります。何が起きるか説明してください。
Enemy* a = new Enemy();
Enemy* b = a;
delete a;
b->TakeDamage(10);

解答例を見る（まず自分でやってから）

b は、すでに解放されたメモリを指しています。 

Enemy* a = new Enemy();
Enemy* b = a;             // a と b は「同じ場所」を指している
delete a;                 // その場所を返した
a = nullptr;              // a は安全になった

b->TakeDamage(10);        // ★ b は nullptr ではない。でも指す先は消えている

a = nullptr; と書いても、b は変わりません。 b は別の変数で、古いアドレスをそのまま持ち続けています。

起こりうること

  • クラッシュする
  • 何事もなく動いてしまう（いちばん怖い）
  • あとで、まったく関係ない場所で落ちる
これが「ダングリングポインタ」です C++でいちばん多く、いちばんやっかいなバグです。
2-08 で、 これをわざと起こして、デバッガで追いかけます。 そして 2-09 で、 k2Engine での正しい対処法（GOHandle）を学びます。
いまは「こういう事故がある」と覚えておくだけで充分です。

09確認

  1. スタックとヒープの違いは？
  2. delete を忘れるとどうなる？ エラーは出る？
  3. delete したあとに nullptr を入れるのはなぜ？
  4. k2Engine のゲームオブジェクトは、何で作る？
答え
  1. スタックは { } を抜けると自動で消える。 ヒープは delete するまで残る。
  2. メモリリーク。エラーは出ないが、じわじわ増えていつか落ちる。
  3. 二重解放を防ぐため。nullptr を delete しても安全だから。
  4. NewGO。消すときは DeleteGO。
