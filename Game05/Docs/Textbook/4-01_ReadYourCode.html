01LV4 は何をするところか

LV2 で動くゲームを作りました。 LV3 で見栄えのするゲームにしました。

LV4 でやるのは「壊れにくく作り直す」ことです。 同じゲームを、3回目に作ります。

新しい機能は、ほとんど作りません LV4 で身につくのは「変更に強い書き方」です。
地味です。でも、2か月後の自分が助かるかどうかはここで決まります。

02まず、自分のコードを開いてください

この章に読み物はほとんどありません。 自分が書いたコードを測ることが、この章の中身です。

LV2〜LV3 で作ったゲームの Player.cpp を開いてください。 半年前でなくても構いません。1週間前のコードでも、たいてい忘れています。

03測る ― 4つの数字

測るものやり方ひとつの目安
いちばん長い関数の行数 数える 50行を超えたら黄信号
いちばんメンバ変数が多いクラス .h の private: を数える 15個を超えたら黄信号
if のネストの深さ いちばん深いところ 3段を超えたら黄信号
FindGO を書いた回数 プロジェクト全体で検索 多いほど、つながりが見えにくい
「目安」であって「ルール」ではありません 80行の関数が、いつも悪いわけではありません。 単純な初期化が80行並んでいるだけなら、分ける必要はありません。
数字は「ここを見てみようか」という合図として使ってください。

04嫌なにおい（コードスメル）

「バグではないが、あとで困る書き方」には、名前が付いています。

名前どういうものかあとで何に困るか
長すぎる関数 1つの関数が何もかもやっている 読めない。一部だけ直せない
重複したコード コピペした似たコードが何か所にもある 直すとき、1か所直し忘れる
巨大なクラス 1つのクラスが何もかも持っている どこを触っても、どこかに影響する
マジックナンバー if (m_hp < 30) の 30 何の数字か分からない。変え忘れる
長い引数リスト 引数が6個も7個もある 順番を間違えても、コンパイルが通る
フラグ引数 Attack(true) 呼び出し側を見ても、何が起きるか分からない

いちばん厄介なのは「重複したコード」です。 仕様が変わったとき、3か所のうち2か所だけ直すという事故が起きます。 しかもコンパイルは通るので、気づきません。

05マジックナンバーだけは、いま直せます

ほかのにおいは、この先の章で道具を手に入れてから直します。 マジックナンバーだけは、いますぐ直せます。 

// 直す前
void Player::Update()
{
    if (m_hp < 30) {
        // 何かする
    }
    m_position.x += 300.0f * g_gameTime->GetFrameDeltaTime();

    if (m_shotTimer > 0.15f) { Shot(); }
}
// 直したあと（Player.cpp の先頭あたり）
namespace {
    const int   PINCH_HP        = 30;      // これ以下でピンチ演出
    const float MOVE_SPEED      = 300.0f;  // 1秒あたりの移動量
    const float SHOT_INTERVAL   = 0.15f;   // 連射の間隔（秒）
}

void Player::Update()
{
    if (m_hp < PINCH_HP) {
        // 何かする
    }
    m_position.x += MOVE_SPEED * g_gameTime->GetFrameDeltaTime();

    if (m_shotTimer > SHOT_INTERVAL) { Shot(); }
}
無名 namespace に置く理由 namespace { ... } の中に書くと、 その .cpp の中だけで見える定数になります。
別のファイルの同じ名前とぶつかりません。 static const と書くのと同じ効果ですが、こちらが今の書き方です。

いちばんの効果は、調整が速くなることです。 数字が先頭に並んでいれば、 ゲームバランスを触るときに Update() を読み返さずに済みます。

自分のコードの4つの数字を測って、メモに書き出す。4-16 で、もう一度測って比べます。

解答例を見る（まず自分でやってから）

数え方（Visual Studio）

測るものやり方
関数の行数 関数の頭と終わりで、左下に出る行番号の差を見る
メンバの数.h を開いて m_ を数える
FindGO の回数 Ctrl+Shift+F で FindGO< をソリューション全体検索。 結果の件数が出ます

数字が悪くても、落ち込まないでください ここで数字が良い人は、LV4 を読む必要がありません。 悪いほど、これから伸びる幅が大きいというだけです。

プロが書いたコードにも、同じにおいはあります。 違うのは「におうと分かっていて、いつ直すか決めている」ことです。

演習2（探す）

自分のコードからマジックナンバーを10個見つけて、名前の付いた定数に置き換える。

解答例を見る（まず自分でやってから）

探し方のコツ

  • if の右側に出てくる数字
  • < > の隣の数字
  • 0.0f 1.0f 以外の小数
  • 配列のサイズ

置き換えなくてよいもの

そのままでよい理由
0 1 -1 意味が自明。i < 0 を定数にしても読みにくくなるだけ
2.0f（半分にする割り算など） 数式の一部として読める
1.0f / 60.0f そう書いてあるほうが分かりやすい

やりすぎた例

const int ZERO = 0;              // ★ これは意味がない
const float HALF = 0.5f;         // ★ これも微妙
if (m_hp < ZERO) { ... }

判断のしかた：「この数字を後で変えたくなるか？」 変えたくなるなら定数に、変えないなら数字のままで構いません。

名前を付けられない数字は、要注意です if (m_timer > 2.7f) の 2.7 に 名前を付けようとして、思いつかないことがあります。

それは「自分でも、なぜその値なのか分かっていない」という合図です。 コメントに「試して、これがいちばん良かった」とだけでも書いてください。

演習3（数える）

同じような処理が2回以上書かれている場所を探す。直さなくてよい。どこにあるかだけ、メモしておく。

解答例を見る（まず自分でやってから）

シューティングでよくある重複

重複しがちな場所効く章
プレイヤーの弾と、敵の弾 4-09
敵A・敵B・敵Cの、ほぼ同じ Update() 4-03、 4-09
画面外に出たら消す処理（各所にコピペ） 4-07
当たり判定（距離を計算する数行） 関数に切り出すだけでよい
スコア加算のたびの FindGO<Score> 4-08
敵の種類ごとの switch 4-10

探し方：コピペした記憶をたどる

「あのクラスをコピーして作ったな」と覚えている場所が、 たいてい重複しています。 検索より記憶のほうが速いです。

メモの書き方

== 重複メモ ==
1. Enemy.cpp / Enemy2.cpp / Boss.cpp の Move()
   → ほぼ同じ。速度が違うだけ
2. Bullet.cpp / EnemyBullet.cpp
   → 当たる相手が違うだけで、あとは同じ
3. 画面外判定 4か所（Bullet, EnemyBullet, Item, Effect）
いま直そうとしないでください 道具を持たずに直そうとすると、たいてい余計に複雑になります。

4-16 で、このメモを見ながらまとめて直します。 それまでは「におう場所の地図」として持っておいてください。

08確認

  1. いちばん困るコードスメルは？ なぜ？
  2. マジックナンバーを定数にする、いちばんの利点は？
  3. LV4 で作るのは、何回目のゲーム？
答え
  1. 重複したコード。仕様変更のとき一部だけ直し忘れ、 しかもコンパイルが通るので気づけないから。
  2. 数字が1か所に集まり、調整が速くなる。意味も分かる。
  3. 3回目。1回目は動かすため、2回目は見せるため、 3回目は壊れにくくするため。
