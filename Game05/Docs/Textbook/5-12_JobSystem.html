マルチスレッド③ ジョブシステムを作る

難易度 ／ 前提 5-11

01この章でできるようになること

  • 更新処理を並列化して、計測できる
  • スレッドを毎回作ってはいけない理由が分かる
  • 並列化しても速くならない場合を知っている

02スレッドを毎回作ってはいけない

// ★ だめ：毎フレーム4つ作って、4つ捨てる
void Update()
{
    std::vector<std::thread> ts;
    for (int i = 0; i < 4; i++) {
        ts.emplace_back(UpdatePart, i);
    }
    for (auto& t : ts) { t.join(); }
}
コスト目安
スレッドを1つ作る 30〜100 マイクロ秒
スレッドを1つ終わらせる10〜50 マイクロ秒

4つ作って捨てるだけで、0.2〜0.5 ms。 16.6ms の予算からすると、無視できません。

だから「作っておいて、使い回す」 4-06 と、まったく同じ発想です。
スレッドをあらかじめ作っておき、 仕事（ジョブ）だけを渡す。 これがスレッドプール／ジョブシステムです。

03いちばん単純なジョブシステム

// JobSystem.h
#pragma once
#include <thread>
#include <mutex>
#include <condition_variable>
#include <functional>
#include <vector>
#include <queue>
#include <atomic>

/// <summary>
/// あらかじめ作ったスレッドに、仕事を配る。
/// </summary>
class JobSystem {
public:
    void Init(int numThread = 0)
    {
        if (numThread <= 0) {
            // 論理コア数 - 1（メインスレッドのぶんを残す）
            numThread = (int)std::thread::hardware_concurrency() - 1;
            if (numThread < 1) { numThread = 1; }
        }
        m_stop = false;
        for (int i = 0; i < numThread; i++) {
            m_threads.emplace_back([this] { WorkerLoop(); });
        }
    }

    void Terminate()
    {
        {
            std::lock_guard<std::mutex> lock(m_mutex);
            m_stop = true;
        }
        m_cv.notify_all();
        for (auto& t : m_threads) {
            if (t.joinable()) { t.join(); }
        }
        m_threads.clear();
    }

    ~JobSystem() { Terminate(); }

    /// <summary>仕事を追加する。</summary>
    void Push(std::function<void()> job)
    {
        {
            std::lock_guard<std::mutex> lock(m_mutex);
            m_jobs.push(std::move(job));
        }
        m_pending++;
        m_cv.notify_one();
    }

    /// <summary>全部の仕事が終わるまで待つ。</summary>
    void WaitAll()
    {
        while (m_pending > 0) {
            std::this_thread::yield();
        }
    }

private:
    void WorkerLoop()
    {
        for (;;) {
            std::function<void()> job;
            {
                std::unique_lock<std::mutex> lock(m_mutex);
                m_cv.wait(lock, [this] { return m_stop || !m_jobs.empty(); });

                if (m_stop && m_jobs.empty()) { return; }

                job = std::move(m_jobs.front());
                m_jobs.pop();
            }
            job();
            m_pending--;
        }
    }

    std::vector<std::thread>          m_threads;
    std::queue<std::function<void()>> m_jobs;
    std::mutex                        m_mutex;
    std::condition_variable           m_cv;
    std::atomic<int>                  m_pending{ 0 };
    bool                              m_stop = false;
};
condition_variable とは 「仕事が来るまで、スレッドを眠らせておく」ための道具です。
眠っているあいだ、CPUをまったく使いません。
これがないと、仕事がないときも ぐるぐる回り続けて（スピンして）、CPUを食いつぶします。

04使う ― 範囲を分割する

// 弾10000発の更新を、4分割して並列に
void BulletSystem::UpdateParallel(float dt)
{
    const int n = m_count;
    const int numJob = 4;
    const int chunk = (n + numJob - 1) / numJob;

    for (int j = 0; j < numJob; j++) {
        int begin = j * chunk;
        int end   = std::min(begin + chunk, n);
        if (begin >= end) { continue; }

        g_jobSystem.Push([this, begin, end, dt] {
            for (int i = begin; i < end; i++) {
                m_positions[i] += m_velocities[i] * dt;
            }
        });
    }
    g_jobSystem.WaitAll();      // ★ 全部終わるまで待つ
}
これが安全な理由 ジョブ j は、[begin, end) の範囲しか触りません。 範囲が重ならないので、データ競合が起きません。

ロックも atomic も、一切使っていません。 5-11 のとおり、 これがいちばん速くて安全な形です。

5-06 で SoA にしておいたことが、 ここで効きます。 配列を範囲で分けるだけで、並列化できます。

05並列化しても速くならない場合

原因説明
処理が軽すぎる ジョブを配るコストのほうが高い
メモリ帯域が上限 4コアで同時に読んでも、メモリは1本
偽共有 5-11
ロックで待っている結局1人ずつになる
分割が不均等 いちばん遅いジョブが終わるまで待つ
2番目は、意外と早く頭打ちになります 「配列を読んで、足して、書き戻す」だけの処理は、 計算がほぼゼロで、メモリ待ちが全部です。
そういう処理は、コアを増やしても2〜3倍で頭打ちになります。

計算が重い処理ほど、並列化がよく効きます。
目安：1ms 未満の処理は、並列化しない ジョブの配布と待ち合わせで、 数十〜100マイクロ秒は使います。
0.3ms の処理を4分割しても、0.2ms にしかなりません。 コードは確実に複雑になります。

06ゲームでの使いどころ

処理並列化備考
パーティクルの更新向く 数が多く、互いに独立
弾の更新数が多ければ—
当たり判定（判定だけ）向く 結果はスレッドごとに貯める
ファイルの読み込み向く 待ち時間が長いので効果大
アニメーションの行列計算向く計算が重い
NewGO / DeleteGO 禁止 エンジンがシングルスレッド前提
描画コマンドの発行k2Engine では不可 RenderContext が1つ
いちばん実用的なのは、ファイルの読み込みです ディスクを待っているあいだ、CPUは何もしていません。 別スレッドで読めば、その間にゲームを動かせます。

5-01 の演習3で見た 「シーン切り替え時のスパイク」を、 これで消せます。
ただし、読み終わったあとの NewGO は、 必ずメインスレッドでやること。

演習2（並列化する）

弾（またはパーティクル）の更新を並列化して、時間を測る。何個から効果が出るか。

解答例を見る（まず自分でやってから） 
void BenchParallelUpdate()
{
    JobSystem js;
    js.Init(4);

    for (int N : { 1000, 10000, 100000, 1000000 }) {
        std::vector<Vector3> pos(N, Vector3::Zero);
        std::vector<Vector3> vel(N, { 1.0f, 2.0f, 3.0f });
        const float dt = 1.0f / 60.0f;
        const int LOOP = 100;

        char head[64];
        sprintf_s(head, "---- N = %d ----\n", N);
        OutputDebugStringA(head);

        //--- 逐次 ---
        {
            BENCH("  逐次");
            for (int k = 0; k < LOOP; k++) {
                for (int i = 0; i < N; i++) { pos[i] += vel[i] * dt; }
            }
        }

        //--- 並列（4分割）---
        {
            BENCH("  並列 x4");
            for (int k = 0; k < LOOP; k++) {
                const int numJob = 4;
                const int chunk = (N + numJob - 1) / numJob;
                for (int j = 0; j < numJob; j++) {
                    int b = j * chunk;
                    int e = std::min(b + chunk, N);
                    if (b >= e) { continue; }
                    js.Push([&pos, &vel, b, e, dt] {
                        for (int i = b; i < e; i++) { pos[i] += vel[i] * dt; }
                    });
                }
                js.WaitAll();
            }
        }

        char b[64];
        sprintf_s(b, "  check %f\n\n", pos[0].x);
        OutputDebugStringA(b);
    }

    js.Terminate();
}

10万個でも、まだ並列のほうが遅い 1フレームあたりに直すと、10万個の逐次は 0.092 ms です。

そこにジョブ配布の 0.03ms と待ち合わせのコストが乗るので、 まったく割に合いません。

「並列化すれば速くなる」は、成り立たないのです。

100万個でも 4倍ではなく 2.3倍

この処理は、メモリ帯域で頭打ちになっています。 1要素あたり 24バイト読んで 12バイト書くだけで、 計算は掛け算と足し算だけ。

コアを増やしても、メモリの帯域は増えません。

計算を重くすると、どうなるか

// わざと計算を増やす
for (int i = b; i < e; i++) {
    Vector3 v = vel[i];
    for (int k = 0; k < 20; k++) {        // ★ 重い計算
        v.x = sinf(v.x) * 1.001f;
        v.y = cosf(v.y) * 1.001f;
    }

}

計算が支配的な処理 → コア数に近い倍率

自分の処理がどちらかを見極めてから、並列化を判断してください。

演習3（読み込みを並列に）

ファイルの読み込みを、別スレッドでやる。読み終わったあとの NewGO は、必ずメインスレッドで。

解答例を見る（まず自分でやってから）

設計 ― 「読む」と「作る」を分ける

// AsyncLoader.h
#pragma once

/// <summary>
/// ファイルを別スレッドで読み、メインスレッドで使えるようにする。
/// </summary>
/// <remarks>
/// エンジンの関数（NewGO や ModelRender::Init）は
/// 別スレッドから呼んではいけないので、
/// 「バイト列を読む」ところまでを別スレッドでやる。
/// </remarks>
class AsyncLoader : public IGameObject {
public:
    bool Start()  override;
    void Update() override;

    /// <summary>読み込みを依頼する。</summary>
    void Request(const std::string& path);

    /// <summary>全部読み終わったか。</summary>
    bool IsDone() const { return m_remain == 0; }

    float GetProgress() const
    {
        if (m_total == 0) { return 1.0f; }
        return 1.0f - (float)m_remain / m_total;
    }

private:
    struct Loaded {
        std::string          path;
        std::vector<uint8_t> data;
    };

    JobSystem              m_jobs;
    std::mutex             m_mutex;
    std::vector<Loaded>    m_finished;    // ★ 読み終わったもの
    std::atomic<int>       m_remain{ 0 };
    int                    m_total = 0;
};
// AsyncLoader.cpp
bool AsyncLoader::Start()
{
    m_jobs.Init(2);        // 読み込みは2スレッドで充分
    return true;
}

void AsyncLoader::Request(const std::string& path)
{
    m_remain++;
    m_total++;

    m_jobs.Push([this, path] {
        //----- ここは別スレッド -----
        // ★ エンジンの関数は、一切呼ばない
        std::vector<uint8_t> data;

        FILE* fp = nullptr;
        if (fopen_s(&fp, path.c_str(), "rb") == 0 && fp != nullptr) {
            fseek(fp, 0, SEEK_END);
            long size = ftell(fp);
            fseek(fp, 0, SEEK_SET);
            data.resize(size);
            fread(data.data(), 1, size, fp);
            fclose(fp);
        }

        {
            std::lock_guard<std::mutex> lock(m_mutex);
            m_finished.push_back({ path, std::move(data) });
        }
        m_remain--;
    });
}

void AsyncLoader::Update()
{
    //----- ここはメインスレッド -----
    std::vector<Loaded> ready;
    {
        std::lock_guard<std::mutex> lock(m_mutex);
        ready.swap(m_finished);          // ★ さっと取り出して、ロックを離す
    }

    // ★ エンジンの関数を呼ぶのは、ここだけ
    for (auto& item : ready) {
        RegisterToEngine(item.path, item.data);
    }
}

この分け方が、この演習の核心です
別スレッドでやることメインスレッドでやること
ファイルをバイト列として読む エンジンに登録する
解凍・パースなど、純粋な計算 NewGO、Init()、GPUリソースの作成
共有データに触らない—
「待ち時間だけを別スレッドに出す」のが、 いちばん安全で、効果も大きいやり方です。
ロックを持ったまま、重い処理をしないこと Update() で swap() を使っているのは、 ロックしている時間を最短にするためです。 

// ★ だめ：ロックしたまま、重い登録処理をする
{
    std::lock_guard<std::mutex> lock(m_mutex);
    for (auto& item : m_finished) {
        RegisterToEngine(...);        // ★ この間、読み込みスレッドが止まる
    }
    m_finished.clear();
}
ロックの中では、取り出すだけ。処理は外で。
k2Engine の ModelRender::Init() は、メインスレッドで 中で DirectX のリソースを作るので、別スレッドから呼ぶと壊れます。

「ファイルを読む」と「GPUリソースを作る」を分けられるかどうかが、 非同期ロードを作れるかの分かれ目です。

エンジンがそこを分けていない場合、 できるのは「ファイルをOSのキャッシュに載せておく」 （先読み）までです。 それでも、体感は改善します。

08確認

  1. スレッドを毎フレーム作ってはいけないのはなぜ？
  2. 配列を範囲で分割する方式が安全なのはなぜ？
  3. 並列化しても速くならない原因を3つ。
  4. 別スレッドで NewGO を呼んではいけないのはなぜ？
答え
  1. 1つ作るのに 30〜100 マイクロ秒かかるから。
  2. それぞれのジョブが、重ならない範囲しか触らないから。 ロックが要らない。
  3. 処理が軽すぎる／メモリ帯域が上限／偽共有／ ロック待ち／分割が不均等。
  4. k2Engine がシングルスレッド前提で書かれていて、 内部のリストなどが保護されていないから。
