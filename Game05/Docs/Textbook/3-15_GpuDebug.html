LV3 表現 ／ 3-15

GPUの中を見る（PIX / RenderDoc）

難易度 ／ 前提 3-03

01この章でできるようになること

  • 1フレームに何が描かれたかを、目で見て確認できる
  • シェーダの中身をデバッグできる
  • 「なぜか映らない」を、推測ではなく観測で解決できる

02なぜ必要か

CPUのコードは、1-18 でやったように ブレークポイントで止めて、変数の中身を見られます。

シェーダには、それができません。 GPUで、何千何万ものピクセルについて同時に走っているからです。

だから「色を出して目で見る」という原始的な方法をとってきました （3-03）。 それをちゃんとしたツールでやろう、というのがこの章です。

03どちらを使うか

PIX on WindowsRenderDoc
作っているところMicrosoft有志（オープンソース）
対応APIDirectX 12 専用DX11/12, Vulkan, OpenGL
入手Microsoft のサイトからrenderdoc.org から
費用無料無料
おすすめ まずこちら。DX12 向けに作られている 軽い。起動が速い

どちらも「1フレームを丸ごと記録して、あとから調べる」 という道具です。使い方の考え方は同じなので、 片方を覚えればもう片方も使えます。

インストールは自分でやってください どちらも配布元が更新されるため、 このページに手順を書いても古くなります。 「PIX on Windows」「RenderDoc」で検索して、 公式サイトから入手してください。

04基本の流れ

  1. ツールからゲームを起動する（または起動中のゲームにつなぐ）
  2. 調べたい場面でキャプチャ（1フレーム記録）
  3. 描画コマンドの一覧が出る
  4. 1つずつクリックすると、その時点の画面が見られる

4番目がすべてです。 「どの描画で絵が変わったか」「どの描画で消えたか」が、 一目で分かります。

05これで解決できること

症状見るところ
何も映らない そもそも DrawIndexed が呼ばれているか。 呼ばれていなければCPU側の問題
真っ黒／真っ白に描かれる そのドローの入力テクスチャを見る。 読み込みに失敗していないか
色がおかしい 定数バッファの中身を見る。 3-04 の詰め方のミスが分かる
形が崩れる 頂点バッファと、頂点シェーダの出力
手前のものが隠れる 深度バッファの中身 （3-07）
重い ドローコールの数。どのドローに時間がかかっているか
いちばん価値があるのは、1つめです 「そもそも描こうとしていないのか」「描こうとしたけど見えないのか」
この2つは原因がまったく違うのに、 画面を見ているだけでは区別がつきません。 ここが分かるだけで、調べる範囲が半分になります。

06ピクセルを1つ選んで追いかける

この機能が、GPUデバッガの真価です。

表示された画面のピクセルを1つクリックすると、 そのピクセルの色を決めたピクセルシェーダを、1行ずつ追えるのです。

  • どのテクスチャから、どんな色を読んだか
  • 定数バッファの値が、どう使われたか
  • 途中の変数の値
  • 最終的にどう計算されて、その色になったか

CPUのブレークポイントと、まったく同じことができます。

シェーダにデバッグ情報が要ります 最適化されたシェーダは、変数が消えていて追えません。
Debug ビルドで試してください。 それでも追えないときは、シェーダのコンパイルオプションに /Zi（デバッグ情報）/Od（最適化なし）が 必要になることがあります。

07k2Engine のフレームを覗いてみる

キャプチャすると、自分が書いていない描画がたくさん並んでいる ことに気づくはずです。

だいたいの順番何をしている
シャドウマップ ライトから見た距離を描く（3-12）
G-Buffer / モデル描画3Dモデルを描く
ポストエフェクト ブルーム、トーンマップなど （3-08）
2D描画スプライト、フォント
ImGui F1 のデバッグ画面。最後に描かれる

エンジンが何をしているか、いちばん確実に分かる方法がこれです。 コードを読むより速いことすらあります。

08演習

演習1（まねる）

PIX か RenderDoc を入れて、自分のゲームを1フレームキャプチャする。描画コマンドを上から順にクリックして、絵が組み上がっていくのを見る。

演習2（追う）

3-05 で作ったダメージフラッシュのピクセルを1つ選び、シェーダをステップ実行して、色が決まる過程を見る。

解答例を見る（まず自分でやってから）

手順

  1. ダメージを受けている瞬間にキャプチャする
  2. 描画コマンド一覧から、プレイヤーを描いているドローを選ぶ
  3. 出力画像の赤くなっている部分のピクセルをクリック
  4. 「Debug Pixel」（PIX）／「Debug this pixel」（RenderDoc）を選ぶ

見えるはずのもの

見るもの確認できること
colorTexture.Sample() の戻り値 テクスチャから読んだ元の色
param0.x の値 C++ から送ったフラッシュの強さが、本当に届いているか
lerp() の結果赤と混ざったあとの色
戻り値画面に出る最終的な色
2つめがこの演習の核心です 3-04 でいちばん多いミスは、 定数バッファの値が、思ったとおりに届いていないことでした。

16バイト境界の詰め方を間違えると、値が別の場所に入ります。 画面を見ているだけでは「なぜか効かない」としか分かりませんが、 ここを見れば一発で分かります。

演習3（調べる）

自分のゲームのドローコール数を数える。F1 の Profiler が出している数と合っているか確かめる。合っていない場合、その差は何か考える。

解答例を見る（まず自分でやってから）

ふつう、ぴったりは合いません。

差の原因説明
ImGui 自身の描画 F1 の画面も描画コマンドを使う。 Profiler が数える前／後で描かれる
DrawInstanced 系 K2_COUNT_DRAW_CALL を入れていない描画関数があれば漏れる
Clear やコピー 画面のクリアやテクスチャのコピーは、ドローではないが GPU の仕事
Effekseer エフェクトはエンジン外のライブラリが描いている

ここで身につけてほしい態度

K2_COUNT_DRAW_CALL は RenderContext::DrawIndexed と DrawIndexedInstance に入れてあります。 つまり Profiler の数字は「エンジンが意図的に数えた数」であって、 GPU が実際にやった仕事の全部ではありません。

計測器は、必ず何かを見落としています 自分が作った計測器が、何を数えていて何を数えていないか。 それを知らずに数字を信じるのが、いちばん危険です。

GPUデバッガは「本当に起きたこと」を見せてくれます。 自作の計測器を検算する道具として使ってください。

09確認

  1. GPUデバッガは、何を記録する？
  2. 「何も映らない」とき、まず確認すべきことは？
  3. ピクセルを選んで何ができる？
答え
  1. 1フレームぶんの描画コマンドと、そのときのリソースの中身。
  2. そもそも DrawIndexed が呼ばれているかどうか。 呼ばれていなければCPU側の問題。
  3. そのピクセルのピクセルシェーダを1行ずつ追える（ステップ実行）。
