CPUの仕組み

難易度 ／ 前提 5-02

01この章でできるようになること

  • CPUが命令を「流れ作業」で処理していることが分かる
  • 分岐予測が外れると遅くなる理由を説明できる
  • 仮想関数がなぜ「遅い」と言われるか説明できる
この章は、すぐには役に立ちません ここで学ぶのは「なぜ」の部分です。 実際に手を動かすのは 5-05 からです。
ただし、ここを知らないと 5-05 以降が丸暗記になります。

02CPU は流れ作業で動いている

命令を1つずつ「読んで、実行して、次」とやっているわけではありません。 工場のベルトコンベアのように、何段階にも分けて、 同時に何個も流しています。

段階やること
フェッチ命令を読む
デコード命令を解釈する
実行計算する
メモリアクセス読み書きする
ライトバック結果を書き戻す

これを「パイプライン」といいます。 実際のCPUでは、10段以上に分かれています。

命令1が「実行」の段にいるとき、 命令2は「デコード」、命令3は「フェッチ」の段にいます。 だから1サイクルに1命令ぶんの成果が出ます。

03問題 ― if があると、次が分からない

if (enemy->IsDead()) {
    AddScore(100);        // ★ こっちを先読みする？
} else {
    enemy->Update();      // ★ それともこっち？
}

条件の結果が出るまで、次にどの命令を流せばいいか分かりません。 でも、待っているとパイプラインが空になります。

そこでCPUは「たぶんこっちだろう」と予測して、先に流します。 これが分岐予測です。

結果
予測が当たった何も損しない。全速力
予測が外れた 流していた命令を全部捨てて、やり直し

外れたときの損失は15〜20サイクルほど。 単純な足し算なら、その間に15回以上できます。

予測は、かなり当たります 最近のCPUの分岐予測は、95%以上当たると言われています。
規則性のある分岐なら、ほぼ外しません。 
for (int i = 0; i < 1000; i++) {   // ★ 999回は「続く」。予測は簡単
    ...
}

04予測が外れやすい分岐

// ★ ランダムな条件 ― 予測できない
for (Enemy* e : enemies) {
    if (rand() % 2 == 0) {        // 半分の確率。予測不能
        ...
    }
}

// ★ データがバラバラに並んでいる ― 予測しにくい
for (Enemy* e : enemies) {
    if (e->IsActive()) {          // 生きてる/死んでるが入り混じっている
        e->Update();
    }
}

対策：条件をそろえる 

// 生きている敵だけを、前に詰めておく
// → ループの前半は全部 true、後半は全部 false
//   予測が当たりやすくなる

auto it = std::partition(enemies.begin(), enemies.end(),
    [](Enemy* e) { return e->IsActive(); });

for (auto i = enemies.begin(); i != it; ++i) {
    (*i)->Update();               // ★ if が要らなくなった
}
これは、たいてい割に合いません 並べ替えのコストのほうが高いことが多いです。
分岐予測を意識するのは、 「何万回も回るループの中」だけにしてください。
知識として知っておくことに意味があります。

05仮想関数が「遅い」と言われる理由

for (IGameObject* go : objects) {
    go->Update();      // ★ どのクラスの Update が呼ばれるか、実行時に決まる
}

仮想関数は、クラスごとの関数表（vtable）を引いてから呼びます。

起きることコスト
1. オブジェクトから vtable のアドレスを読む メモリアクセス1回
2. vtable から関数のアドレスを読む メモリアクセス1回
3. そのアドレスへジャンプ 予測しにくい分岐
4. インライン化できない これがいちばん大きい
でも、これを理由に仮想関数をやめないでください 仮想関数1回のコストは、数ナノ秒です。 1フレームに1000回呼んでも、数マイクロ秒。 16.6ms の予算からすれば、誤差です。

問題になるのは「1フレームに10万回以上呼ぶ」ような場合だけです。 パーティクルや、大量の弾の更新などです。

4番の「インライン化できない」が、実は本体です。 5-02 で見たとおり、 Release では小さい関数がインライン展開されます。 仮想関数は、それができません。

06本当のボトルネックは、メモリ

やることおおよそのサイクル数
足し算・引き算1
掛け算3〜5
割り算20〜40
分岐予測ミス15〜20
L1キャッシュから読む4
L2キャッシュから読む12
L3キャッシュから読む40
メインメモリから読む 200〜300
最後の行を見てください メモリから1回読むあいだに、足し算が200回以上できます。
つまり、いまのCPUにとって「計算」はほぼタダで、 「データを取ってくる」ことだけが高いのです。

これが LV5 でいちばん重要な事実です。 次の章から、ここを掘り下げます。

07演習

演習1（考える）

「割り算より掛け算のほうが速い」は本当か。上の表を見て、どれくらい差があるか確認する。それは16.6msのうちどれくらいか。

演習2（見積もる）

弾1000発 × 敵50体の当たり判定で、メモリアクセスが何回起きるか見積もる。上の表を使って、おおよその時間を計算する。

解答例を見る（まず自分でやってから）

前提

for (Bullet* b : m_bullets) {       // 1000発
    for (Enemy* e : m_enemies) {    // 50体
        if (IsHit(b->GetPosition(), e->GetPosition())) { ... }
    }
}

回数

何を回数
内側のループ1000 × 50 = 50,000回
ポインタをたどる（b->）50,000回
ポインタをたどる（e->）50,000回

最悪の場合 ― 全部メインメモリから読む

100,000回 × 250サイクル = 25,000,000 サイクル

3GHz のCPUなら
25,000,000 ÷ 3,000,000,000 = 約 8.3 ミリ秒

16.6ms の予算のうち、8.3ms。半分です。

最良の場合 ― 全部L1キャッシュにある

100,000回 × 4サイクル = 400,000 サイクル
                      = 約 0.13 ミリ秒
同じコードで、60倍の差があります 命令の数はまったく同じです。 違うのは「データがどこにあるか」だけです。

これが、LV5 でいちばん伝えたいことです。

実際はどうなるか

現実には、この中間です。ポイントは 「m_bullets が std::vector<Bullet*> である」こと。

  • Bullet* の配列自体は、連続して並んでいる → キャッシュに乗る
  • その先の Bullet 本体は、バラバラの場所にある → キャッシュに乗らない

NewGO で1つずつ確保したオブジェクトは、 メモリ上でバラバラに散らばっています。

だから「ポインタの配列」は遅いのです これを解決する方法が 5-06 です。

いまは「どれくらいの差になりうるか」を 数字で感じられれば充分です。

演習3（調べる）

自分のPCのキャッシュサイズを調べる。（L1 / L2 / L3 それぞれ何KB / 何MB か）本文には答えがありません。

解答例を見る（まず自分でやってから）

調べ方 ― タスクマネージャ

  1. Ctrl+Shift+Esc
  2. [パフォーマンス] タブ → [CPU]
  3. 右下に L1キャッシュ / L2キャッシュ / L3キャッシュ が出ます

調べ方 ― コマンド

wmic cpu get L2CacheSize,L3CacheSize,NumberOfCores,NumberOfLogicalProcessors

典型的な値

階層大きさだいたい何が入るか
L132〜64 KB（コアごと） Vector3 なら 2,000〜5,000個
L2512KB〜2MB（コアごと） Vector3 なら 4万〜16万個
L38〜32MB（全コア共有） 数十万〜数百万個
メインメモリ8〜64 GB全部

自分のゲームのデータ量と比べてみる

Bullet  1個 = 位置(12) + 速度(12) + タイマー(4) + フラグ(4)
             + SpriteRender(数百バイト) + vtable(8) ...
           ≒ 400 バイト（SpriteRender を含むと、かなり大きい）

1000発 × 400 バイト = 400 KB

→ L1(64KB) には全然入らない
→ L2(1MB) にはなんとか入る
→ でも、敵やその他のデータと取り合いになる
「1個あたりを小さくする」が効く理由が、これです 当たり判定に必要なのは、位置（12バイト）と半径（4バイト）だけです。

それなのに、400バイトのオブジェクト全体を メモリから引っぱってきています。

必要な16バイトだけを、別の配列にまとめて持てば、 25分の1のメモリで済みます。 1000発ぶんでも 16KB。L1キャッシュに収まります。

これが 5-06 の SoA です。
L1 が「コアごと」なのも、あとで効いてきます コア1とコア2は、別々のL1キャッシュを持っています。

2つのコアが同じデータを触ると、 キャッシュの内容を合わせる通信が発生します。

これが 5-11 で出てくる 「偽共有（false sharing）」の正体です。

08確認

  1. 分岐予測が外れると、どれくらい損する？
  2. 仮想関数のコストで、いちばん大きいのは？
  3. メインメモリから読むのは、足し算の何倍くらい遅い？
  4. いまのCPUにとって、高いのは「計算」と「データ取得」のどちら？
答え
  1. 15〜20サイクル。
  2. インライン化できないこと。
  3. 200〜300倍。
  4. データ取得。計算はほぼタダ。
