LV5 最適化 ／ 5-02

K2_PROFILE_SCOPE で自分のコードを測る

難易度 ／ 前提 5-01

01この章でできるようになること

  • 重い場所を、推測ではなく計測で絞り込める
  • 計測そのものが結果を歪めることを知っている
  • Release で正しく測れる

02使い方は1行

void Player::Update()
{
    K2_PROFILE_SCOPE("Player");     // ★ これだけ

    Move();
    UpdateShot();
    CheckHit();
}

この行から、} を抜けるまでの時間が測られます。 F1 → Profiler パネルに、名前と時間が並びます。

4-08 で出てきた RAII です。 終了を書き忘れることが、原理的にありません。

03入れ子にできる

void GameScene::Update()
{
    K2_PROFILE_SCOPE("GameScene");

    UpdateEnemies();
    UpdateBullets();
    UpdateCollision();
}

void GameScene::UpdateCollision()
{
    K2_PROFILE_SCOPE("Collision");    // ★ GameScene の内側として表示される
    ...
}

パネルには、字下げされて階層で表示されます。 

GameScene         8.42 ms
  Enemies         1.20 ms
  Bullets         0.65 ms
  Collision       6.10 ms     ← ここが重い

04絞り込み方 ― 上から半分ずつ

いきなり細かいところに入れないでください。

  1. まず大きい単位で3〜4か所に入れる （更新／描画／当たり判定）
  2. いちばん重いところを見つける
  3. その中を、また3〜4か所に分ける
  4. 2〜3回繰り返せば、だいたい特定できる
二分探索と同じ考え方です 1-19 でバグを探したときと同じです。
範囲を半分に狭めることを繰り返すのが、いちばん速い。

05計測そのもののコスト

毎フレーム何千回も呼ばれる関数に入れないでください 計測1回にも時間がかかります。 弾1000発それぞれの Update() に入れると、 計測のせいで重くなり、計測結果が信用できなくなります。 
// ★ だめ
void Bullet::Update()
{
    K2_PROFILE_SCOPE("Bullet");     // 1000発なら1フレームに1000回
    ...
}

// ○ まとめて測る
void BulletPool::UpdateAll()
{
    K2_PROFILE_SCOPE("Bullets");    // 1フレームに1回
    for (Bullet* b : m_bullets) {
        b->Update();
    }
}

k2EngineLow/dbg/DebugProfiler.h にも 「1フレームに数十回まで」と書いてあります。 それを超えるなら、測り方を変えてください。

06Debug と Release

DebugRelease
最適化なしあり
速度数倍〜10倍遅い本来の速度
インライン化されないされる
計測に使えるか 比較には使える こちらで測ること
Debug の数字で判断すると、間違った結論に至ります Debug では、小さい関数呼び出しが本当に関数呼び出しになります。 だから「関数呼び出しが重い」という誤った結論が出ます。
Release ではインライン展開されて、呼び出し自体が消えます。

k2Engine では、Release でもデバッグGUIが使えます。 k2EngineLow/dbg/DebugConfig.h の K2_ENABLE_DEBUG_GUI が定義されていれば動きます。

07測るときの決まりごと

やること理由
同じ場面で測る 敵の数が違えば、当然結果も違う
何回か測って、ばらつきを見る 1回だけでは、たまたまかもしれない
ほかのアプリを閉じる ブラウザや動画で、平気で数msずれる
電源設定を「高パフォーマンス」に ノートPCは、省電力でCPUの速度を落とす
変更は1つずつ 2つ変えると、どちらが効いたか分からない
再現できる場面を作っておくと、あとが楽です 
// デバッグパネルに、負荷テスト用のボタンを置く
if (ImGui::Button(U8("敵を200体出す"))) {
    for (int i = 0; i < 200; i++) {
        CreateEnemy(enEnemyType_Zako, RandomPosition());
    }
}
毎回同じ条件を作れると、比較が正確になります。

08演習

演習1（入れる）

大きい単位で3か所に K2_PROFILE_SCOPE を入れて、どこがいちばん重いか見る。

演習2（絞る）

いちばん重かったところの中をさらに分けて、原因を1つの関数まで絞り込む。

解答例を見る（まず自分でやってから）

段階1 ― 大きく3つ

void GameScene::Update()
{
    { K2_PROFILE_SCOPE("Enemies");   UpdateEnemies();   }
    { K2_PROFILE_SCOPE("Bullets");   UpdateBullets();   }
    { K2_PROFILE_SCOPE("Collision"); UpdateCollision(); }
}
Enemies      1.20 ms
Bullets      0.65 ms
Collision    6.10 ms     ← ここ

段階2 ― Collision の中を分ける

void GameScene::UpdateCollision()
{
    { K2_PROFILE_SCOPE("Col:PlayerBullet"); CheckPlayerBulletVsEnemy(); }
    { K2_PROFILE_SCOPE("Col:EnemyBullet");  CheckEnemyBulletVsPlayer(); }
    { K2_PROFILE_SCOPE("Col:Body");         CheckPlayerVsEnemy();       }
}
Collision            6.10 ms
  Col:PlayerBullet   5.80 ms     ← ここ
  Col:EnemyBullet    0.22 ms
  Col:Body           0.05 ms

段階3 ― 中身を見る

void GameScene::CheckPlayerBulletVsEnemy()
{
    for (Bullet* b : m_bullets) {
        if (!b->IsActive()) { continue; }

        for (Enemy* e : m_enemies) {        // ★ 二重ループ
            if (!e->IsActive()) { continue; }
            if (IsHit(b, e)) { ... }
        }
    }
}

弾200発 × 敵50体 = 10000回。 これが原因だと分かりました。

ここまで来れば、対策を選べます
対策効き方章
非アクティブを先に弾く まずこれ。タダ—
大まかな範囲で先に除外する大きい—
空間分割（グリッド）桁で効く—
データの並べ方を変える数倍 5-06
SIMD でまとめて計算数倍 5-13
並列化コア数ぶん 5-12
上から順に検討してください。 下のほうほど、コードが複雑になります。
計測を入れる前と後で、全体の時間が変わっていないか確認を 段階2で6個もスコープを入れると、 それ自体が数十マイクロ秒かかります。

原因が分かったら、細かいスコープは消してください。 入れっぱなしにすると、ゲーム本体が遅くなります。

演習3（比べる）

Debug と Release で、同じ場所の数字を比べる。何倍違うか。どこがいちばん差が大きいか。

解答例を見る（まず自分でやってから）

測り方

  1. 同じ場面を作る（デバッグパネルのボタンで敵200体、など）
  2. Debug で測って記録
  3. Release でビルドし直して、同じ場面で測る

典型的な結果

                     Debug    Release   倍率
Frame               52.3 ms   14.8 ms   3.5x
  Enemies            8.4 ms    1.2 ms   7.0x
  Bullets            6.1 ms    0.6 ms  10.2x   ★いちばん差が大きい
  Collision         18.2 ms    6.1 ms   3.0x
  Render            12.0 ms    5.9 ms   2.0x

なぜ場所によって倍率が違うのか

差が大きい処理理由
小さい関数を大量に呼ぶ Release でインライン化されて、呼び出しが消える
Vector3 の演算が多い 演算子オーバーロードが全部インライン化される
ループが単純ベクトル化されることがある
std::vector の operator[] Debug では範囲チェックが入る
差が小さい処理理由
GPU を待っている時間CPU の最適化と無関係
ファイルの読み込みディスクの速度で決まる
メモリアクセスが多い処理 メモリ待ちは最適化で消えない
最後の行が、LV5 のここから先の話です コンパイラの最適化で速くなるのは、「計算」の部分だけです。

「メモリからデータが届くのを待っている」時間は、 どれだけ最適化しても減りません。

減らすには、データの置き方を変えるしかありません。 それが 5-04 からの話です。
Debug で遅くても、気にしすぎないでください Debug が遅いのは、そういうものです。

ただしDebug で遊べないほど遅いと、開発しづらくなります。 その場合は、Debug でも敵の数を減らす設定を入れるなど、 開発しやすさのための工夫を検討してください。

09確認

  1. K2_PROFILE_SCOPE は、どこからどこまでを測る？
  2. 弾1000発それぞれに入れてはいけないのはなぜ？
  3. Release で測るべき理由は？
  4. 絞り込みの進め方は？
答え
  1. その行から、いま入っている { } を抜けるまで。
  2. 計測自体にコストがあり、結果が歪むから。
  3. Debug は最適化が切れていて、 インライン化されないため誤った結論が出る。
  4. 大きい単位から入れて、重いところを半分ずつ絞る。
