02SIMD とは

Single Instruction, Multiple Data — 1つの命令で、複数のデータを同時に処理する仕組みです。 

// ふつう（1個ずつ）
c[0] = a[0] + b[0];
c[1] = a[1] + b[1];
c[2] = a[2] + b[2];
c[3] = a[3] + b[3];        // ★ 4命令

// SIMD（4個まとめて）
__m128 va = _mm_load_ps(a);
__m128 vb = _mm_load_ps(b);
__m128 vc = _mm_add_ps(va, vb);    // ★ 1命令で4個
_mm_store_ps(c, vc);
命令セット幅float 何個
SSE128 bit4個
AVX256 bit8個
AVX-512512 bit16個。対応CPUが限られる
実は、もう使っています k2Engine の Vector3 や Matrix は、 DirectXMath を使っています。
k2EngineLow/math/Vector.h を見ると、 DirectX::XMVector3LengthSq などが出てきます。 これは中で SIMD 命令を使っています。

03AoS だと、うまく使えない

// AoS：Vector3 が 12バイトずつ並んでいる
struct Bullet { Vector3 pos; ... };
std::vector<Bullet> bullets;

// ★ 4個の x をまとめたくても、メモリ上で離れている
// bullets[0].pos.x, bullets[1].pos.x, ...  → 飛び飛び
// SoA：x だけ、y だけ、z だけの配列にする
struct BulletSoA {
    std::vector<float> x, y, z;
};

// ★ x[0..3] が連続している → 1命令で読める
__m128 vx = _mm_load_ps(&x[0]);
5-06 の SoA が、ここでも効きます SIMD を使うには、SoA がほぼ前提です。
しかも Vector3 の配列ではなく、 x・y・z を ばらばらの float 配列にするところまで必要です。

読みやすさは、さらに落ちます。

04当たり判定を4個まとめて

#include <xmmintrin.h>     // SSE

/// <summary>
/// 中心 (cx, cy) 半径 r の円と、4個の点の当たりを、まとめて判定する。
/// </summary>
/// <returns>当たった点のビットが立った値（下位4ビット）</returns>
int CheckHit4(const float* px, const float* py,
              float cx, float cy, float r)
{
    __m128 vpx = _mm_load_ps(px);          // x を4個
    __m128 vpy = _mm_load_ps(py);          // y を4個

    __m128 vcx = _mm_set1_ps(cx);          // cx を4つに複製
    __m128 vcy = _mm_set1_ps(cy);

    __m128 dx = _mm_sub_ps(vpx, vcx);      // 4個ぶんの差
    __m128 dy = _mm_sub_ps(vpy, vcy);

    __m128 d2 = _mm_add_ps(_mm_mul_ps(dx, dx),
                           _mm_mul_ps(dy, dy));   // 4個ぶんの距離の2乗

    __m128 vr2 = _mm_set1_ps(r * r);
    __m128 cmp = _mm_cmplt_ps(d2, vr2);    // 4個ぶんの比較

    return _mm_movemask_ps(cmp);           // ビットに変換
}
// 使う（要素数は4の倍数にそろえておく）
for (int i = 0; i < count; i += 4) {
    int mask = CheckHit4(&px[i], &py[i], ex, ey, radius);
    if (mask == 0) { continue; }            // ★ 4個とも外れ。よくある

    for (int k = 0; k < 4; k++) {
        if (mask & (1 << k)) { OnHit(i + k); }
    }
}
if (mask == 0) continue; が効きます ほとんどの場合、4個とも外れです。 比較1回で4個をまとめて捨てられます。
分岐の回数も4分の1になります（5-03）。

05アラインメント

_mm_load_ps は、16バイト境界が必要です そろっていないとクラッシュします。 
// ★ 危ない：std::vector<float> の要素は16バイト境界とは限らない
__m128 v = _mm_load_ps(&vec[1]);      // ★ 落ちる

// ○ そろっていなくても読める版（少し遅い）
__m128 v = _mm_loadu_ps(&vec[1]);     // u = unaligned
迷ったら _mm_loadu_ps を使ってください。 最近のCPUでは、速度差はほとんどありません。 
// きちんとそろえるなら
alignas(16) float px[1024];
alignas(16) float py[1024];

要素数が4の倍数でないときの端数処理も必要です。 

int i = 0;
for (; i + 4 <= count; i += 4) {
    // SIMD で4個ずつ
}
for (; i < count; i++) {
    // ★ 端数は、ふつうに1個ずつ
}

06たいていは、書かなくてよい

方法手間備考
コンパイラに任せるゼロ 単純なループは、勝手にSIMD化される
DirectXMath を使う小 k2Engine が既にやっている
組み込み関数を書く大 この章でやったもの
アセンブリを書く超大 いまどき、ほぼ不要

Visual Studio は、条件がそろえば自動でベクトル化します。 

// プロジェクトのプロパティ → C/C++ → コマンドライン に追加
/Qvec-report:2

ビルド時に「このループはベクトル化した／できなかった」と 出力されます。できなかった理由も番号で教えてくれます。

自動ベクトル化を助ける書き方
  • ループの中に if を入れない
  • ループの中で関数を呼ばない（インライン化されるものは可）
  • 単純な配列を使う（float* や vector<float>）
  • 繰り返し回数が、ループの前に確定している
  • ポインタが重なっていないと分かるようにする

07演習

演習1（確かめる）

/Qvec-report:2 を付けてビルドし、自分のコードのどのループがベクトル化されているか見る。

演習2（書く）

当たり判定を SIMD で書いて、ふつうの書き方と時間を比べる。

解答例を見る（まず自分でやってから） 
#include <xmmintrin.h>
#include "Bench.h"

namespace {
    const int N = 100000;      // 4の倍数にしておく
}

void CompareSimd()
{
    alignas(16) static float px[N];
    alignas(16) static float py[N];

    for (int i = 0; i < N; i++) {
        px[i] = (float)(i % 1000) - 500.0f;
        py[i] = (float)(i / 1000) - 50.0f;
    }

    const float cx = 0.0f, cy = 0.0f, r = 50.0f;
    const int LOOP = 100;

    //--- ふつう ---
    int count1 = 0;
    {
        BENCH("スカラー");
        for (int k = 0; k < LOOP; k++) {
            count1 = 0;
            const float r2 = r * r;
            for (int i = 0; i < N; i++) {
                float dx = px[i] - cx;
                float dy = py[i] - cy;
                if (dx * dx + dy * dy < r2) { count1++; }
            }
        }
    }

    //--- SIMD ---
    int count2 = 0;
    {
        BENCH("SIMD (SSE)");
        for (int k = 0; k < LOOP; k++) {
            count2 = 0;
            __m128 vcx = _mm_set1_ps(cx);
            __m128 vcy = _mm_set1_ps(cy);
            __m128 vr2 = _mm_set1_ps(r * r);

            for (int i = 0; i < N; i += 4) {
                __m128 vpx = _mm_load_ps(&px[i]);
                __m128 vpy = _mm_load_ps(&py[i]);

                __m128 dx = _mm_sub_ps(vpx, vcx);
                __m128 dy = _mm_sub_ps(vpy, vcy);
                __m128 d2 = _mm_add_ps(_mm_mul_ps(dx, dx),
                                       _mm_mul_ps(dy, dy));

                int mask = _mm_movemask_ps(_mm_cmplt_ps(d2, vr2));
                // ビットが何個立っているか数える
                count2 += __popcnt(mask);
            }
        }
    }

    char buf[128];
    sprintf_s(buf, "スカラー=%d  SIMD=%d\n", count1, count2);
    OutputDebugStringA(buf);
}

典型的な結果（Release）

スカラー                     :   34.820 ms
SIMD (SSE)                   :   12.104 ms     ← 2.9倍
スカラー=7854  SIMD=7854
「4倍」にはなりません 2.5〜3倍あたりが、現実的なところです。

理由：
  • ロードとストアの回数は減らない
  • メモリ帯域の制限（5-12 と同じ）
  • スカラー版も、コンパイラが勝手にベクトル化していることがある
結果が一致するか、必ず確認してください 上のコードで count1 == count2 を確認しているのは、 そのためです。

SIMD のコードは間違えやすく、 しかも「速いけど答えが違う」という壊れ方をします。

4-14 のテストパネルに、 「スカラー版と SIMD 版の結果が一致する」を 入れておくと安心です。

コンパイラの自動ベクトル化と比べる

// スカラー版から if を外すと、自動ベクトル化されやすくなる
int count = 0;
for (int i = 0; i < N; i++) {
    float dx = px[i] - cx;
    float dy = py[i] - cy;
    count += (dx * dx + dy * dy < r2) ? 1 : 0;   // ★ 分岐ではなく算術に
}
スカラー（if あり）          :   34.820 ms
スカラー（三項演算子）       :   13.902 ms     ← 自動ベクトル化された
SIMD（手書き）               :   12.104 ms
書き方を少し変えるだけで、手書きSIMDにほぼ並びます これが「たいていは自分で書かなくてよい」の意味です。

コンパイラがベクトル化しやすい形に書くほうが、 読みやすく、移植性もあり、間違いも少ない。

演習3（判断する）

自分のゲームに SIMD が必要か判断する。必要でないなら、なぜかを書く。本文には答えがありません。

解答例を見る（まず自分でやってから）

判断の基準

条件SIMD の価値
同じ計算を数万回以上繰り返すある
すでに SoA になっているある
その処理が 1ms 以上かかっているある
ループの中に複雑な分岐があるない。書けない
AoS のままない。まず SoA にする
数百回程度のループない

記録の例

== SIMD 導入の検討 ==

【候補】弾 × 敵 の当たり判定
  弾 800発 × 敵 30体 = 24,000回
  計測：0.18 ms（フレーム 11.2ms の 1.6%）

【SIMD にした場合】
  3倍速くなったとして 0.06 ms → 0.12 ms 浮く
  フレーム全体：11.2 → 11.1 ms

【判断】導入しない。

【理由】
1. 0.12ms は 16.6ms の 0.7%。体感に影響しない
2. すでに 60FPS 出ている
3. コードが確実に読みにくくなる
4. アラインメントと端数処理でバグを入れるリスクがある

【代わりにやったこと】
判定を「三項演算子」に書き換えて、自動ベクトル化されるようにした。
/Qvec-report:2 で確認したところ、ベクトル化されていた。
0.18ms → 0.09ms。コードは1行変えただけ。

【将来 SIMD を検討する条件】
弾が 5000発を超え、当たり判定が 2ms を超えたら再検討する。
「コンパイラに任せる」が、いちばん賢い選択であることが多い 手書き SIMD は、LV5 の中でも 「効果のわりにコストが高い」部類です。

それより先に、5-06 の SoA 化や、 5-01 の「そもそもやらない」を やり尽くしてください。
それでも、知っておく価値はあります 「なぜ SoA にすると速いのか」の答えのひとつが、 「SIMD が使えるようになるから」です。

そして、シェーダ（3-03）は、 まさに SIMD の塊です。 GPU が速いのは、何千個ものピクセルに、 同じ命令を同時に適用しているからです。

SIMD を知ると、GPU がなぜ速いのかも分かります。

08確認

  1. SSE で float を何個まとめられる？
  2. SIMD を使うのに、SoA がほぼ前提なのはなぜ？
  3. _mm_load_ps と _mm_loadu_ps の違いは？
  4. 手書きする前に、まず何を試す？
答え
  1. 4個（128ビット）。
  2. まとめて読む4個が、メモリ上で連続している必要があるから。
  3. 前者は16バイト境界が必要。後者はそろっていなくても読める。
  4. コンパイラの自動ベクトル化。 ループから分岐を外すなど、ベクトル化しやすい形に書く。
