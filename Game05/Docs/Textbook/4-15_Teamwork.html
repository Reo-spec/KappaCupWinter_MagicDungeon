LV4 設計 ／ 4-15

チームで作る

難易度 ／ 前提 1-03

01この章でできるようになること

  • ブランチを切って作業し、プルリクエストを出せる
  • コンフリクトを解決できる
  • 人のコードをレビューできる／されても凹まない
1人でも、この章は役に立ちます ブランチとコミットの習慣は、1人開発でも効きます。 「昨日の自分」は、他人と同じくらい何も覚えていません。

02ブランチを切る

# いまの状態を確認
git status

# main から新しいブランチを作って移動
git switch -c feature/boss-second-phase

# ...作業...

git add .
git commit -m "ボスの第2形態を追加"
git push -u origin feature/boss-second-phase
ブランチ名の例意味
feature/boss-second-phase機能追加
fix/bullet-not-deletedバグ修正
refactor/enemy-moverリファクタリング
main に直接コミットしないでください チームでは、これが最大のルールです。 誰かが壊したとき、全員が止まります。
ブランチなら、壊れているのは本人だけです。

03コミットメッセージ

だめよい
修正 弾が画面外で消えないバグを修正
いろいろ 敵の移動を IMover に切り出し
aaa ボスの第2形態を追加

「何をしたか」ではなく「なぜしたか」が書けるとさらに良いです。 

弾のプール化

毎フレーム NewGO/DeleteGO していたため、弾幕時に
フレーム落ちしていた。200発のプールを作って使い回す形に変更。
Profiler で 0.42ms → 0.03ms を確認。
「何をしたか」は差分を見れば分かります 差分から分からないのは「なぜ」だけです。
半年後の自分が読むのは、この「なぜ」です。

04コンフリクト

同じ行を2人が変えると起きます。怖がる必要はありません。 

<<<<<<< HEAD
    m_hp = 100;
=======
    m_hp = 150;
>>>>>>> feature/balance
記号意味
<<<<<<< HEAD の下 いま自分がいるブランチの内容
======= の下 取り込もうとしている側の内容

どちらかを選ぶか、両方を合わせて、記号を全部消します。 判断に迷ったら、相手に聞いてください。

コンフリクトを減らすいちばんの方法 こまめに main を取り込むことです。 
git switch main
git pull
git switch feature/my-work
git merge main
1週間ぶんためると、解決不能になります。 毎日やってください。

05ゲーム開発ならではの問題 ― バイナリファイル

ファイルマージできる？
.cpp .hできる
.txt（ステージデータ）できる
.dds .tkm .wav できない。どちらか一方を選ぶしかない
.vcxproj できるが、壊れやすい
2人が同じファイルをプロジェクトに追加すると、よく壊れます .vcxproj は XML なので、 マージできるように見えて、順番が入れ替わって壊れます。
ファイルの追加をするときは、事前に声をかけてください。
壊れたら、片方を採用して、もう片方が手動でファイルを追加し直す のがいちばん速いです。

4-10 でステージをテキストにしたのは、 ここでも効きます。テキストならマージできます。

06プルリクエストとレビュー

プルリクエスト（PR）＝「この変更を取り込んでください」という依頼です。

出す側が書くこと 

## 何をしたか
敵の移動処理を IMover として切り出しました。

## なぜ
敵の種類ごとにクラスをコピペしていて、
移動以外を直すときに全部直すはめになっていたため。

## 確認したこと
- 4種類すべての敵が、以前と同じ動きをすること
- テストパネルが全部 OK

## 見てほしいところ
ZigzagMover の m_baseX の持ち方が、これで良いか自信がありません。

レビューする側が見ること

  • 動くか（できれば実際に動かす）
  • 半年後に読めるか
  • 同じことを2か所に書いていないか
  • 危ない書き方はないか（nullptr チェック、寿命）
レビューは「人」ではなく「コード」に対してするもの
だめな言い方よい言い方
なんでこんな書き方したの ここ、〜だと読みやすいと思いました。どうでしょう
これはバグる この場合に nullptr になりませんか？
（何も言わない） ここの分け方、良いと思いました
良いところも書いてください。 指摘だけが並ぶと、出すのが怖くなります。

07作業を分けるコツ

分け方ぶつかりやすさ
クラス単位で担当を分ける 低い。おすすめ
機能単位（「敵担当」「UI担当」）低い
2人で同じクラスを触る高い
片方がリファクタリング中に、もう片方が機能追加 最悪。地獄を見ます

LV4 でやってきた設計は、ここで効いてきます。

やったことチームでの効果
Component に分ける 同時に別のファイルを触れる
Observer 反応を足すのに、相手のファイルを触らない
Strategy 新しい敵＝新しいファイル。ぶつからない
データ化 プログラマ以外がステージを作れる
良い設計とは、結局「分担しやすい設計」です 1人で書いていると、設計の良し悪しはピンときません。
3人で同じファイルを触ってコンフリクトを起こすと、 一瞬で理解できます。

08演習

演習1（慣れる）

1人でも構わないので、ブランチを切って作業し、main にマージするまでを3回やる。

演習2（ぶつける）

わざとコンフリクトを起こして、解決する。（2つのブランチで、同じ行を別々に変える）

解答例を見る（まず自分でやってから）

起こし方

# ブランチA
git switch -c test/conflict-a
# Player.cpp の MOVE_SPEED を 300 → 400 に変更
git commit -am "移動速度を上げた"
git switch main
git merge test/conflict-a        # ここは普通にマージできる

# ブランチB（main から切る）
git switch -c test/conflict-b
# 同じ行を 400 → 250 に変更
git commit -am "移動速度を下げた"

# さらに main 側でも同じ行を変えておく
git switch main
# 400 → 500 に変更
git commit -am "移動速度をもっと上げた"

# ここでコンフリクト
git merge test/conflict-b
Auto-merging Player.cpp
CONFLICT (content): Merge conflict in Player.cpp
Automatic merge failed; fix conflicts and then commit the result.

解決

// Player.cpp を開くと
<<<<<<< HEAD
const float MOVE_SPEED = 500.0f;
=======
const float MOVE_SPEED = 250.0f;
>>>>>>> test/conflict-b
// 記号を全部消して、採用する値だけ残す
const float MOVE_SPEED = 350.0f;    // 話し合って、間を取った
git add Player.cpp
git commit          # メッセージは自動で入る
git status          # クリーンになっていることを確認
記号を消し忘れると、コンパイルエラーになります <<<<<<< ======= >>>>>>> の3つを全部消してください。

解決したら、必ずビルドしてから commit してください。 壊れたままコミットすると、チーム全員が止まります。

やめたくなったら

git merge --abort       # マージを取り消して、元の状態に戻る

これを知っているだけで、かなり気が楽になります。 コンフリクトが怖いのは、「途中でやめられない」と思っているからです。

Visual Studio を使う手もあります

[Git 変更] ウィンドウから「マージ エディターを開く」と、 左右に並べて、チェックボックスで選べます。 記号の消し忘れが起きないので、慣れないうちはこちらが安全です。

演習3（レビューする）

友達のコードを1つレビューする（または、自分の1か月前のコードを、他人だと思ってレビューする）。指摘3つ、良かったところ1つ。

解答例を見る（まず自分でやってから）

レビューの観点（上から順に見る）

優先見るところ例
1壊れる可能性 nullptr チェック、配列の範囲、寿命
2意図が読めるか 関数名、変数名、マジックナンバー
3重複同じ処理が2か所にないか
4好みの問題 波かっこの位置、空行の数 → 指摘しない

書き方の例

【良かったところ】
Enemy の移動を IMover に分けているのが分かりやすかったです。
新しい敵を足すとき、どこを書けばいいか一目で分かりました。

【1】Enemy.cpp:45
FindGO<Player>("player") の戻り値を nullptr チェックせずに
使っています。プレイヤーが死んだ後のフレームで落ちませんか？

【2】Bullet.cpp:28
「300.0f」が3か所に出てきます。定数にまとめると、
弾速を調整するとき1か所で済むと思います。

【3】Boss.cpp:112
UpdatePhase2() が140行あって、読むのがつらかったです。
攻撃の種類ごとに分けられそうに見えました。
指摘は「命令」ではなく「質問」の形にすると角が立ちません 「〜しませんか？」「〜に見えました」「〜だと思います」

自分が見落としている事情があるかもしれない、 という前提で書くと、相手も答えやすくなります。 実際、理由があってそう書いていることは、よくあります。

レビューされる側の心構え

  • コードへの指摘であって、自分への評価ではありません
  • 納得できないときは、理由を説明して議論してよい
  • 「直します」と「直しません、理由は〜」のどちらも正しい返事です
  • 指摘が多いのは、丁寧に読んでもらえたということ
1か月前の自分のコードをレビューするのも、強くおすすめします 他人のコードだと思って読むと、驚くほど指摘が出ます。

そして「なぜこう書いたのか思い出せない」という体験が、 コメントとコミットメッセージの価値を教えてくれます。

09確認

  1. チームでの最大のルールは？
  2. コンフリクトを減らすいちばんの方法は？
  3. コミットメッセージに書くべき、差分から分からないことは？
  4. マージを途中でやめるコマンドは？
答え
  1. main に直接コミットしない。
  2. こまめに main を自分のブランチへ取り込む。
  3. 「なぜそうしたか」。
  4. git merge --abort。
