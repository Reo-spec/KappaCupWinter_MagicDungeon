LV4 設計 ／ 4-13

リファクタリング ― 壊さずに作り替える

難易度 ／ 前提 4-05 , 4-12

01この章でできるようになること

  • 動いているコードを、動いたまま作り替えられる
  • 「直したら別が壊れた」を減らせる
  • どこから手を付けるか、自分で決められる

02リファクタリングの定義

外から見た動きを変えずに、中身を整理すること 「動きを変えずに」がすべてです。
バグ修正でも、機能追加でもありません。 それらと混ぜないことが、いちばん大事なルールです。
やることリファクタリング？
長い関数を分けるはい
変数名を分かりやすくするはい
Strategy に書き直すはい
「ついでに」HPの上限を直すいいえ（バグ修正）
「ついでに」敵を1種類足すいいえ（機能追加）
混ぜると、原因が分からなくなります 整理と修正を同時にやって動かなくなったとき、 「整理でミスったのか、修正が間違っていたのか」が分かりません。
コミットも分けてください。

03鉄則 ― 小さく、こまめに

やり方結果
1つ直す → ビルド → 動かす → コミット 壊れても、直前に戻れる
10個まとめて直す → ビルド エラー40個。どれが原因か分からない

「こまめすぎるかな」と思うくらいが、ちょうどいいです。 関数を1つ切り出すたびにビルドしても、遅すぎることはありません。

始める前に、必ずコミットしてください リファクタリングは、途中でよく分からなくなることがあります。 そのとき git reset --hard で戻せる状態かどうかで、 気楽さがまったく違います。
ブランチを切っておくと、さらに安心です （4-15）。

04Visual Studio に任せられるもの

手で書き換えないでください。ミスの元です。

やりたいことショートカット
名前を変える Ctrl+R, Ctrl+R
選択部分を関数に切り出す Ctrl+R, Ctrl+M
定義へ移動F12
すべての参照を検索Shift+F12
クイックアクション（提案を見る） Ctrl+.

名前の変更は、必ずこれを使ってください。 検索と置換でやると、コメントや、たまたま同じ名前の別の変数まで 書き換えてしまいます。

05よく使う手順

1. 関数の切り出し 

// 前
void Player::Update()
{
    // ...移動の処理が30行...
    // ...射撃の処理が20行...
    // ...当たり判定が25行...
}

// 後
void Player::Update()
{
    Move();
    UpdateShot();
    CheckHit();
}

切り出す単位は「コメントが書いてあるところ」です。 // 移動の処理 と書いてあるなら、 そこは Move() という関数になるべきだったということです。

2. 一時変数に名前を付ける 

// 前
if (m_position.y < -600.0f || m_position.y > 600.0f
 || m_position.x < -1000.0f || m_position.x > 1000.0f) {
    Deactivate();
}

// 後
const bool isOutOfScreen = IsOutOfScreen(m_position);
if (isOutOfScreen) {
    Deactivate();
}

3. 早期リターンでネストを浅くする 

// 前
void Player::Damage(int amount)
{
    if (m_isAlive) {
        if (!m_isInvincible) {
            if (amount > 0) {
                m_hp -= amount;
                ...
            }
        }
    }
}

// 後
void Player::Damage(int amount)
{
    if (!m_isAlive)     { return; }
    if (m_isInvincible) { return; }
    if (amount <= 0)    { return; }

    m_hp -= amount;
    ...
}
3つめは、効果のわりにいちばん簡単です ネストが3段から1段になります。 条件が「何をしないか」として並ぶので、読むのも速くなります。
リファクタリングを始めるなら、ここからがおすすめです。

06大きく作り替えるとき ― 並走させる

「敵を全部 Strategy に書き直す」のような大きい変更は、 一気にやると必ず壊れます。

新旧を並べて動かし、少しずつ移すのが安全です。 

// 1. 新しい仕組みを作る（古いほうは残したまま）
class Enemy : public IGameObject {
    void Update() override
    {
        if (m_mover != nullptr) {
            m_mover->Move(m_position, dt);     // ★ 新
        } else {
            UpdateOldMove();                    // ★ 旧（そのまま）
        }
    }
};

// 2. 敵を1種類ずつ、新しいほうに移す
// 3. 全部移り終わったら、旧を消す
これを「ストラングラーパターン」といいます 古い仕組みを、新しい仕組みで少しずつ包んで置き換えるやり方です。
どの時点でもゲームが動いているのが利点です。 途中で作業を中断しても、壊れたままになりません。

07どこから手を付けるか

全部きれいにしようとしないでください。 優先順位はこうです。

優先対象理由
1 これから触る場所 すぐ元が取れる
2バグがよく出る場所 複雑だからバグが出ている
3いちばん長い関数読めないのは事実
やらない もう触らない、動いている場所 触ると壊れる可能性だけが増える
「動いているものは触るな」は、半分正しいです もう二度と触らないコードは、汚くても構いません。
リファクタリングは「これから何度も触る場所」への投資です。 投資先を間違えないでください。

08演習

演習1（浅くする）

自分のコードでいちばんネストが深い関数を、早期リターンで浅くする。

演習2（切り出す）

いちばん長い関数を、Ctrl+R, Ctrl+M で関数に分ける。1つ切り出すたびにビルドする。

解答例を見る（まず自分でやってから）

手順

  1. まずコミットする
  2. 切り出したい範囲を選択
  3. Ctrl+R, Ctrl+M
  4. 名前を付ける
  5. ビルド → 実行 → 動作確認
  6. コミット
  7. 2に戻る

切り出す場所の見つけ方

目印意味
コメントが書いてある そこは関数になるべきだった。名前はコメントをそのまま使う
空行で区切られている自分でも「別の処理」だと思っている
for ループ全体まとまりになっている
同じ変数だけを使う数行独立した処理

切り出したあと、コメントは消す

// 前
void Player::Update()
{
    // 移動の処理
    ...30行...
}

// 後（コメントは関数名になったので、もう要らない）
void Player::Update()
{
    Move();
}

void Player::Move()
{
    ...30行...
}
引数が5個以上になったら、切り出し方を見直す Visual Studio が void Move(float& x, float& y, bool& isJump, float& timer, int& state) のような関数を作ったら、切り出す範囲が悪いです。

そこは処理のまとまりではなく、途中で切っているだけです。 範囲を変えてやり直してください。
メンバ関数なら、引数は減ります m_position や m_hp はメンバなので、 切り出した関数からもそのまま使えます。 引数が増えるのは、ローカル変数をまたいで切ったときです。

演習3（並走させる）

ストラングラーパターンで、敵の動きを1種類ずつ IMover に移す。移す途中でも、必ずゲームが動く状態を保つ。

解答例を見る（まず自分でやってから）

ステップ1 ― 新しい入り口を作る（動作は変わらない）

// Enemy.h
public:
    void SetMover(std::unique_ptr<IMover> mover) { m_mover = std::move(mover); }

private:
    std::unique_ptr<IMover> m_mover;   // ★ 最初は全部 nullptr
    void UpdateOldMove();               // ★ いままでの処理をそのまま

// Enemy.cpp
void Enemy::Update()
{
    const float dt = g_gameTime->GetFrameDeltaTime();

    if (m_mover != nullptr) {
        m_mover->Move(m_position, dt);
    } else {
        UpdateOldMove();               // ★ いまはこちらしか通らない
    }
    ...
}

この時点でビルドして、動作が変わっていないことを確認します。 m_mover は全部 nullptr なので、 まだ何も変わっていないはずです。

ステップ2 ― 雑魚だけ移す

// EnemyFactory.cpp
case enEnemyType_Zako:
    e->SetHp(10);
    e->SetMover(std::make_unique<StraightMover>(200.0f));   // ★ ここだけ
    break;

case enEnemyType_Shooter:
    e->SetHp(30);
    // ★ まだ SetMover しない → 旧処理のまま
    break;

ビルドして、雑魚の動きが前と同じか確認します。 違ったら StraightMover の速度が合っていません。 ここで直せば、影響は雑魚だけです。

ステップ3 ― 1種類ずつ繰り返す

[コミット] Zako を IMover に移行
[コミット] Shooter を IMover に移行
[コミット] Tank を IMover に移行
[コミット] Bomber を IMover に移行

ステップ4 ― 旧処理を消す

void Enemy::Update()
{
    const float dt = g_gameTime->GetFrameDeltaTime();

    if (m_mover != nullptr) {
        m_mover->Move(m_position, dt);
    }
    ...
}
// ★ UpdateOldMove() を削除
どの時点でも、ゲームは動いています ステップ2と3のあいだで作業を中断しても、問題ありません。 新旧が混ざったまま、ちゃんと遊べます。

「今日は時間がないから、ここで止めよう」ができる というのが、このやり方のいちばんの価値です。

比較のしかた

「前と同じ動きか」を目で確認するのは、意外と難しいものです。 4-11 のリプレイがあると、 同じ入力で2回動かして見比べられます。

やってはいけないこと 移行の途中で「ついでに動きを良くする」のは禁止です。

前と違う動きになったとき、 「移行ミスなのか、意図した改良なのか」が分からなくなります。

改良は、全部移り終わってから。別のコミットで。

09確認

  1. リファクタリングと、バグ修正・機能追加を混ぜてはいけないのはなぜ？
  2. 名前の変更に、検索と置換を使ってはいけないのはなぜ？
  3. ストラングラーパターンの利点は？
  4. リファクタリングしなくてよい場所は？
答え
  1. 壊れたとき、整理のミスか修正の誤りか区別できなくなるから。
  2. コメントや、たまたま同じ名前の別の変数まで書き換えてしまうから。
  3. どの時点でもゲームが動いている。途中で中断できる。
  4. もう触らない、動いている場所。
