02計測用の道具を用意する

// Bench.h
#pragma once
#include <chrono>
#include <cstdio>

/// <summary>
/// ブロックにかかった時間を、出力ウィンドウに出す。
/// </summary>
class ScopedTimer {
public:
    explicit ScopedTimer(const char* name)
        : m_name(name), m_start(std::chrono::high_resolution_clock::now()) {}

    ~ScopedTimer()
    {
        auto end = std::chrono::high_resolution_clock::now();
        double ms = std::chrono::duration<double, std::milli>(end - m_start).count();

        char buf[256];
        sprintf_s(buf, "%-28s : %8.3f ms\n", m_name, ms);
        OutputDebugStringA(buf);
    }

private:
    const char* m_name;
    std::chrono::high_resolution_clock::time_point m_start;
};

#define BENCH(name) ScopedTimer bench_timer_##__LINE__(name)

5-02 の K2_PROFILE_SCOPE と同じ RAII です。 こちらは1回きりの実験用に、出力ウィンドウへ直接出します。

03実験1 ― 2次元配列を、縦に読むか横に読むか

void Experiment1()
{
    const int N = 2048;
    static int a[N][N];        // 16MB。スタックには置けないので static

    // 初期化
    for (int y = 0; y < N; y++) {
        for (int x = 0; x < N; x++) { a[y][x] = 1; }
    }

    long long sum1 = 0, sum2 = 0;

    {
        BENCH("横に読む（連続）");
        for (int y = 0; y < N; y++) {
            for (int x = 0; x < N; x++) {
                sum1 += a[y][x];        // ★ メモリの並び順どおり
            }
        }
    }

    {
        BENCH("縦に読む（飛び飛び）");
        for (int x = 0; x < N; x++) {
            for (int y = 0; y < N; y++) {
                sum2 += a[y][x];        // ★ 8KB ずつ飛ぶ
            }
        }
    }

    // 最適化で消されないように、結果を使う
    char buf[128];
    sprintf_s(buf, "sum1=%lld sum2=%lld\n", sum1, sum2);
    OutputDebugStringA(buf);
}

命令の数はまったく同じです。足す順番が違うだけ。

典型的な結果 

横に読む（連続）              :    3.412 ms
縦に読む（飛び飛び）          :   38.907 ms     ← 11倍
なぜか a[y][x] は、x 方向に連続して並んでいます。
横に読むと、1回のキャッシュライン（64バイト＝int 16個）で 16回ぶんまかなえます。
縦に読むと、毎回 8KB 先へ飛ぶので、 1回読むたびにキャッシュミスします。

04実験2 ― 飛ばす幅を変える

void Experiment2()
{
    const int N = 16 * 1024 * 1024;     // 64MB
    static int a[N];
    for (int i = 0; i < N; i++) { a[i] = 1; }

    for (int step = 1; step <= 64; step *= 2) {
        long long sum = 0;
        char name[64];
        sprintf_s(name, "step = %2d", step);

        {
            ScopedTimer t(name);
            for (int i = 0; i < N; i += step) {
                sum += a[i];
            }
        }
    }
}

読む要素の数は、step が倍になるごとに半分になります。 ふつうに考えれば、時間も半分になるはずです。

典型的な結果 

step =  1  :  12.4 ms   （1600万個）
step =  2  :   8.1 ms   （800万個）
step =  4  :   6.9 ms   （400万個）
step =  8  :   6.5 ms   （200万個）
step = 16  :   6.3 ms   （100万個）  ← ここまでほぼ変わらない
step = 32  :   3.2 ms   （50万個）
step = 64  :   1.6 ms   （25万個）
step = 16 まで、時間がほとんど減りません int は4バイト。16個で64バイト ＝ ちょうど1キャッシュライン。
step が16以下のあいだは、 「どのみち同じキャッシュラインを読んでいる」ので、 読む個数が減っても速くならないのです。

step が16を超えると、初めてキャッシュラインをまたぐようになり、 読むライン数が減って速くなります。

この折れ曲がりが、キャッシュラインが64バイトである証拠です。 自分の目で確認できます。

05実験3 ― 配列のサイズを変える

void Experiment3()
{
    // 何度もなめて、キャッシュに乗るかどうかを見る
    for (int kb = 16; kb <= 64 * 1024; kb *= 2) {
        int n = kb * 1024 / sizeof(int);
        std::vector<int> a(n, 1);

        // 同じ総アクセス回数になるよう、回数を調整
        long long total = 256 * 1024 * 1024 / sizeof(int);
        int loop = (int)(total / n);
        if (loop < 1) { loop = 1; }

        long long sum = 0;
        char name[64];
        sprintf_s(name, "%6d KB", kb);
        {
            ScopedTimer t(name);
            for (int k = 0; k < loop; k++) {
                for (int i = 0; i < n; i++) { sum += a[i]; }
            }
        }
    }
}

アクセスの総回数は、どのサイズでもほぼ同じです。 それなのに、時間は階段状に増えます。 

    16 KB :   45 ms      ← L1 に収まる
    32 KB :   46 ms
    64 KB :   58 ms      ← L1 からあふれた
   256 KB :   62 ms      ← L2
  1024 KB :   68 ms
  4096 KB :  105 ms      ← L2 からあふれた（L3）
 16384 KB :  118 ms
 65536 KB :  240 ms      ← L3 からあふれた（メインメモリ）
段差の位置が、自分のPCのキャッシュサイズです 5-03 の演習3で調べた値と、 段差の位置が一致するはずです。
一致したら、あなたはいま、自分のCPUの中身を外から観測したことになります。

06実験でよくある失敗

症状原因対策
0.000 ms になる 結果を使っていないので、ループごと消された 合計を printf などで使う
差が出ないDebug ビルド Release にする
毎回値がばらつく他のアプリ、電源設定 何回か測って中央値を取る
1回目だけ極端に遅い ページフォルト（OSがメモリを割り当てる） 捨てて、2回目以降を使う
スタックオーバーフローで落ちる 巨大な配列をローカル変数にした static か std::vector にする
1番目が、いちばんよく起きます Release のコンパイラは非常に賢く、 「結果が使われない計算」を丸ごと消します。
合計を計算しても、それを誰も読まなければ、ループごと消えます。
必ず、結果を外に出してください。

確認用のコード

template<class T>
void StepTest(const char* typeName)
{
    const int N = 16 * 1024 * 1024;
    static std::vector<T> a;
    a.assign(N, (T)1);

    char head[64];
    sprintf_s(head, "---- %s (sizeof=%zu) ----\n", typeName, sizeof(T));
    OutputDebugStringA(head);

    for (int step = 1; step <= 128; step *= 2) {
        double sum = 0;
        char name[64];
        sprintf_s(name, "  step = %3d", step);
        {
            ScopedTimer t(name);
            for (int i = 0; i < N; i += step) { sum += (double)a[i]; }
        }
        // 消されないように
        if (sum < 0) { OutputDebugStringA("never\n"); }
    }
}

void Run()
{
    StepTest<char>("char");
    StepTest<int>("int");
    StepTest<double>("double");
}

結果の見方

---- int (sizeof=4) ----
  step =   1 :  12.4 ms
  step =   2 :   8.1 ms
  step =   4 :   6.9 ms
  step =   8 :   6.5 ms
  step =  16 :   6.3 ms   ← ここまで横ばい
  step =  32 :   3.2 ms   ← ここから半減しはじめる
  step =  64 :   1.6 ms

---- double (sizeof=8) ----
  step =   1 :  24.1 ms
  step =   2 :  13.0 ms
  step =   4 :  12.4 ms
  step =   8 :  12.2 ms   ← ここまで横ばい
  step =  16 :   6.1 ms   ← 半分の step で折れる
  step =  32 :   3.0 ms
「64バイト ÷ 型のサイズ」で折れ曲がります 型を変えると折れ曲がる位置が変わる。 これで、64という数字が型ではなく 「メモリ側の単位」であることが確かめられます。

教科書に「64バイトです」と書いてあるのを読むのと、 自分で測って位置がずれるのを見るのとでは、 理解の質がまったく違います。
きれいに出ないこともあります CPUの先読み（プリフェッチ）が賢いので、 step が小さいうちは予想より速く出ることがあります。

折れ曲がりがぼやけていても、 「横ばい → 半減」の傾向が見えていれば成功です。

演習3（自分のゲームで）

自分のゲームの中で、飛び飛びにアクセスしている場所を探す。（ヒント：std::list、ポインタの配列、FindGO をループの中で呼んでいるところ）本文には答えがありません。

解答例を見る（まず自分でやってから）

探すべきパターン

パターンなぜ遅い直し方
std::vector<Bullet*> をなめる ポインタの先はバラバラ 5-06
ループの中で FindGO 毎回255本のリストを検索する ループの外で1回取る
std::map をなめる木構造。ノードがバラバラ vector ＋ ソート
2次元配列を縦に読む実験1そのもの ループの順番を入れ替える
std::string を大量に持つ 長い文字列はヒープに飛ぶ ID（int）に置き換える

いちばん多いのは、2番目です

// ★ よくある書き方
for (Enemy* e : m_enemies) {
    Player* p = FindGO<Player>("player");     // ★ 毎回呼んでいる
    if (p == nullptr) { continue; }
    e->ChaseTo(p->GetPosition());
}
// ○ 外に出す
Player* p = FindGO<Player>("player");
if (p != nullptr) {
    const Vector3 target = p->GetPosition();
    for (Enemy* e : m_enemies) {
        e->ChaseTo(target);
    }
}

FindGO は255本のリストを順に見て、 名前を strcmp で比較します。 敵50体ぶん呼べば、それだけで数千回の文字列比較です。

測って確かめる

{
    K2_PROFILE_SCOPE("EnemyChase");
    ...
}

直す前と後で数字を記録してください。 これは 5-01 の 「そもそもやらない」に当たる、いちばん効く種類の最適化です。

GOHandle を使うと、さらに良くなります 2-09 の GOHandle は、 名前ではなくインスタンスIDで引くので、 strcmp が走りません。 

// メンバに持っておく
GOHandle<Player> m_player;

// 使うとき
if (Player* p = m_player.Get()) { ... }
毎フレーム安全に取り直せて、しかも速い。
見つからなかったら、それでよいです 自分のゲームが十分に速いなら、直す必要はありません。

5-01 のとおり、 測ってボトルネックだと分かった場所だけ直してください。

08確認

  1. 同じ回数の足し算なのに、10倍の差が出るのはなぜ？
  2. 実験で「0.000 ms」が出たら、何を疑う？
  3. int の配列で、折れ曲がりが step=16 に出るのはなぜ？
答え
  1. データがキャッシュに乗っているかどうかが違うから。 計算ではなく、メモリ待ちの時間が違う。
  2. 結果を使っていないので、 コンパイラにループごと消された。
  3. 4バイト × 16 = 64バイト。 そこまでは同じキャッシュラインを読んでいるから。
