メモリリークとクラッシュダンプ

難易度 ／ 前提 5-01

01この章でできるようになること

  • メモリリークを見つけられる
  • 提出後に落ちたゲームの原因を、あとから調べられる
  • 「自分のPCでは動くのに」に対処できる

02メモリリークに気づく

F1 → Profiler の Memory を見てください。

様子判断
一定の値で落ち着いている正常
上下するが、平均は変わらない正常
じわじわ増え続ける リークの疑い
シーンを切り替えるたびに増える ほぼ確実にリーク
シーンを10回往復してみてください タイトル → ゲーム → タイトル → ゲーム …
そのたびにメモリが増えるなら、 シーン終了時に何かを消し忘れています。
いちばん見つけやすいリークです。

03Visual Studio でリークを検出する

// main.cpp の先頭
#define _CRTDBG_MAP_ALLOC
#include <crtdbg.h>

int WINAPI WinMain(...)
{
    // ★ 終了時に、解放されていないメモリを出力ウィンドウに出す
    _CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF);
    ...
}

プログラムを終了すると、出力ウィンドウにこう出ます。 

Detected memory leaks!
Dumping objects ->
Player.cpp(42) : {1483} normal block at 0x000001F2A4B0, 128 bytes long.
 Data: < ... >
Object dump complete.

ファイル名と行番号まで出ます。

ファイル名が出ないことも多いです new が .cpp の中で 直接呼ばれていないと、場所が特定できません。 （std::vector の中など）

そのときは確保番号 {1483} を使います。 
// main の先頭に置くと、1483回目の確保でブレークする
_CrtSetBreakAlloc(1483);
毎回同じ順番で確保されるなら、これで犯人を捕まえられます。

04k2Engine でよくあるリーク

やりがちなこと対策
シーンを消すとき、子のGOを消していない デストラクタで DeleteGO
new したものを delete していない std::unique_ptr を使う
Observer の解除忘れ RAII の Subscription
std::vector が増え続ける 「リーク」ではないが、同じ症状
ログの文字列を貯め続ける上限を決める
 
// シーンの終わりに、自分が作ったものを片付ける
GameScene::~GameScene()
{
    // QueryGOs で、自分が作ったものをまとめて消す
    QueryGOs<Enemy>("enemy", [](Enemy* e) {
        DeleteGO(e);
        return true;        // 続ける
    });

    DeleteGO(m_player);
    DeleteGO(m_score);
}
「リークではないが、メモリが増え続ける」ほうが多い std::vector に push_back し続けていて、 誰も消していないというパターンです。
これは delete 漏れではないので、 リーク検出には引っかかりません。

Profiler の Memory を見るのが、いちばん確実です。

05クラッシュダンプ ― 提出後に落ちたとき

「先生のPCで落ちました」と言われたとき、 原因を調べる手段がなければ、手も足も出ません。

落ちた瞬間のメモリの状態をファイルに書き出しておけば、 あとから Visual Studio で開けます。 

// CrashDump.cpp
#include <windows.h>
#include <DbgHelp.h>
#pragma comment(lib, "Dbghelp.lib")

namespace {

LONG WINAPI OnUnhandledException(EXCEPTION_POINTERS* ep)
{
    // ファイル名に日時を入れる
    SYSTEMTIME st;
    GetLocalTime(&st);

    char path[MAX_PATH];
    sprintf_s(path, "crash_%04d%02d%02d_%02d%02d%02d.dmp",
              st.wYear, st.wMonth, st.wDay,
              st.wHour, st.wMinute, st.wSecond);

    HANDLE hFile = CreateFileA(path, GENERIC_WRITE, 0, nullptr,
                               CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, nullptr);
    if (hFile != INVALID_HANDLE_VALUE) {
        MINIDUMP_EXCEPTION_INFORMATION mei = {};
        mei.ThreadId = GetCurrentThreadId();
        mei.ExceptionPointers = ep;
        mei.ClientPointers = FALSE;

        MiniDumpWriteDump(GetCurrentProcess(), GetCurrentProcessId(),
                          hFile, MiniDumpWithDataSegs, &mei,
                          nullptr, nullptr);
        CloseHandle(hFile);
    }

    MessageBoxA(nullptr,
        "エラーが発生しました。\n"
        "crash_*.dmp を開発者に送ってください。",
        "エラー", MB_OK | MB_ICONERROR);

    return EXCEPTION_EXECUTE_HANDLER;
}

}  // namespace

void SetupCrashDump()
{
    SetUnhandledExceptionFilter(OnUnhandledException);
}
// main.cpp
int WINAPI WinMain(...)
{
    SetupCrashDump();        // ★ いちばん最初に
    ...
}

06ダンプを読む

  1. .dmp ファイルを Visual Studio にドラッグする
  2. 「ネイティブのみでデバッグ」をクリック
  3. 落ちた行にカーソルが止まります
  4. コールスタックと、変数の中身が見られます
pdb ファイルが必要です .pdb（デバッグ情報）がないと、 関数名も行番号も出ません。
配布した .exe と、 まったく同じビルドの .pdb を 保存しておいてください。

ビルドし直すと、対応しなくなります。 提出したバージョンの .pdb は、 ソースコードと一緒に Git に入れるか、別に保管してください。

Release ビルドでも .pdb は作れます。 

プロパティ → C/C++ → デバッグ情報の形式 → /Zi
プロパティ → リンカー → デバッグ → デバッグ情報の生成 → はい (/DEBUG)
これを入れても、実行速度は落ちません .pdb は別ファイルなので、 .exe の中身も速度も変わりません。
Release ビルドに入れておかない理由がありません。

07そのほかの調査手段

手段使いどころ
ログをファイルに出す いちばん手軽。まずこれ
アサート（assert） おかしい状態を、その場で止める
リプレイ（4-11） 再現手順を、ファイルで渡せる
Application Verifier メモリの不正アクセスを、その場で捕まえる
イベントビューアー ダンプが無くても、落ちたモジュール名は分かる
 
// いちばん簡単なログ
void WriteLog(const char* format, ...)
{
    static FILE* fp = nullptr;
    if (fp == nullptr) {
        fopen_s(&fp, "game.log", "w");
        if (fp == nullptr) { return; }
    }

    va_list args;
    va_start(args, format);
    vfprintf(fp, format, args);
    va_end(args);

    fflush(fp);        // ★ これが大事。落ちても消えない
}
fflush を忘れないでください バッファに溜まったまま落ちると、 肝心の最後の数行が書かれません。
落ちる直前のログこそが、いちばん知りたい情報です。
毎回 fflush は遅いですが、デバッグ用なら構いません。

08演習

演習1（検出する）

_CrtSetDbgFlag を入れて、わざとリークを作って検出されるか確かめる。そのあと、自分のゲームで実行する。

演習2（追う）

シーンを10回往復して、Profiler の Memory が増えないか確認する。増えるなら、原因を突き止める。

解答例を見る（まず自分でやってから）

手順

  1. タイトル画面で Memory を記録（例：182 MB）
  2. ゲーム → タイトル を1往復して、また記録
  3. 10往復して、増え方を見る
== メモリ推移 ==
起動直後       182.4 MB
1往復後        189.1 MB   (+6.7)
2往復後        195.8 MB   (+6.7)
3往復後        202.5 MB   (+6.7)
...
10往復後       249.4 MB   (+67.0)

→ 1往復あたり 6.7MB。明らかにリーク

原因の絞り込み

試すこと分かること
F1 の GameObject List で、個数を見る GO が消えていないなら、一目で分かる
ゲームシーンで、敵を出さずに往復 敵が原因かどうか
UI だけのシーンで往復UI が原因かどうか
増加量から推測 6.7MB ÷ オブジェクトのサイズ で、おおよその個数
GameObject List パネルが、いちばん速い F1 → GameObject List で、 生きているオブジェクトの一覧と個数が見られます （2-06）。

往復するたびに「enemy」が30個ずつ増えていたら、 それが答えです。

メモリの数字を追うより、まずこのパネルを見てください。

よくある原因と直し方

// ★ 原因：シーンを消しても、子が残る
void GameScene::~GameScene()
{
    // 何もしていない → 敵も弾もUIも残り続ける
}

// ○ 直す
GameScene::~GameScene()
{
    QueryGOs<Enemy>("enemy", [](Enemy* e) { DeleteGO(e); return true; });
    QueryGOs<Bullet>("bullet", [](Bullet* b) { DeleteGO(b); return true; });

    if (m_player) { DeleteGO(m_player); }
    if (m_score)  { DeleteGO(m_score); }
    if (m_camera) { DeleteGO(m_camera); }
}
「自分が作ったものは、自分で消す」を徹底してください NewGO したクラスが、対応する DeleteGO の 責任を持つと決めておくと、漏れにくくなります。

2-05 でやった「寿命」の話が、 ここで効いてきます。

増えないのが確認できたら

== メモリ推移（修正後）==
起動直後       182.4 MB
1往復後        184.1 MB   (+1.7)   ← 最初だけ増える（キャッシュ）
2往復後        184.3 MB   (+0.2)
5往復後        184.4 MB   (+0.1)
10往復後       184.5 MB   (+0.1)

→ 落ち着いた。正常

最初の数回だけ増えて、そのあと横ばいになるのは正常です。 テクスチャやモデルのキャッシュ、アロケータの確保などです。

演習3（備える）

クラッシュダンプの仕組みを入れる。わざと落として、ダンプを Visual Studio で開けるか確かめる。

解答例を見る（まず自分でやってから）

わざと落とす

// デバッグパネルに、クラッシュさせるボタンを置く
if (ImGui::Button(U8("わざとクラッシュさせる"))) {
    int* p = nullptr;
    *p = 42;                  // ★ アクセス違反
}

確認の手順

  1. Release ビルドで、.pdb を生成する設定にする
  2. Visual Studio の外から .exe を起動する （デバッガに接続されていると、ダンプが出ません）
  3. ボタンを押して落とす
  4. crash_*.dmp ができているか確認
  5. その .dmp を Visual Studio にドラッグ
  6. 「ネイティブのみでデバッグ」をクリック

うまくいけば

例外がスローされました:
  0xC0000005: 場所 0x00000000 への書き込み中にアクセス違反が発生しました。

呼び出し履歴：
  Game.exe!DrawDebugPanel() 行 128
  Game.exe!nsDbg::DebugGui::Render() 行 240
  Game.exe!K2EngineLow::Execute() 行 88
  ...

落ちた行と、そこに至る呼び出しの履歴が全部見えます。

pdb が対応していないと、こうなります 
呼び出し履歴：
  Game.exe!0x00007FF6A2B41C30()
  Game.exe!0x00007FF6A2B0F881()
  ...
アドレスしか出ません。まったく役に立ちません。

配布した exe と同じビルドの pdb を、必ず保管してください。

提出時の準備

提出物/
├ MyGame.exe
├ Assets/
├ readme.txt
└ （手元に保管）
   ├ MyGame.pdb          ★ 配布はしないが、必ず取っておく
   └ ソースコードのコミットハッシュをメモ
これがあると、対応がまったく違います 「先生のPCで落ちました」

ダンプなし： 「すみません、こちらでは再現しなくて…」で終わり。

ダンプあり： 「dmp を送ってください」→ 5分で原因特定 → 修正版を提出。

就職後、これは当たり前に求められるスキルです。 製品版のゲームは、全部この仕組みを持っています。
個人情報に注意 ダンプにはメモリの内容が入ります。 ファイルパス（C:\Users\自分の名前\...）なども含まれます。

提出やネット公開の前に、何が入るか意識してください。 MiniDumpNormal にすると、含まれる情報を減らせます。

09確認

  1. リークを疑うのは、Profiler の何を見たとき？
  2. 「リークではないが、メモリが増え続ける」例は？
  3. クラッシュダンプを読むのに必要なものは？
  4. ログを書くとき、忘れてはいけないことは？
答え
  1. Memory が、じわじわ増え続けているとき。 特にシーンを往復するたびに増えるとき。
  2. std::vector に追加し続けている。 DeleteGO し忘れたゲームオブジェクトが残っている。
  3. そのビルドと対応した .pdb ファイル。
  4. fflush。落ちる直前の行が書かれないと意味がない。
