マルチスレッド② mutex と atomic

難易度 ／ 前提 5-10

01この章でできるようになること

  • 壊れない書き方ができる
  • mutex と atomic を使い分けられる
  • ロックの落とし穴（デッドロック、偽共有）を知っている

02mutex ― 1人ずつ通す

#include <mutex>

int        g_counter = 0;
std::mutex g_mutex;

void CountUp()
{
    for (int i = 0; i < 1000000; i++) {
        std::lock_guard<std::mutex> lock(g_mutex);   // ★ 鍵をかける
        g_counter++;
    }   // ★ ここで自動的に解除される
}

これで、必ず 4,000,000 になります。

lock_guard は RAII です これで5回目の RAII です。 { } を抜けたら、必ず解除されます。
return で抜けても、例外が出ても、解除されます。

g_mutex.lock() / unlock() を 手で書かないでください。必ずどこかで解除を忘れます。

03atomic ― 分割されない操作

#include <atomic>

std::atomic<int> g_counter{ 0 };

void CountUp()
{
    for (int i = 0; i < 1000000; i++) {
        g_counter++;        // ★ これだけで安全
    }
}

std::atomic は、 「読む・足す・書く」を分割されない1つの操作にします。 CPU の専用命令が使われます。

mutexatomic
守れるもの何でも（複数の変数、複雑な処理） 1つの変数の、単純な操作だけ
速さ遅い（数十〜数百 ns） 速い（数 ns）
待ちが発生するかする（他が終わるまで止まる） しない
使いどころ配列の操作、複数変数の更新 カウンタ、フラグ
atomic は「1操作」しか守れません 
std::atomic<int> g_hp{ 100 };

// ★ これは安全ではない
if (g_hp > 0) {         // 読む
    g_hp -= 10;         // ★ この間に、別スレッドが変えているかも
}
「読んで、判断して、書く」は3操作です。 それぞれは atomic でも、全体としては競合します。
こういう場合は mutex を使ってください。

04ロックは、思ったより高い

// ★ 遅い：100万回ロックする
for (int i = 0; i < 1000000; i++) {
    std::lock_guard<std::mutex> lock(g_mutex);
    g_counter++;
}

// ○ 速い：自分の中で数えて、最後に1回だけ足す
int local = 0;
for (int i = 0; i < 1000000; i++) {
    local++;
}
{
    std::lock_guard<std::mutex> lock(g_mutex);
    g_counter += local;        // ★ ロックは1回
}
やり方時間の目安
ロックなし（壊れる）2 ms
atomic25 ms
mutex を毎回180 ms
ローカルに貯めて最後に1回 2 ms
いちばん良いのは「共有しないこと」です ロックを速くする工夫より、 そもそも共有データを作らないほうが、はるかに効きます。

5-10 の演習3でやった 「スレッドごとに持って、あとで合流」が、これです。

05デッドロック

std::mutex mutexA, mutexB;

void Thread1()
{
    std::lock_guard<std::mutex> a(mutexA);    // A を取る
    std::lock_guard<std::mutex> b(mutexB);    // ★ B 待ち
}

void Thread2()
{
    std::lock_guard<std::mutex> b(mutexB);    // B を取る
    std::lock_guard<std::mutex> a(mutexA);    // ★ A 待ち
}

お互いが、相手の持っているものを待ちます。永遠に止まります。

対策説明
ロックの順番を決める 必ず A → B の順で取る、と決める
std::scoped_lock を使う 複数を一度に取る。デッドロックしない
そもそも2つ以上ロックしない いちばん確実
 
// C++17 以降。順番を気にせず、安全に複数取れる
std::scoped_lock lock(mutexA, mutexB);
ロックを持ったまま、関数を呼ばないでください 
std::lock_guard<std::mutex> lock(g_mutex);
SomeFunction();        // ★ この中でもロックを取っていたら？
呼んだ先で同じ mutex を取ると、自分自身で止まります。 （std::mutex は再帰的にロックできません）
ロックしている範囲は、できるだけ短く、単純に。

06偽共有（false sharing）

ロックも共有変数も使っていないのに、遅くなる現象です。 

struct Counter {
    int value;
};
Counter g_counters[4];       // ★ スレッドごとに1個

void Work(int id)
{
    for (int i = 0; i < 10000000; i++) {
        g_counters[id].value++;     // ★ 自分のぶんしか触らない
    }
}

安全です。でも、遅いです。

Counter は4バイト。 4個並べても16バイト ＝ 同じキャッシュライン（64バイト）に収まります （5-04）。

コア1が g_counters[0] に書くたびに、 そのキャッシュライン全体が「変更された」扱いになり、 コア2のキャッシュが無効化されます。 触っている場所は違うのに、です。 

// 対策：キャッシュライン単位に離す
struct alignas(64) Counter {
    int value;
    char padding[60];
};
Counter g_counters[4];       // ★ それぞれ別のキャッシュラインに乗る
これだけで、5〜10倍速くなることがあります 「マルチスレッドにしたのに速くならない」の、 隠れた原因のひとつです。
5-03 で「L1 はコアごと」と書いた話が、 ここで効いてきます。

07演習

演習1（直す）

5-10 の実験1を、mutex と atomic の両方で直して、それぞれの時間を測る。

演習2（速くする）

ローカルに貯めて最後に1回だけ足す形に書き直して、時間を比べる。

解答例を見る（まず自分でやってから） 
#include <thread>
#include <mutex>
#include <atomic>
#include "Bench.h"

namespace {
    const int N = 1000000;
    const int NUM_THREAD = 4;
}

void CompareLocking()
{
    //--- (1) ロックなし（壊れる）---
    {
        static int counter = 0;
        counter = 0;
        BENCH("(1) ロックなし（壊れる）");
        std::vector<std::thread> ts;
        for (int t = 0; t < NUM_THREAD; t++) {
            ts.emplace_back([]{ for (int i = 0; i < N; i++) { counter++; } });
        }
        for (auto& t : ts) { t.join(); }
        char b[64]; sprintf_s(b, "    -> %d\n", counter);
        OutputDebugStringA(b);
    }

    //--- (2) atomic ---
    {
        static std::atomic<int> counter{0};
        counter = 0;
        BENCH("(2) atomic");
        std::vector<std::thread> ts;
        for (int t = 0; t < NUM_THREAD; t++) {
            ts.emplace_back([]{ for (int i = 0; i < N; i++) { counter++; } });
        }
        for (auto& t : ts) { t.join(); }
        char b[64]; sprintf_s(b, "    -> %d\n", counter.load());
        OutputDebugStringA(b);
    }

    //--- (3) mutex を毎回 ---
    {
        static int counter = 0;
        static std::mutex m;
        counter = 0;
        BENCH("(3) mutex 毎回");
        std::vector<std::thread> ts;
        for (int t = 0; t < NUM_THREAD; t++) {
            ts.emplace_back([]{
                for (int i = 0; i < N; i++) {
                    std::lock_guard<std::mutex> lock(m);
                    counter++;
                }
            });
        }
        for (auto& t : ts) { t.join(); }
        char b[64]; sprintf_s(b, "    -> %d\n", counter);
        OutputDebugStringA(b);
    }

    //--- (4) ローカルに貯める ---
    {
        static int counter = 0;
        static std::mutex m;
        counter = 0;
        BENCH("(4) ローカルに貯めて1回");
        std::vector<std::thread> ts;
        for (int t = 0; t < NUM_THREAD; t++) {
            ts.emplace_back([]{
                int local = 0;
                for (int i = 0; i < N; i++) { local++; }
                std::lock_guard<std::mutex> lock(m);
                counter += local;
            });
        }
        for (auto& t : ts) { t.join(); }
        char b[64]; sprintf_s(b, "    -> %d\n", counter);
        OutputDebugStringA(b);
    }
}

典型的な結果（Release、4スレッド）

(1) ロックなし（壊れる）       :    2.104 ms
    -> 1382914                                ★ 値が違う
(2) atomic                     :   24.883 ms
    -> 4000000
(3) mutex 毎回                 :  182.447 ms
    -> 4000000
(4) ローカルに貯めて1回        :    2.011 ms   ★ 速くて正しい
    -> 4000000
(4) が (1) と同じ速さで、しかも正しい ロックの回数を 400万回から 4回に減らしただけです。

「速くて正しい」が両立しています。

なぜ (2) の atomic も遅いのか

atomic の操作自体は数ナノ秒です。 ところが4つのコアが同じ変数を取り合うと、 キャッシュラインがコア間を行ったり来たりします。

これをキャッシュラインのピンポンといいます。 偽共有と同じ現象で、変数が本当に共有されている場合です。

(1) が (4) と同じ速さなのに注意 「ロックを外したら速くなった」と喜んではいけません。

速いのは、正しく動いていないからです。

必ず結果の値を確認してください。 マルチスレッドでは、速度より先に正しさを確認する癖をつけてください。

演習3（偽共有を見る）

偽共有を再現して、alignas(64) で直す。何倍速くなったか。

解答例を見る（まず自分でやってから） 
#include <thread>
#include <vector>
#include "Bench.h"

namespace {
    const int N = 10000000;
    const int NUM_THREAD = 4;
}

// ★ 詰まっている版
struct CounterPacked {
    int value;
};

// ★ キャッシュラインごとに離した版
struct alignas(64) CounterPadded {
    int value;
    char padding[60];
};

void FalseSharingTest()
{
    //--- 詰まっている ---
    {
        static CounterPacked counters[NUM_THREAD] = {};
        BENCH("詰まっている（偽共有あり）");
        std::vector<std::thread> ts;
        for (int t = 0; t < NUM_THREAD; t++) {
            ts.emplace_back([t]{
                for (int i = 0; i < N; i++) { counters[t].value++; }
            });
        }
        for (auto& t : ts) { t.join(); }

        char b[128];
        sprintf_s(b, "    sizeof=%zu  合計=%d\n",
                  sizeof(CounterPacked),
                  counters[0].value + counters[1].value
                + counters[2].value + counters[3].value);
        OutputDebugStringA(b);
    }

    //--- 離してある ---
    {
        static CounterPadded counters[NUM_THREAD] = {};
        BENCH("離してある（偽共有なし）");
        std::vector<std::thread> ts;
        for (int t = 0; t < NUM_THREAD; t++) {
            ts.emplace_back([t]{
                for (int i = 0; i < N; i++) { counters[t].value++; }
            });
        }
        for (auto& t : ts) { t.join(); }

        char b[128];
        sprintf_s(b, "    sizeof=%zu  合計=%d\n",
                  sizeof(CounterPadded),
                  counters[0].value + counters[1].value
                + counters[2].value + counters[3].value);
        OutputDebugStringA(b);
    }
}

典型的な結果

詰まっている（偽共有あり）     :  142.883 ms
    sizeof=4  合計=40000000
離してある（偽共有なし）       :   18.201 ms     ← 7.8倍速い
    sizeof=64  合計=40000000
どちらも結果は正しいのに、7.8倍違います 共有変数は1つもありません。ロックもありません。

それぞれのスレッドが、自分専用の変数しか触っていません。

それでも遅い。これが偽共有の怖さです。

何が起きているか

メモリ上の配置（詰まっている版）

  ┌────────── 1本のキャッシュライン（64バイト）──────────┐
  │ counters[0] │ counters[1] │ counters[2] │ counters[3] │ …   │
  └──────────────────────────────────────────────────────┘
       コア0         コア1         コア2         コア3

コア0 が counters[0] に書く
  → このキャッシュラインが「変更された」状態になる
  → コア1・2・3 が持っていた同じラインのコピーが無効化される
  → コア1 が counters[1] を触ろうとすると、
     自分は何も変えていないのに、メモリから読み直しになる

これが毎回起きるので、実質メモリアクセスになります。

実務での対処

やり方備考
alignas(64) で離す 単純。メモリは食う
ローカル変数に貯めて、最後に書く いちばん良い。演習2と同じ
std::hardware_destructive_interference_size C++17。環境ごとの正しい値が取れる
 
// いちばん良い形
ts.emplace_back([t]{
    int local = 0;                        // ★ スタック上。コアごとに別
    for (int i = 0; i < N; i++) { local++; }
    counters[t].value = local;            // ★ 書き込みは1回だけ
});
結局、いつも同じ結論になります 「共有を減らす」「書き込みを減らす」。

ロックの技術を磨くより、 そもそも触らない設計にするほうが、速くて安全です。

08確認

  1. mutex と atomic の使い分けは？
  2. atomic でも守れないのは、どんな処理？
  3. デッドロックを防ぐ、いちばん確実な方法は？
  4. 偽共有とは？ 対策は？
答え
  1. 複数の変数や複雑な処理は mutex。 単一変数のカウンタやフラグは atomic。
  2. 「読んで、判断して、書く」のように、複数の操作にまたがるもの。
  3. 2つ以上のロックを同時に取らないこと。 取るなら順番を決めるか scoped_lock。
  4. 別々の変数が同じキャッシュラインに乗り、 コア間で無効化し合う現象。alignas(64) で離すか、 ローカルに貯めて最後に1回書く。
